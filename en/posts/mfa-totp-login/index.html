Understanding MFA and Dynamic Verification Codes Through a Login

Eva·2026.10.09·17 min read

 

You enter your password and click Log In, only for the website to ask you to open your phone's authenticator and enter six digits. You just proved you know the password. Why verify yourself again?

Start with that login screen. If someone else already has your password, how will the server handle their login request?

A password-only system struggles to distinguish you from them. Both submit exactly the same secret, so the server naturally gives the same result. Even a very long password has this problem once it is fully exposed.

MFA adds another check that can still stop the other person at that point.

This article follows the common “account password plus authenticator” flow, explaining an account's journey from enabling protection to everyday login and recovering after losing a device. Algorithm and security requirements are checked against RFCs, NIST, and OWASP materials. The implementations described illustrate the principles; they do not imply that a particular project already includes these features.

What can you verify after a password leaks?

A password proves that you know a secret. The system can also require proof that you control an authenticator bound to the account in advance.

Someone who knows the password then still lacks the second condition. You can open your authenticator to obtain the current code; someone with only the password usually cannot.

These are two different categories of proof, or two “authentication factors.”

Authentication factorWhat it provesCommon examples
Knowledge factorYou know a secretPassword, PIN
Possession factorYou control an authenticator or the secret it containsAuthenticator, security key
Biometric factorYour physical characteristics meet the requirementFingerprint, face

MFA is the umbrella term for multifactor authentication; both 2FA and 3FA are forms of MFA. MFA stands for Multi-Factor Authentication and requires at least two different categories of authentication factors.

The “password plus authenticator code” flow combines knowledge and possession factors, making it 2FA, or two-factor authentication. It already satisfies MFA, so a website can reasonably call it either MFA or 2FA. A third factor is not required.

If a system also requires a fingerprint and correctly combines and verifies a password, hardware security key, and fingerprint, it constitutes 3FA, or three-factor authentication. The distinction is the number of factor categories used; MFA and 2FA are not two separate login technologies.

Three verification steps do not necessarily constitute 3FA. Entering a password, SMS code, and TOTP code looks like three steps, but the last two usually both represent possession. The flow still uses only two categories. Count the categories of proof, not pages or input boxes.

This also explains why “asking one more question” may not help. A security question after a password still tests what you know. There are two steps, but only one factor category. Logging in with only an SMS verification code usually uses just one possession factor; a verification code alone does not mean MFA is enabled.

For this account, we are choosing a password plus an authenticator. The password already exists; next, the website must recognize your authenticator. Otherwise, anyone could open an app that generates numbers—why should the server accept yours?

The setup QR code links your phone to your account

Open the account's security settings and enable an authenticator. The website typically displays a QR code, asks you to scan it, and then asks for the code shown in the app.

This step is called binding or enrollment.

The server first generates a random secret for the account, called a shared key. The QR code carries that key along with the account name, issuer, and algorithm parameters. After scanning it, the authenticator saves this information, giving the phone and server identical copies of the secret. The common otpauth:// format conveys this enrollment information.

Below the QR code, you may also see an option to enter the key manually. This is an alternative when scanning is unavailable.Both the QR code and manual key must remain secret: anyone who obtains their contents may be able to reproduce the same codes.

Why enter a verification code after scanning? Displaying a QR code does not establish that the phone saved the key correctly. You may have scanned the wrong account or closed the page midway. Checking the first code generated by the phone confirms that both sides can calculate from the same information before changing the factor from “pending confirmation” to “enabled.”

The current user's identity must also be verified before binding. Someone who happens to access a device you left logged in should not be able to easily bind their own authenticator. Replacing or disabling MFA later similarly requires reauthentication proportionate to the risk.

The phone now stores the key. Its displayed numbers count down and change at the end of each interval, even without a network connection.

Where do these numbers come from?

How can an offline phone produce numbers the website accepts?

The phone and server agree on an algorithm and independently calculate using the shared key and current time. They do not need to send codes to each other every few dozen seconds.

This mechanism is TOTP, short for Time-Based One-Time Password. A common configuration uses six digits, refreshed every 30 seconds. The number of digits and time interval are configurable; neither value is a universal requirement.

Set formulas aside for now. Imagine dividing time into consecutive intervals. Within the same interval, both parties obtain the same time number and combine it with the same key to calculate the same digits. In the next interval, the number changes, and so does the result.

The algorithm's “time step” is this number.

T = floor((当前 Unix 时间 - 起始时间) / 时间步长度)
TOTP = HOTP(共享密钥 K, 时间步 T)

HOTP in the formula is another one-time-password algorithm. It uses a key and counter, applying HMAC and truncation to produce digits suitable for entry. TOTP builds on it by replacing the event counter with a time step. In real development, use mature libraries and standard test vectors rather than implementing these cryptographic details yourself.

The abbreviations now fall into place. OTP is the general category of one-time-password mechanisms; HOTP and TOTP are specific algorithms. MFA and 2FA describe how many different factors a login combines. We use TOTP for the possession factor and combine it with a password to provide two-factor authentication.

The phone can calculate offline because both its key and clock are local. Accessing the website still requires a network connection, of course.

Clock inaccuracies can cause problems. A phone may run slightly fast or slow, or a user may submit at the final second of a countdown. Servers typically need an explicitly limited time tolerance to verify neighboring time steps. A wider window accepts more possible codes at once, so tolerance cannot grow indefinitely.

Storage differs here as well. To verify TOTP, the server must recalculate with the shared key. It therefore usually encrypts the key and manages the decryption master key separately from the database. An irreversible hash alone cannot support this calculation. Enrollment QR codes, shared keys, and submitted dynamic codes should also stay out of logs.

Only after these preparations does the account have a usable second factor. Log out and log back in to see how it works.

At the next login, the correct password only gets you halfway

You enter your account and password, and the server confirms the password. For an account requiring MFA, it should retain a restricted intermediate state while awaiting code verification.

This temporary state is often called an MFA challenge. It records the account being verified, what is permitted, and when it expires. The browser may use it to submit a code, but not to read business data.

You then see a second page asking you to open your authenticator. After you enter its current digits, the server retrieves the account's shared key, calculates results within the allowed time window, and compares them. Only successful verification establishes a full session with application access.

Between those two checks, the account must not receive full application access. If a full session is issued immediately after password verification and only a frontend code prompt follows, an attacker can skip the page and use that session to call backend APIs directly. The second page exists, but its protection does not.

The server must therefore distinguish two facts. Having MFA enrolled means a factor is available; completing MFA in the current session means this particular login met the requirement. Session refresh must retain the relevant authentication information and expiry, and must not silently promote an incomplete login.

A website usually does not ask for another code every time you open an article. After login, the browser carries session credentials that identify the authenticated login. Changing an authenticator or performing a sensitive operation may require recent reauthentication. Risk signals such as changed devices or login locations can also trigger additional verification.

Authentication still does not confer administrator privileges. The server must separately check what the account may do. An ordinary member who completes MFA can access only authorized data.

The login flow now appears complete, but dynamic codes hide one easily overlooked issue.

Can the same code be used twice before the countdown ends?

Within one time step, the digits displayed on the phone do not change. If the server checks only whether the digits match, two consecutive submissions may both succeed.

That conflicts with the one-time requirement.

TOTP generates numbers that change over time; the server must also remember which time step has already succeeded. After verification, a database transaction and conditional update should mark that step and the current challenge as consumed so later requests cannot succeed again. A common approach stores the most recently accepted time step for the factor and accepts only newer values allowed by policy.

This process must handle concurrency. Two requests can arrive almost simultaneously and both read “unused.” Without atomicity between reading and writing, both might pass. Verification must ensure only one request consumes the challenge and receives a usable session. If the database fails, full privileges must not be granted first.

If the client does not receive the success response, the user may need to restart verification. Safe retry handling is possible, but a consumed code cannot simply become valid again.

Guessing codes is another problem. Six digits provide a limited space, so failed attempts must be restricted. Limiting only an individual challenge is insufficient: an attacker may repeatedly request new challenges. Apply account-level rate limits as well, with source addresses as an additional dimension. Set thresholds according to system risk and actual usage.

At this point, a leaked password alone cannot complete this login flow. But the more effective these restrictions are, the more important reliable recovery becomes when a legitimate user loses their authenticator.

How do you recover an account after losing your phone?

This is why websites often ask you to save recovery codes when enabling MFA.

Recovery codes are pregenerated random backup credentials, each invalidated after successful use. Unlike TOTP, they usually do not change every few dozen seconds. Store them somewhere accessible even after losing the phone. A screenshot kept only on that same phone may disappear along with your backup method.

The server does not need the original recovery codes to recalculate dynamic codes, so it can store hashes of high-entropy recovery codes and their usage state. This differs from TOTP shared keys, which must be decryptable.

Return to the login screen with a lost phone. The password is correct, but TOTP is unavailable, so the user chooses recovery. The system verifies a recovery code under predefined rules, consumes it on success, and guides the user through regaining access or binding a new authenticator.

Define in advance which step the recovery code replaces, whether a password remains required, and which functions become accessible afterward. An administration console could issue a short-lived, restricted recovery session, require enrollment of a new authenticator, and only then restore full access. Revoke the old factor and remaining old recovery codes according to policy, and notify the account holder of the change.

If every authenticator and recovery code is lost, the user must follow a predefined identity-verification process. Support staff cannot disable MFA after improvising a few easily guessed questions, because an attacker could take the same route.

Recovery is therefore part of authentication design. If normal login is strict but recovery checks only an easily compromised email account, attackers may take over through that route. Whether email can support a particular recovery step depends on the complete flow; NIST's out-of-band authentication requirements do not accept email as that type of authentication channel either.

We have now connected enrollment, login, and device-loss handling for an account. One more situation deserves attention. The phone is not lost and the code has not been exposed for long: it was just entered into a fake website immediately after generation. What happens then?

Dynamic codes can also be phished. How can the second factor improve?

An attacker can relay them in real time.

The user enters a password and current code into a fake page; the attacker immediately submits both to the real website. If verification is still valid, login may succeed. TOTP's short lifetime reduces the opportunity for abuse but cannot independently stop immediate exploitation.

Other verification methods are easier to understand once you see which link each changes.

SMS delegates code delivery to telecommunications networks, adding risks such as number transfers and SIM swaps. Push approval removes manual digit entry, but users must recognize legitimate requests, and repeated notifications may lead to accidental approval. Both require carefully designed failure and recovery flows.

FIDO security keys and passkeys use public-key authentication. During registration, the authenticator creates credentials for the service and the server stores the public key. At login, the server issues a challenge, the authenticator signs with the private key, and the server verifies the signature. A correctly implemented WebAuthn flow checks the service identifier and origin, preventing a phishing domain from freely obtaining and using authentication results for the real site.

This provides phishing resistance and changes the user's interaction. They may insert a security key or approve with a device PIN, fingerprint, or face, without copying dynamic digits into a webpage.

Fingerprint verification usually happens locally on the device; the website does not need fingerprint data. When the service correctly requires and verifies user verification, the device credential and local PIN or biometric can jointly provide multifactor authentication. A single fingerprint action can therefore satisfy multiple factors.

This does not contradict the “two inputs” at the start. The authentication method determines the number of factors. Passwordless login means only that the site's password is unused; it does not automatically establish a factor count. Logging in through an email link also offers different protection from a passkey with user verification.

Recovery still matters after choosing passkeys. Credentials may be bound to one device or synchronized through a credential provider. You need to understand how new devices obtain them and how the synchronization account is recovered. With traditional TOTP, keeping the password and code-generating secret in the same password manager is also a tradeoff: it reduces effort, but a complete compromise of that storage system can expose both credentials together.

There is also a shared boundary. After successful login, the browser receives session credentials. If an attacker steals still-valid credentials, they may access the application directly without revisiting the code page. HTTPS, cookie protection, defenses against script injection, and session revocation remain necessary.

Applying this flow to your own project

To add MFA to an existing system, review the journey this account just followed. First decide which accounts must enable it and how existing users will transition, then check the state required at each step.

Account stageWhat the server must storeWhat must be prevented
Preparing enrollmentPending factor, encrypted shared key, and expiryActivation before confirmation
Password acceptedShort-lived challenge, account, purpose, and failure countPremature application access
Dynamic code acceptedConsumed time step, consumed challenge, and session authentication informationReplay and duplicate concurrent success
Everyday accessSession expiry, revocation state, and application permissionsPromotion of unverified sessions or unauthorized access
Lost deviceRecovery-code hashes, consumption state, and recovery permissionsRepeated recovery or bypassed identity verification

Challenge tokens must be sufficiently random, and sensitive database information needs appropriate protection. Operational backups must also account for decryption keys: a database backup without its master key may leave existing TOTP enrollments unrecoverable.

For acceptance testing, walk through the entire flow with a controlled account. Exit halfway through scanning and confirm that the factor stays disabled. After password verification, call a business API directly and confirm access is still denied. Then submit the same code concurrently, confirm only one attempt succeeds, and verify that expired challenges cannot be reused.

Next, simulate an unavailable phone and rebind using a recovery code. Consumed recovery codes must not work again, and revoked authenticators must no longer authenticate. When the database fails or a response is lost, check that the system leaves no improperly usable session.

Finally, log in in the target environment and check certificates, clocks, and mandatory-enrollment policy. Even after the page says “MFA enabled,” test every entry point from logout through account recovery.
