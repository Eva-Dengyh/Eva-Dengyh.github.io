Harness Engineering: Engineering Principles That Make AI Agents Truly Useful

Eva·2026.04.22·20 min read

 

 

Agent = Model + Harness

Understanding Harness Engineering starts with a definition:

Agent = Model + Harness

The model is the source of intelligence; the harness is the system that makes that intelligence useful. The converse also holds: if a component is not the model itself, it is part of the harness.

A bare model is not an agent. It takes text, images, and audio as input and outputs text. That is all. Out of the box, it cannot maintain persistent state across sessions, execute code, access real-time knowledge, or set up an environment to get work done. The harness builds these capabilities around the model.

A harness includes:

  • System Prompts: Inject initial instructions and context
  • Tools, Skills, MCPs: Give the model callable capability interfaces
  • Infrastructure: Execution environments such as filesystems, sandboxes, and browsers
  • Orchestration logic: Subagent scheduling, task dispatch, and model routing
  • Hooks / Middleware: Deterministic execution layers for checkpoints, linting, compaction, and more

Deriving Harness Structure from Model Limitations

Every harness component can be derived by asking, "What do we want the agent to do that a bare model cannot?"

The Filesystem: The Most Basic Harness Primitive

A model can directly manipulate only information in its current context window. Before filesystems, providing data meant pasting content directly into the conversation, which is completely impractical for autonomous agents.

The filesystem is the harness's central primitive because it unlocks a range of higher-level capabilities:

  • Agents gain a workspace where they can read code, data, and documents
  • Intermediate artifacts can be written and read incrementally, without keeping everything in context
  • Task state can persist across sessions
  • Multiple agents or people can collaborate through shared files; the filesystem is a natural collaboration interface
  • With Git, agents can track changes, roll back mistakes, and run parallel experiments

Bash + Code Execution: A General-Purpose Tool

Today's mainstream agent execution pattern is the ReAct loop: model reasoning → tool call → observe results → reason again. But a harness can only execute tools whose logic it already implements. Designing a tool for every possible operation is extremely expensive and inflexible.

Giving an agent a Bash tool is a better solution: the model can design the tools it needs by writing code, rather than being confined to a fixed set of preconfigured tools. Code execution has become the default general-purpose strategy for autonomous problem solving.

Sandboxes: Safe Execution Environments

Once you have filesystem access and code execution, you still need somewhere to run them. Executing agent-generated code locally poses security risks, and a single local environment cannot support large numbers of concurrent agent tasks.

Sandboxes let agents run code, inspect files, and install dependencies in isolation. The harness decides where an agent runs, what it can access, and which commands it can execute. These are all harness-layer design decisions; a model cannot configure its own execution environment.

Sandboxes also enable scale: execution environments can be created on demand, distributed in parallel, and destroyed after tasks finish.

Memory and Search: Overcoming Knowledge Limitations

A model's knowledge is locked in its training weights; information outside its context is invisible to it. The solution is context injection.

The filesystem comes into play again here. Memory-file standards such as AGENTS.md let agents accumulate and pass knowledge between sessions: an agent writes what it learned in the current session to a file, and the harness injects that file into context at the start of the next session, creating a form of continuous learning.

For real-time knowledge after the training cutoff, Web Search and MCP tools such as Context7 give agents access to the latest library versions, current data, and other information that did not exist during training.

Two Core Engineering Challenges

Context Rot

Agent performance should not degrade the longer it works, but in practice it does. This phenomenon is called Context Rot: as the context window fills, the model's reasoning quality and task-completion ability steadily decline.

A harness needs dedicated mechanisms to combat context rot:

Compaction: As the context window approaches its limit, the harness must strategically summarize and offload existing context so the agent can keep working instead of being interrupted by an API error.

Tool-output truncation: Large tool responses can fill the context window, even though useful information often appears only at the beginning and end. The harness retains the first and last tokens, offloads the full output to the filesystem, and reads it on demand when needed.

Progressive disclosure of Skills: Loading every tool and MCP server into context at once consumes many tokens before the agent even starts. Skills address this through progressive disclosure: relevant Skill metadata is injected into context only when needed.

These mechanisms share one principle: Context is a scarce resource, and the harness is the execution layer for context engineering.

Long-Horizon Execution

Enabling agents to autonomously complete complex tasks over extended periods is one of the central challenges in agent engineering today. Bare models face problems such as premature termination, inability to decompose complex problems, and inconsistent behavior across multiple context windows.

Ralph Loop: A harness pattern that intercepts a model's attempts to exit through a hook, reinjects the original task objective into a fresh context window, and forces the agent to keep progressing until completion criteria are met. The filesystem makes this possible: each iteration starts with clean context but reads the previous state from disk.

Planning and self-verification: Through prompt injection and filesystem support, the harness helps agents break goals into steps and verify each step's output by running tests, inspecting logs, and comparing expected results. Test results and errors return to the model as feedback, forming a self-correction loop.

Design by Contract: The Harness's Constraint Layer

Beyond supplying capabilities—the tools and environments a model needs—a harness also needs a constraint layer to manage the model's nondeterministic behavior.

Every LLM output is the result of probabilistic sampling, and behavior is extremely sensitive to context. More importantly, prompt constraints are soft in engineering terms:

  • Attention dilution: As conversation turns accumulate, constraints in the system prompt carry progressively less weight in the overall context
  • Physical truncation: When the context window fills, the earliest content—usually constraint rules—is discarded first
  • No execution semantics: Natural-language instructions constrain a model probabilistically, not through enforcement

The harness's constraint layer is best understood through Design by Contract:

Preconditions: Before the model performs a high-impact operation, the harness inserts a mandatory checkpoint. The model must produce a structured execution intent—goal, scope, side effects, and verification method—which external logic, rather than the model itself, validates before allowing execution. The crucial point is that validation happens outside the model.

Postconditions: After an operation, the harness requires verification evidence from external systems: unit-test results, runtime logs, API responses, and filesystem diffs. This evidence becomes the model's next input, switching it from self-assessment to evidence-driven operation.

Invariants: Maintain an external state document recording task goals, completed work and supporting evidence, technical decisions and their reasons, and unresolved issues. The model's internal context may disappear at any time, but this document remains the task's single source of truth, allowing any session to restore its state.

Capability Design: Narrowing the Model's Decision Space

The harness addresses execution boundaries; capability design addresses capability boundaries.

Exposing tools at too fine a granularity creates two problems: the huge space of tool combinations makes decisions hard to validate, and dependencies and side effects between tools remain unencapsulated, so a mistake at any step can cascade.

A better approach is to package tools into capabilities with clear business semantics:

# 暴露基础工具：Model 需要自己组合和判断副作用
tools = [read_file, write_file, run_sql, call_api, ...]

# 封装成 Capability：Model 只需选择业务操作
capabilities = [
    update_user_profile,    # 内部封装校验、写库、缓存失效
    run_regression_suite,   # 内部封装环境准备、执行、结果收集
    deploy_to_staging,      # 内部封装构建、推送、健康检查
]

Each capability contains its own validator. The model's unit of decision changes from "which API should I call, with what parameters?" to "which business operation should I choose?" A smaller decision space is easier to validate and less likely to go out of control.

Recognizing Poor Harness Design

Before discussing how to build a harness properly, we must distinguish two fundamentally different problems: having no harness at all, and having a poor-quality harness. They manifest differently and require entirely different remedies.

No Harness at All

These designs share one feature: there are no enforced constraints outside the model, and all control relies on the model's internal "self-restraint."

The soft-constraint trap: Piling rules and prohibitions into the system prompt and expecting the model to follow them voluntarily. This effectively hands control of execution boundaries to the probabilistic engine itself. The longer the rules, the more likely they are to be diluted or forgotten during long workflows, with no external mechanism to guarantee their enforcement at any moment.

Missing tool boundaries: Exposing many fine-grained tools without defining usage boundaries leaves tool selection entirely to the model's reasoning. This is more than a capability-design problem: it is a loss of control at the harness layer, with no mechanism to intervene before a dangerous tool call.

Neither case constitutes a harness, because the control plane is not outside the model.

A Harness Exists, but Its Quality Is Poor

These designs have external control flow, but their control methods introduce new problems.

Bare retry loops: On detecting an error, simply feed the error back into the model's context and let it retry indefinitely. This is external control, but it does not realign goals and boundaries before retrying. In such a loop, the model converges toward whatever it thinks will eliminate the error, rather than the correct solution; fixing a syntax error may come at the cost of deleting an entire module. Effective retries require the model to restate the current objective and confirm the repair scope before each iteration, rather than continuing unchecked.

Excessive up-front documentation: Forcing the model to produce extensive design documents before taking any action, making documentation a prerequisite for execution. This is a form of state management, but the wrong granularity or timing has two costs: many tokens are spent generating documents, and documents become an unmaintainable burden once they diverge from execution. State management should provide a lightweight source of truth that stays synchronized, rather than heavyweight one-off documentation.

The distinction matters: the first problem calls for introducing a harness; the second calls for improving its design. Conflating them leads to trying to solve "no external constraints" by "adding more documentation," or evading "overly crude control" by "removing control entirely."

Managing Goal Hierarchies in Long Tasks

In long-horizon execution, beyond Ralph Loops and planning mechanisms, there is an easily overlooked runtime problem: models tend to bypass the current phase's specific objective and advance directly toward their interpretation of the overall goal.

The behavior looks busy, but each step tries to solve everything at once instead of progressing through decomposed steps. The longer the workflow, the further execution drifts from the plan.

An effective harness must maintain three levels of goals at runtime and keep them separate:

Overall goal: The completion criteria for the entire task or current major stage. This is an anchor that does not change with the outcome of an individual execution round.

Phase goal: The scope of problems that may be addressed over the next several conversation turns. Until a phase ends, the model must not bring the next phase's work into the current scope.

Current-round action goal: The number and boundaries of operations allowed in a single execution round, usually limited to one to three concrete actions.

The key constraint across these levels is: completing a phase does not mean completing the overall goal. Once a phase has converged, the harness must explicitly communicate that conclusion to the model, rather than letting it decide on its own whether to advance to the next phase.

Redefining Goals at Runtime

The goal hierarchy is not set once at the start and then frozen. When external evidence during execution—test failures, log anomalies, or API errors—conflicts with the current phase goal, that goal must be redefined.

This redefinition does not reject the plan; it is the normal mechanism by which the harness responds to real feedback. A typical example: the phase was meant to "complete feature X," but runtime logs reveal a systemic issue in a dependency chain. The phase goal should narrow to "first identify the root cause of the chain failure." Once that issue is resolved and accepted, work on the original phase goal can resume.

The harness supplies the external evidence that triggers redefinition and then forces the model to acknowledge the new phase boundaries, preventing it from immediately drifting back toward the overall goal.

Harness Control Points Within an Execution Round

Understanding harness architecture is one thing; understanding how it manifests in actual execution is another. In a complete execution round, harness control logic acts at the following key points.

Point One: Align on Goals Before Any Implementation

At the start of a task, the harness's first control point is to have the model restate its understanding rather than execute immediately: what it sees as the overall goal, the current phase's main focus, and the boundaries and open questions.

This step explicitly extracts the model's intent, exposing misunderstandings so they can be corrected before any code is written. Skip it, and faster subsequent execution only makes drift harder to notice.

Point Two: A Minimal Spec Locks the Round's Scope

After goal alignment, the model does not proceed straight to implementation. It first produces a lightweight execution spec: the current round's goal, scope boundaries, explicitly excluded work, and verification method.

The spec's central purpose is to prevent the model from smuggling higher-level goals into the current round. Without explicit boundaries, execution naturally expands toward the overall goal, turning a round intended only for A into simultaneous work on A, B, and C. The spec is the contract for this round; only what it contains may be executed.

Point Three: A Pre-execution Checkpoint

Before the model makes any actual change, the harness inserts a mandatory checkpoint: the model must explain in its own words its current understanding, concrete next actions, expected side effects, and how completion will be verified. Execution begins only after a person or rules engine confirms this output.

A checkpoint is not a formality; it is the final external validation of execution intent. If the model cannot articulate its plan clearly here, it usually has not formed a stable execution plan. Letting it proceed simply postpones the problem until execution.

Point Four: Acceptance Based on External Evidence

After execution, the harness refuses to accept the model's self-assessment as a completion signal. Acceptance rests on only three categories: test results; runtime logs and observed workflow behavior; and direct evidence from a test environment or manual verification.

This transfers authority over the completion judgment from the model to external systems. Models have a strong tendency to declare success after a task, but that tendency reflects generation probabilities, not whether the result is correct. External evidence is the only reliable acceptance criterion.

Acceptance must also explicitly distinguish two levels: whether the current phase goal is complete, and whether the overall goal is complete. These questions must be answered separately; the former cannot stand in for the latter.

Point Five: Runtime Course Correction

When surprises arise during execution—logged errors, API anomalies, or failed tests—the harness's runtime correction mechanism intervenes.

The key is to narrow the current round's scope before continuing the original plan. If logs reveal a systemic problem in a workflow, the round's goal narrows from "complete feature X" to "identify the root cause of the workflow problem." Only after that cause is demonstrably resolved does work on the original goal resume.

The most important point is that models naturally tend to "fix a few other things while they are at it" when receiving error feedback. The harness must keep repairs within the current minimal goal, rather than allowing expansion into other problems before the present repair is complete.

After correction, acceptance must again rely on external evidence—whether this minimal goal was actually completed—not the model's subjective judgment.

Future Directions for Harness Engineering

Harness Engineering is actively evolving. Several directions deserve attention:

Coevolution of model training and harness design: Current agent products already incorporate the harness into training. Models are post-trained through interaction with the harness, gradually acquiring stronger native abilities in filesystem operations, Bash execution, task planning, and parallel subagent work. As this loop continues, a model becomes stronger within the harness it was trained on, but can also overfit its details: changing tool-calling logic may reduce performance. Harness design is therefore an important variable in agent capability.

Dynamic harness assembly: Most harnesses today are statically preconfigured, with tools and context determined before a task begins. The future direction is to assemble exactly the tools and context needed for the current task on demand, rather than preload everything that might be used.

Agents analyzing harness failures: Let agents analyze their own execution traces, identify failure patterns at the harness layer, and suggest improvements, enabling the harness to optimize itself.

When to Introduce a Harness

Introducing a harness has an engineering cost. Use the following framework to assess where it applies:

ScenarioRequired harness components
Single call, stateless, repeatable taskAlmost none
Operations with side effects (database writes, API calls, file changes)Execution gates (preconditions)
Ongoing tasks across sessionsState Store + invariants
Evidence-based acceptance rather than trusting model self-assessmentEvaluator (postconditions)
Extended autonomous executionRalph Loop + planning + self-verification
Collaboration among multiple agents or peopleFilesystem as a shared collaboration layer
Complete enterprise deliveryAll of the above

The longer the workflow, the greater the side effects, and the more participants involved, the more valuable the harness becomes.

Summary

Harness Engineering is an engineering approach to building systems around model intelligence. The model handles reasoning and decisions; the harness enables that intelligence to work reliably, verifiably, and sustainably in real engineering environments.

Its core components are derived from two directions: model limitations imply the capabilities that must be supplied—filesystems, code execution, sandboxes, and memory—while engineering reliability requirements imply the necessary constraints—preconditions, postconditions, and invariants.

Prompt Engineering determines what a model can generate in a given context; Harness Engineering determines under what conditions those outputs are accepted or rejected, and how task state is saved and restored across sessions. They address problems at different layers.
