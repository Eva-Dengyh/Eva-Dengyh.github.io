FastSAM-Demo/V3: Interactive Image Segmentation with SAM 2.1 and a Go Gateway

Eva·2026.05.20·10 min read

 

An open-source click-to-segment web application: upload an image and click an object to cut it out.
The frontend uses Next.js, the backend uses FastAPI + SAM 2.1, and a custom Go inference gateway between them provides sticky routing and horizontal scaling.

GitHub: https://github.com/Eva-Dengyh/FastSAM-Demo
License: MIT

What the project looks like

Open the page → drag in an image → click an object → see the segmentation highlighted in real time. Multiple clicks select multiple objects with different colored overlays. Export the original image, the overlay, or masks only.

The model is Meta's SAM 2.1 (Segment Anything Model 2), open-sourced under Apache 2.0. Weights download directly without an application. The tiny version is as small as 39 MB and runs on a CPU; the 224 MB large version flies on a GPU.

This update: From one process to multiple workers and a Go gateway

The project originally connected Next.js directly to a single FastAPI process. This refactoring inserts a Go inference gateway between frontend and backend, upgrading it to horizontally scaled workers with business-aware routing.

Before and after

旧:  浏览器  ──▶  FastAPI 单进程  ──▶  SAM 2.1

新:  浏览器  ──▶  Go Gateway (:8080)  ──┬──▶  FastAPI worker-0  ──▶  SAM 2.1

Why this layer is needed

The central motivation is straightforward: sticky routing, rather than high concurrency.

SAM 2.1 inference has two steps:

  • set_image() computes image embeddings: 0.5–3 seconds (slow, compute-intensive)
  • predict() produces masks: 20–100 milliseconds (fast, decoder only)

Uploading computes the embedding and caches it in one worker's memory. Every later click on that image must return to the same worker to hit the cache; otherwise it requires recomputation, roughly 30 times slower, or produces an error.

Routing by image_id operates at the business level:

  • nginx's ip_hash / hash $cookie_xxx cannot do this—the sticky key lives in the multipart upload response's JSON body
  • Python cannot handle it alone either: separate processes cannot see each other's state

So I added a Go gateway. Its httputil.ReverseProxy.ModifyResponse hook intercepts response JSON, extracts image_id into a session table, and uses image_id to look up the worker for subsequent segmentation requests. A dozen or so lines solve the problem.

What the gateway does

Seven subpackages and just over a thousand lines of Go handle:

CapabilityImplementation
Sticky routingimage_id → worker_id session table with TTL and a background sweeper
Concurrency controlOne bounded channel and N consumer goroutines per worker; immediate 429 when full
Load balancingNew sessions go to the healthy worker with the shortest queue
Unhealthy worker removalPeriodically ping /health; consecutive failures remove the worker and clear its sessions, while consecutive successes restore it
Cold-start protectionWorkers start unhealthy and receive traffic only after passing probes
Cross-service tracingX-Request-Id generated at entry → forwarded by ReverseProxy → logged by the backend
Graceful shutdownAfter SIGTERM, stop accepting connections and wait for in-flight requests
ObservabilitySeven Prometheus metrics plus zerolog structured logging

Two layers of concurrency protection

Go does not handle everything. Python retains a fallback asyncio.Semaphore layer so even a misconfigured gateway concurrency limit cannot exhaust GPU memory. It is a small detail that keeps the system safe under configuration errors.

Frontend-friendly error semantics

Status codeMeaningFrontend action
200SuccessNormal processing
410image_id expired: worker restart, TTL expiry, or removalAutomatically upload the image again
429Worker queue fullBack off and retry according to Retry-After
503No available workersWait for health checks to restore availability

The frontend's lib/api.ts implements these semantics so network fluctuations and backend restarts are invisible to users.

With Grafana connected, the health of the whole system is visible at a glance.

Current capabilities

Features

  • Drag-and-drop upload + real-time Canvas rendering
  • Click-to-segment, with millisecond responses when the embedding cache is hit
  • Multiple-object management, different colored overlays, and list-based addition and removal
  • Three export modes: Original image / overlay / masks only
  • Horizontal scaling + automatic recovery, with worker failures invisible to users
  • RLE-compressed mask transmission, achieving over 98% compression

Core data flow

upload:
  前端 ──multipart──▶ Gateway
                       ├─ 选最低负载 worker
                       ├─ ReverseProxy 流式转发(不读进 Gateway 内存)
                       ├─ 拦响应 JSON 截 image_id
                       └─ sessions.Put(image_id, worker_id)
                          │
                          └──▶ FastAPI ──▶ SAM 2.1 set_image() 缓存 embedding

segment:
  前端 ──{image_id, points}──▶ Gateway
                                ├─ 按 image_id 查会话表 → 命中粘性 worker
                                └─ 不命中返 410 → 前端自动重新上传
                                   │
                                   └──▶ 同一 worker ──▶ predict() 复用 embedding

Running in five minutes

Docker (recommended)

git clone https://github.com/Eva-Dengyh/FastSAM-Demo.git
cd FastSAM-Demo

# 下载模型权重(只需一次)
mkdir -p models
wget -O models/sam2.1_hiera_tiny.pt \
  https://dl.fbaipublicfiles.com/segment_anything_2/092824/sam2.1_hiera_tiny.pt

docker-compose up --build

Open http://localhost:3001 to use it.

Local development

Requires Go 1.22+, Python 3.10+ with uv, and Node 18+.

./start.sh

Automatically starts two backends (:8000 / :8002), the gateway (:8080), and frontend (:3000).

Verifying the multiworker path

./scripts/verify-multiworker.sh

Automatically performs eight uploads to verify load balancing and sticky routing. Uploads should be evenly distributed between the two workers, and all segmentation requests for the same image_id should always reach the same worker.

What comes next

The project currently segments individual images, but the architecture and model offer several directions for expansion. The following roadmap is open to contributions.

Video segmentation

SAM 2.1's main advantage over SAM 1 / MobileSAM is video support through temporal propagation with memory attention. The current version does not use it. Adding this capability would give a compelling answer to why the project chose SAM 2.1.

Required technical work:

  • Introduce SAM2VideoPredictor in the backend for frame-by-frame inference and temporal propagation
  • Add long-running tasks to the gateway: POST to obtain task_id → progress over WebSocket → fetch results on completion
  • Build a frontend timeline, keyframe prompts, and per-frame mask overlays

Text-prompt segmentation: Grounding DINO + SAM

Upgrade interaction from clicking to typing: enter “cat,” let Grounding DINO detect bounding boxes, and have SAM generate masks. This popular open-vocabulary segmentation combination would move the project from single-modal to multimodal.

A data-annotation tool

Add batch uploads, annotation export (COCO / YOLO / Pascal VOC), manual mask editing, undo/redo, and user accounts to turn the demo into a small annotation tool people can actually use.

Making full use of the Go gateway

  • Move SessionTable to Redis: Make the gateway stateless, supporting multiple instances and rolling upgrades without lost sessions
  • Automatic scaling with Kubernetes HPA: Use gateway_queue_depth as a custom metric to scale GPU workers by queue depth
  • Replace configuration-based discovery with service discovery: List-watch Kubernetes endpoints so worker changes need no configuration edits

Other directions to explore

  • Real-time WebSocket segmentation, with local prediction and background correction while dragging continuously
  • Hot-switch models at runtime among tiny / small / base+ / large
  • iOS / Android clients using Expo + React Native
  • Grafana dashboards + alert rules

Final thoughts

This project started as a way to test SAM 2.1's interactive web experience. Along the way, I ended up refactoring the entire backend architecture.

I am sharing it to:

  • Give people building image segmentation a ready-to-use starting template
  • Provide a concrete example for anyone considering horizontal scaling for Python inference services—nginx really cannot handle this sticky-routing requirement
  • Gather feedback and issues to keep improving the architecture

Stars, forks, PRs, and issues are welcome, as is criticism—especially of the Go gateway. I would love to hear more elegant implementation ideas.
