Chapter 1: What Is Hermes?

A one-sentence definition:

Hermes Agent is a self-improving AI agent framework built by Nous Research. It is one of the most complete open-source agent solutions available, integrating multiplatform access, persistent memory, evolving skills, and parallel subagent execution.

What you can do with it:

在终端里跟它聊天                    ✅
在 Telegram 里跟它聊天              ✅
在 Discord 里跟它聊天               ✅
在微信里跟它聊天                    ✅
让它帮你读写文件、搜索网页、跑代码     ✅
让它记住你说过的重要事情              ✅
让它从错误里学习，下次做得更好         ✅
设置定时任务让它自动执行              ✅
同时做多件独立的事（子Agent）         ✅
切换到任何一个 LLM 模型              ✅
把它部署在云端，省电省钱              ✅

Why "Hermes"?

Hermes, the messenger god of Greek mythology, was the fastest and best informed. The name reflects two core agent capabilities: delivering messages and responding quickly.

Chapter 2: Why Has Hermes Taken Off?

2.1 The AI Agent Market in 2024–2025

Most AI agent products have the following pain points:

Locked to one model, such as Claude or GPTSwitch to any model with one configuration change, without changing code
Locked to one platform, such as Telegram or DiscordOne gateway connects all major chat platforms

Resource consumption and high always-on operating costsCloud hibernation on Daytona or Modal, with near-zero idle costs

2.3 Technical Highlights

Several Hermes modules achieve industry-leading capabilities in their respective areas:

  • Memory system: Full-session history search using SQLite FTS5, plus LLM summaries
  • Skills system: Agent-driven automatic extraction and reuse of experience
  • Context compression: Intelligent summary-based compression that preserves key information
  • Terminal backends: Six supported backends: local, Docker, SSH, Daytona, Modal, and Singularity
  • MCP integration: Connect any external tool server using Model Context Protocol

Chapter 4: Core Module Design

Hermes's architecture revolves around three core questions:

问题1：工具越来越多，怎么管理？       → 注册表模式（Registry Pattern）
问题2：模型越来越多，怎么切换？       → Provider 抽象层
问题3：功能越来越多，代码怎么改？      → 插件化（Plugins）+ Skills

Chapter 5: The Tool System (Registry Pattern)

5.1 Background

  • Hermes includes 60+ tools and supports dynamic expansion through MCP
  • The tool count continues to grow without making the code chaotic
  • Tools have different dependencies: some require API keys, while others only operate on local files
  • Tools must be enabled or disabled by platform; for example, certain sensitive tools are enabled only in CLI mode

5.2 Three-layer Architecture

第1层：定义层（每个工具文件）
  tools/file_tools.py  ─┐
  tools/terminal_tool.py ─┼─ 每个文件末尾调用 registry.register()
  tools/web_tools.py    ─┘

第2层：注册中心（tools/registry.py）
  唯一真相来源：_registry[name] = ToolEntry(...)
  提供 register() / get() / dispatch() 三个接口

第3层：分发层（model_tools.py）
  handle_function_call(name, args)
  根据 name 找到 registry entry，调用 handler，返回 JSON 字符串

5.3 Tool Registration

Each tool file, such as todo_tool.py, has the following structure:

# ============ 第1步：定义 Schema（给 AI 模型看的说明书）============

TODO_SCHEMA = {
    "name": "todo",
    "description": (
        "管理任务清单。..."
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "todos": {
                "type": "array",
                "description": "任务列表..."
            },
            "merge": {
                "type": "boolean",
                "description": "是否合并..."
            }
        },
        "required": []
    }
}

# ============ 第2步：实现 Handler（真正做事的 Python 函数）============

def todo_tool(todos=None, merge=False, store=None):
    # ... 实际逻辑 ...
    return json.dumps({"todos": current_list})

# ============ 第3步：注册到全局注册表（末尾调用一次即可）============

registry.register(
    name="todo",                    # 工具名
    toolset="todo",                 # 属于哪个工具组
    schema=TODO_SCHEMA,              # Schema 说明书
    handler=lambda args, **kw: todo_tool(...),  # 执行函数
    check_fn=check_todo_requirements,  # 可用性检查
    emoji="📋",                      # UI 图标
)

Key Insight: Schema and Handler Are Completely Separate

  • The schema is an instruction manual for the AI model, describing the tool's name, parameters, and function
  • The handler is the executor: the actual Python logic
  • Changing the schema does not affect the handler, and vice versa

5.4 Tool Discovery

Tool loading is fully automatic and happens when model_tools.py is imported:

def _discover_tools():
    """Import all tool modules to trigger their registry.register() calls."""
    _modules = [
        "tools.todo_tool",
        "tools.file_tools",
        "tools.terminal_tool",
        "tools.web_tools",
        # ... 60+ 个模块
    ]
    for mod_name in _modules:
        importlib.import_module(mod_name)  # 导入时自动注册

_discover_tools()  # 模块加载时立即执行

Adding a tool therefore means adding a Python file and one registration line at the bottom, with zero configuration.

5.5 Toolset Grouping

Tools are grouped by function, and each group can be enabled or disabled as a whole:

toolset "file"      → read_file, write_file, patch, search_files
toolset "terminal"  → terminal, process (background process)
toolset "web"       → web_search, browser_navigate, browser_snapshot
toolset "delegate"  → delegate_task (子 Agent)
toolset "session"  → session_search (跨会话搜索)
toolset "skills"    → skill_view, skill_manage, skills_list

Users can configure groups through the hermes tools command rather than setting up each tool individually.

Chapter 6: The Messaging Gateway (Adapter Pattern)

6.1 Background

Different chat platforms use entirely different messaging protocols:

Telegram：     通过 Bot API (HTTP Long Polling)
Discord：      通过 WebSocket Gateway API
Slack：        通过 WebSocket + HTTP
WhatsApp：     通过 Baileys/Meta 官方 API
Email：        通过 IMAP/SMTP

If platform-specific handling lives directly in the core, every new platform requires risky changes to core code.

6.2 Adapter-pattern Architecture

                        统一消息格式
                         ▲
                         │ Gateway Core (run.py)
                         │
┌────────────────────────┼─────────────────────────────────────────────┐
│                        │                                             │
│    ┌───────────────────┴───────────────────┐                         │
│    │                                       │                         │
│    ▼                                       ▼                         │
│  Telegram 适配器                        Discord 适配器                  │
│  platform/telegram.py                   platform/discord.py           │
│                                         │                             │
│  解析 Telegram API                      解析 Discord WebSocket         │
│  → 统一消息                             → 统一消息                     │
│                                         │                             │
│  发送：统一回复                         发送：统一回复                 │
│  → Telegram API                         → Discord API                │
└───────────────────────────────────────────────────────────────────────┘

Unified message format, defined by the Gateway Core:

class UnifiedMessage:
    user_id: str          # 用户唯一标识
    platform: str         # "telegram" / "discord" / ...
    text: str             # 消息文本
    attachments: list      # 图片/文件等附件
    chat_id: str          # 会话 ID
    thread_id: str | None # 话题 ID（支持 Discord thread 等）
    timestamp: datetime   # 时间戳

6.3 Why Is This Design Good?

  • Adding a platform: Write only a new adapter file, around 500–1,000 lines; the core run.py requires no changes
  • Independent evolution: Each platform adapter can be tested and upgraded independently
  • Fault isolation: A crash in one platform's adapter does not affect other platforms or the core

Chapter 7: The AI Loop (ReAct Pattern)

7.1 What Is ReAct?

ReAct = Reason + Act. This is currently the dominant design pattern for AI agents:

Reason（思考）：AI 模型分析当前情况，决定下一步做什么
Act（行动）：   AI 模型调用工具执行

交替进行，直到任务完成

7.2 Hermes's AI Loop

┌─────────────────────────────────────────────────────────────┐
│                     run_agent.py 核心循环                     │
│                                                             │
│  while (api_call_count < max_iterations                     │
│         AND iteration_budget.remaining > 0):                 │
│                                                             │
│      ┌──────────────────────────────────────────────────┐  │

│      │      ...（完整对话历史）                           │  │

│      │      │      role:"tool",                          │  │
│      │      │      tool_call_id: xxx,                   │  │

│      │      │                                            │  │

7.3 Why Is a Loop Necessary?

Complex tasks cannot be completed in one step. For example:

用户："帮我分析 /project 目录的代码，写一份报告"

AI 第1轮思考："我需要先看看目录里有哪些文件"
  → tool_call: terminal("ls -la /project")

AI 第2轮思考："好，我看到有 main.py, utils.py, tests/ 等"
  → tool_call: read_file("main.py")
  → tool_call: read_file("utils.py")

AI 第3轮思考："文件内容读完了，我来写报告"
  → 最终回复（无 tool_call，break 出去）

7.4 Loop Control: iteration_budget

Set a maximum iteration count to prevent the AI from calling tools forever:

class IterationBudget:
    max_total = 90        # 最多 90 次 API 调用
    remaining = max_total

    def consume(self) -> bool:
        """返回 False 表示预算耗尽，强制退出"""
        if self.remaining <= 0:
            return False
        self.remaining -= 1
        return True

Scenario: If a tool returns an error, such as a network timeout, the AI may repeatedly retry it. Once the budget is exhausted, execution is forcibly stopped to prevent an infinite loop.

7.5 What If the Context Gets Too Long?

When conversation history grows close to the model's context limit, it triggers context compression:

压缩前：
messages = [系统提示词, 用户问题1, AI回答1, 用户问题2, AI回答2, ... 100轮...]

压缩后：
messages = [
    系统提示词,
    [摘要: 前50轮对话的核心信息],
    最近10轮完整对话  ← 总是保留最新的对话
]

Compression strategy (context_compressor.py):

  • Protect recent turns: Never compress the most recent N conversation turns
  • Summarize the middle: Use an LLM to summarize earlier conversation, retaining key points
  • Recount: Re-estimate tokens after compression to ensure the context remains within limits

8.3 Responsibilities of prompt_builder.py

prompt_builder.py dynamically assembles these layers, deciding what to include based on the following factors:

def _build_system_prompt(self) -> str:
    layers = []

    # 第1层：基础身份
    layers.append(self._get_identity_block())

    # 第2层：工具列表（只包含当前启用的工具）
    layers.append(self._get_tools_block())

    # 第3层：用户偏好（从 memory 读取）
    if self.memory_enabled:
        layers.append(self._get_user_preferences_block())

    # 第4层：当前上下文
    layers.append(self._get_context_block())

    # 第5层：Skills 指令
    layers.append(self._get_skills_block())

    return "\n\n".join(layers)

Chapter 9: Memory and Skills

9.1 Ordinary Memory vs. Skills

普通记忆（Memory）         → 存储事实（"用户叫 Eva"）
Skills                   → 存储经验（"遇到 X 类型问题，用 Y 方法解决"）

9.2 How Memory Works

用户说："我下周三要去北京出差"

            │
            ▼ 记忆工具自动提取
┌─────────────────────────────────────────────┐
│  实体提取：                                  │
│    - 用户：Eva                              │
│    - 事件：出差                              │
│    - 地点：北京                              │
│    - 时间：下周三                            │
│                                             │
│  存储到 ~/.hermes/memory/                  │
│  文件：travel_beijing_eva_2025.md           │
└──────────────────────┬──────────────────────┘
                       │
           下一轮对话开始时
                       │
                       ▼ 从 memory/ 读取相关记忆
           注入系统提示词 → AI 知道"用户要出差去北京"

9.3 How Skills Work

Skills are Hermes's most distinctive innovation. The central idea is:

"Rather than telling an agent how to work, let it learn how to work for itself."

用户让 Hermes 完成一个复杂任务
  → Hermes 执行完成
  → Hermes 问自己："我应该把这次经验记成一个 Skill 吗？"
  → 如果值得记住：
      创建 ~/.hermes/skills/my-skill/SKILL.md
      内容包括：
        - 这个 Skill 在什么场景下触发
        - 具体操作步骤
        - 注意事项和陷阱
  → 下次遇到同类任务：
      Hermes 自动检索相关 Skill → 加载步骤 → 执行

Skill storage format (Markdown):

# python-debug

## 触发条件
当用户描述了 Python 错误、异常、或要求"帮我调试"时触发。

## 操作步骤
1. 首先让用户提供完整的错误信息
2. 使用 terminal_tool 运行出错命令，获取完整 stack trace
3. 分析错误类型：
   - SyntaxError → 检查拼写和缩进
   - ImportError → 检查包是否安装、路径是否正确
   - IndexError  → 检查列表边界
4. 根据错误类型逐一排查
5. 提供修复方案和修改后的代码

## 注意事项
- 不要在看到完整错误前就猜测原因
- stack trace 从下往上看，找到第一个 ERROR 行

9.4 Retrieving and Invoking Skills

When a user describes a task, Hermes automatically:

  1. 1. Retrieves — Searches the Skills directory for relevant Skills
  2. 2. Loads — Injects the matching Skill's Markdown into the prompt
  3. 3. Executes — Follows the Skill's steps

Chapter 10: Model Abstraction (Provider Pattern)

10.1 Background

Dozens of LLM providers use different API formats and authentication methods. Hard-coding one API would require extensive code changes when switching models.

10.2 Hermes's Solution

Hermes code uses only an OpenAI-compatible format:

from openai import OpenAI

client = OpenAI(
    api_key="sk-xxx",
    base_url="https://api.anthropic.com"  # 可以指向任何兼容端点
)

# 这个调用格式，可以是：
#   - Claude（通过 Anthropic 或 OpenRouter）
#   - GPT-4（原生 OpenAI）
#   - 任何 OpenRouter 支持的 200+ 模型
#   - 本地 Ollama 模型
client.chat.completions.create(
    model="claude-3-opus",
    messages=[...],
    tools=[...]
)

10.4 Switching Models

Users need just one command:

Chapter 11: What Makes the Architecture Good?

11.1 Four Dimensions for Evaluating Architecture

Maintainability: How much code must change to add a feature?

新增一个工具        → 新建 1 个 Python 文件 + 1 行注册代码
新增一个平台适配器   → 新建 1 个适配器文件
新增一个模型支持    → 改配置，不改代码
修复工具 Bug        → 只改该工具文件
核心重构            → 工具和适配器都不受影响

Testability: Can each module be tested independently?

工具函数           → ✅ 可以单独写单元测试
注册表             → ✅ 可以注册假工具后测试分发逻辑
适配器             → ✅ 可以 Mock 测试，不依赖真实 API
prompt_builder     → ✅ 可以构造不同配置测试输出

Extensibility: Can it run in more environments?

终端后端：        本地 / Docker / SSH / Daytona / Modal / Singularity
消息平台：        Telegram / Discord / Slack / WhatsApp / Signal / Email
外部扩展：        MCP（Model Context Protocol）支持任意外部工具服务器

Flexibility: Can unnecessary parts be disabled?

工具集（toolsets）  → 按组启用/禁用
平台适配器          → 配置文件开关
记忆系统            → 可关闭（节省资源）
Skills 系统         → 可关闭

12.2 Most Distinctive Feature: Self-evolving Skills

This is the biggest distinction between Hermes and all other agent frameworks.

Traditional agent:

用户每次遇到同类问题 → 都要重新描述一遍 → Agent 每次重新摸索

Hermes with Skills:

第1次遇到问题 → Agent 解决 → 判断值得记住 → 存入 Skill
第2次遇到同类问题 → Agent 自动找到 Skill → 直接套用经验
第N次 → Skill 越来越完善，Agent 越来越专业

Hermes thus achieves real learning—not by updating model parameters, but by accumulating experiential knowledge.

12.3 Most Practical Feature: Multiplatform Unification

A real workflow for most users:

在地铁上（微信）     → 发一条消息给 Hermes："帮我看看代码有没有 Bug"
到公司（电脑）        → 打开终端 → 继续同一个对话，Hermes 已经记住了任务
下班路上（Telegram）  → 再发一条："帮我写个报告总结今天的发现"
回家（躺在床上）      → 语音问 Hermes："今天完成了什么？"

The entire process is continuous, with the same agent, memory system, and accumulated Skills.
