OpenSpec: Spec-Driven Development for AI Coding

Eva·2026.05.22·15 min read

 

Introduction

Now that AI coding is part of everyday development, why do requirements that exist only in chat create a hidden delivery risk? And how can spec-driven development tools such as OpenSpec turn drifting AI collaboration into an engineering process that can be reviewed, resumed, and archived?

OpenSpec is not a new code generator or a more complex project-management system.

It adds a lightweight “specification track” to AI coding assistants: align on what to build before coding, document changes during development, and merge incremental specifications into the project's current source of truth afterward. It addresses not whether AI can write code, but whether people and models agree on the goal before coding, and whether the project remembers the change afterward.

This article draws on OpenSpec's official documentation, GitHub project description, and my observations using it in local projects. It shares a practical approach to AI collaboration and represents my personal views.

1. Why Does AI Coding Need a Specification Track?

Over the past year, discussion of AI coding tools has focused on which model is smarter, which IDE integration works best, and how to write prompts that make an Agent get changes right on the first attempt.

These questions matter. But once an AI coding assistant joins a continuously evolving project, the harder questions are:

  • Does it understand this requirement's boundaries?
  • Are its code changes based on current project facts or temporary impressions in chat?
  • If this conversation ends, can the next one resume without losing anything?
  • When several people work simultaneously, who knows why a requirement was designed this way?
  • If production breaks three weeks later, can we recover the original design context?

Traditional development cushions these problems with requirements documents, design reviews, task breakdowns, PR reviews, and test cases. With AI assistants, many teams instead compress those safeguards into a chat:

“Add dark mode.”

“Also follow the system theme.”

“That design was wrong; use localStorage instead.”

“Continue.”

This works smoothly in a demo. In a real project, it gradually becomes context debt.

A chat window is not an engineering source of truth. It is good for communication and exploration, but poor at carrying long-term requirements or serving as a reviewable, reversible, transferable team record.

OpenSpec addresses this gap by moving AI collaboration from temporary chats back into a version-controlled specification workflow inside the repository.

2. What Exactly Is OpenSpec?

OpenSpec is a lightweight Spec-Driven Development (SDD) framework for AI coding assistants. Through a CLI, Slash Commands, and Skills, it puts proposals, specifications, designs, tasks, and archives into the code repository, allowing people and AI to align on what to build before writing code.

In one sentence:

OpenSpec is a specification workbench that moves requirements context from chat into the code repository.

It gives AI's freedom a track to follow rather than simply making AI more “free.”

After initialization, the project contains an openspec/ directory with roughly this structure:

openspec/
├── specs/
│   └── <domain>/
│       └── spec.md
├── changes/
│   └── <change-name>/
│       ├── proposal.md
│       ├── design.md
│       ├── tasks.md
│       └── specs/
│           └── <domain>/
│               └── spec.md
└── config.yaml

Two directories are key:

  • openspec/specs/: The main specification library for the project's current behavior; the requirements-level Source of Truth.
  • openspec/changes/: Active changes, each in its own folder containing a proposal, design, tasks, and specification deltas.

This expresses OpenSpec's basic position:

How the system currently works belongs in specs/; how this change will modify it belongs in changes/.

The separation looks simple, but is crucial for AI collaboration. It distinguishes the system's current state from the current change's intent, so the model need not guess project facts from an ever-longer conversation.

3. How Does OpenSpec Differ from Ordinary Documentation?

Many people first see OpenSpec and wonder whether it simply adds a few Markdown files to a project.

If that were all, a dedicated tool would be unnecessary. Its real value is turning documentation into an executable control plane for AI collaboration.

Common problems with ordinary documentation:

  • Nobody reads it after it is written.
  • Nobody updates it when the design changes.
  • It becomes historical baggage once it diverges from the code.
  • The AI does not know which document to read.
  • Collaborators lack a unified entry point.

OpenSpec embeds documentation into the workflow:

  • /opsx:propose first creates the change proposal and supporting artifacts.
  • /opsx:apply follows tasks.md and checks off progress.
  • /opsx:sync synchronizes delta specifications into the main specifications.
  • /opsx:archive archives the completed change while retaining historical context.

Documentation becomes the input, process, and acceptance criteria for AI work, rather than a side product.

In one sentence:

Ordinary documentation records what we once considered; OpenSpec governs how this change should be understood, implemented, and recorded.

4. Core Concepts: What Does OpenSpec Manage?

To understand OpenSpec, start with four objects: Spec, Change, Artifact, and Delta Spec.

1. Spec: The Source of Truth for Current System Behavior

openspec/specs/ contains specifications describing the behavior the system should currently provide. They are neither implementation plans nor explanations of code structure.

Good specifications focus on externally observable behavior:

  • What does the user do?
  • What should the system return?
  • How should exceptional cases be handled?
  • What are the security, compatibility, performance, and permission requirements?
  • Which behaviors can tests verify?

Avoid writing:

在 UserService.ts 里新增 createUserWithProfile 方法。

Prefer writing:

### Requirement: 用户注册

系统 SHALL 在用户提交合法邮箱和密码后创建账号，并返回登录态。

#### Scenario: 合法注册
- GIVEN 用户输入未注册邮箱和符合规则的密码
- WHEN 用户提交注册表单
- THEN 系统创建账号
- AND 用户进入已登录状态

A Spec governs how the system should behave, not how the programmer intends to write it.

2. Change: An Independent Workspace for One Change

openspec/changes/<change-name>/ is the workspace for a change.

A change typically contains:

  • proposal.md: Why, what, and scope.
  • specs/: Incremental modifications to the main specifications.
  • design.md: Technical approach and key decisions.
  • tasks.md: Implementation task checklist.
  • .openspec.yaml: Optional change metadata.

This resembles a Git branch, except it manages requirements and design differences rather than code differences.

A code branch answers:

What changed in the code?

An OpenSpec change answers:

Why change it, how do we plan to change it, and how should the system behave afterward?

3. Artifact: Turn Vague Ideas into Actionable Outputs

Artifacts are work products within a change.

The default spec-driven process is roughly:

proposal -> specs -> design -> tasks -> implement

The purpose is not ceremony, but breaking a vague requirement into questions at different levels:

  • proposal.md answers why and where the boundaries are.
  • specs/ answers how system behavior changes.
  • design.md answers how to implement it technically.
  • tasks.md answers the order of execution.

When all four questions are crammed into one prompt, the model easily mixes them together. OpenSpec separates them so AI can receive, update, and execute them more reliably.

4. Delta Spec: Describe Only This Change

Delta Spec is a particularly important OpenSpec design.

Instead of rewriting the full specification every time, describe the increment:

  • ADDED Requirements: What behavior is added.
  • MODIFIED Requirements: What existing behavior is modified.
  • REMOVED Requirements: What behavior is removed.

This suits existing projects particularly well. Most real engineering changes a small part of an existing system rather than building a new system from scratch.

The problem with full documents is that readers must perform the diff in their heads.

A Delta Spec tells them directly what the diff is.

5. The OPSX Workflow: From /opsx:propose to /opsx:archive

As of May 22, 2026, OpenSpec's official documentation recommends the new OPSX workflow. The default core profile includes:

  • /opsx:propose
  • /opsx:explore
  • /opsx:apply
  • /opsx:sync
  • /opsx:archive

Enabling the expanded workflow also provides:

  • /opsx:new
  • /opsx:continue
  • /opsx:ff
  • /opsx:verify
  • /opsx:bulk-archive
  • /opsx:onboard

For most teams, mastering the default path is enough to start:

/opsx:propose -> /opsx:apply -> /opsx:sync -> /opsx:archive

1. /opsx:explore: Explore Before the Idea Is Mature

Do not rush to create a formal change while requirements remain vague.

For example:

/opsx:explore 我想给订单列表加一个批量导出能力，但还不确定要导出哪些字段，也不确定权限怎么卡。

At this stage, have the AI:

  • Read existing code and specifications.
  • Clarify business boundaries.
  • Identify potentially affected modules.
  • Compare implementation approaches.
  • Turn a vague idea into a requirement ready for a proposal.

Exploration is not about chatting longer; it prevents the model from changing code before the problem is thought through.

2. /opsx:propose: Formally Create a Change

Once the goal is reasonably clear, create a change:

/opsx:propose 为订单列表添加批量导出 CSV 能力

Based on project context, the AI creates a directory resembling:

openspec/changes/export-orders-csv/
├── proposal.md
├── design.md
├── tasks.md
└── specs/
    └── orders/
        └── spec.md

Review three things carefully here:

  • Is the requirements intent correct?
  • Is the scope too broad?
  • Are non-goals explicit?

Without firm boundaries here, faster implementation only takes you further off course.

3. /opsx:apply: Implement from the Task Checklist

Move to implementation after confirming the proposal:

/opsx:apply export-orders-csv

The AI reads the change's artifacts and follows tasks.md. Each completed item is checked off:

## 1. Export API
- [x] 1.1 增加订单导出接口
- [x] 1.2 校验导出权限
- [ ] 1.3 增加导出字段映射

The key is not having AI automatically finish everything, but keeping each step on a reviewed task track.

If implementation reveals a flawed design, do not push blindly ahead. Update design.md or specs/ first, then continue with /opsx:apply.

4. /opsx:sync: Synchronize Delta Specifications into the Main Specifications

OpenSpec's main specifications live in openspec/specs/, while change-specific deltas live in openspec/changes/<name>/specs/.

To merge a delta spec back into the main specifications, run:

/opsx:sync export-orders-csv

This keeps the source of truth for current system behavior up to date with the change.

Not every team must run sync manually, since archive often prompts for or handles synchronization. Still, this step matters: OpenSpec's full cycle ends not when the code is written, but when the main specifications also reflect the resulting system behavior.

5. /opsx:archive: Archive After Completion

Once the feature is complete and validation passes:

/opsx:archive export-orders-csv

OpenSpec moves the change to the archive directory, for example:

openspec/changes/archive/2026-05-22-export-orders-csv/

Archiving preserves decision history; it is not garbage collection.

Three months later, if you wonder why an order export omitted the cost-price field, the best reference is the original proposal, design, delta spec, and tasks, rather than scattered PR discussion.

6. Where OpenSpec Is Most Useful

Not every change needs OpenSpec. It best suits work whose boundaries are easily lost if managed only through chat.

1. New Features

New features often involve scope, user behavior, interface contracts, error cases, and acceptance tests. Asking AI to code immediately can skip requirements clarification.

OpenSpec first turns the feature into:

  • Intent
  • Scope
  • Requirements
  • Scenarios
  • Design
  • Tasks

Then implementation begins.

2. Modifying Existing Behavior

Changing existing behavior needs specifications even more than adding features.

You must answer not only what is being added, but also:

  • Which old behavior changes?
  • Does the old behavior have compatibility requirements?
  • Which downstream dependencies are affected?
  • Should tests be modified or added?

Delta Spec's MODIFIED Requirements is well suited to expressing such changes.

3. Large Refactors

The biggest refactoring risk is accidentally changing external behavior along with code structure.

OpenSpec fixes external behavior in specifications, telling AI what it must preserve during refactoring. The specification here defines behavioral boundaries, not implementation plans.

4. Cross-Team or Long-Running Tasks

When work spans people, days, or sessions, chat context deteriorates quickly.

The OpenSpec change folder becomes a handoff point:

  • Newcomers read the proposal to learn why.
  • Then the specs to learn how behavior changes.
  • Then the design to learn the technical approach.
  • Finally, the tasks to learn current progress.

This is far more reliable than searching chat history.

5. AI Agent Collaboration

OpenSpec is especially valuable for AI Agents. Their weakness is not inability to execute, but drifting over long sequences of actions.

proposal.md, design.md, tasks.md and delta specs provide external memory and intermediate goals.

This does not freeze the Agent's autonomy; it gives every step a task track it can revisit.

7. OpenSpec and the AI Agent Harness

If an AI coding assistant is a nondeterministic executor, OpenSpec resembles a Harness's source of truth and stage controls.

It provides a specification-level control plane, rather than a runtime sandbox or permission-approval system:

  • Use specs/ to fix current system behavior.
  • Use changes/ to isolate the current change's intent.
  • Use proposal.md to hold the goal and boundaries.
  • Use delta specs to constrain behavioral changes.
  • Use design.md to fix the technical approach.
  • Use tasks.md to govern execution cadence.
  • Use archive to close the delivery cycle and preserve historical traceability.

OpenSpec is not a complete Harness, but is a crucial layer in an AI coding Harness: Spec is Truth.

It addresses the most common context problem in AI collaboration:

Models may forget and chats may end, but the repository's specifications must not disappear.

8. Summary

Engineering in the AI coding era is about more than making models write more code for us.

The deeper question is how to make a model understand the goal before coding, preserve boundaries while coding, and add the change to the project's long-term memory afterward.

This is where OpenSpec's value lies.

It is neither a smarter Agent nor a heavier requirements system. It is a lightweight specification track that turns AI collaboration into an engineering cycle that can be reviewed, resumed, synchronized, and archived.

For individual developers, OpenSpec reduces context loss from forgetting why a change was made in the previous conversation.

For teams, it brings AI-assisted requirements, design, tasks, and historical decisions back into the code repository, allowing reviews to examine intent and behavioral changes before focusing only on code diffs.

For AI Agents, OpenSpec provides an external source of truth. Models can keep executing efficiently without relying solely on temporary chat memory.

More plainly, AI coding's challenge is shifting from generating code to reliably delivering changes. OpenSpec defines changes before they enter code, constrains them during implementation, and ensures the project remembers them afterward.

Appendix: OpenSpec Command Quick Reference

Installation and Initialization

npm install -g @fission-ai/openspec@latest
cd your-project
openspec init

Initialize for Specific Tools

openspec init --tools claude,cursor
openspec init --tools all
openspec init --tools none

Common Slash Commands

/opsx:explore <想法或问题>
/opsx:propose <要构建的能力>
/opsx:apply <change-name>
/opsx:sync <change-name>
/opsx:archive <change-name>

Common CLI Commands

openspec --version
openspec list
openspec show <change-name>
openspec validate <change-name> --strict
openspec status --change <change-name>
openspec list --specs
openspec view
openspec update

Expanded Workflow

openspec config profile
openspec update

After enabling, use these as needed:

/opsx:new
/opsx:continue
/opsx:ff
/opsx:verify
/opsx:bulk-archive
/opsx:onboard
