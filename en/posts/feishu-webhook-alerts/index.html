Still Watching Monitors Manually? A Complete Guide to Feishu Webhook Alerts

Eva·2026.04.30·7 min read

 

1. Why use a Feishu bot for alerts?

Team information is often scattered across systems: PR updates in repositories, service failures in monitoring platforms, builds in CI/CD pipelines, and operations in security audit logs. If someone must log into each system to check, information arrives much less promptly.

Through webhooks, a Feishu bot brings these separate event streams into one channel. It is easy to configure, requires no additional intermediary service, supports rich message cards, and fits naturally into team messaging. Once one person sets up the webhook, everyone in the group can receive updates in real time.

2. How webhooks work: One URL connects your systems

A custom Feishu bot is essentially an HTTP POST endpoint. Add a custom bot to a Feishu group, obtain its webhook address, and have any system capable of HTTP requests send messages there. JSON message bodies support plain text, rich text, cards, and other formats.

Any system that can call an external URL when an event happens can therefore connect to a Feishu bot. GitLab, Prometheus, Jenkins, Nacos, WAFs, and even your own scripts can produce messages.

3. Six practical scenarios

Scenario 1: GitLab collaboration updates

This is one of the most common integrations. Engineering teams produce many code changes daily, including merge request creation, approval, and merging, as well as code comments and triggered branch-protection rules.

Problems it solves: Prevent PRs from sitting unreviewed for hours and make reviews more transparent. When a PR merges into the main branch, testing and release staff can know immediately.

Configuration approach: In a GitLab project's Settings > Webhooks, enter the Feishu bot's webhook address and enable Merge Request events and Comment events. GitLab automatically sends event payloads. A simple relay, such as Nginx Lua, a Cloudflare Worker, or a lightweight custom service, can transform GitLab payloads into Feishu cards showing the PR title, author, changed-file count, and other key details.

Scenario 2: CI/CD pipeline results

Modern development depends heavily on automated pipelines, but build failures and deployment problems cannot wait until tomorrow's stand-up.

Problems it solves: Notify the responsible person immediately of build failures, announce version information after production deployment, and alert when nightly builds hang for too long.

Configuration approach: Jenkins can call the Feishu webhook directly through a Pipeline script's httpRequest step. GitLab CI can use after_script in .gitlab-ci.yml to send success or failure messages according to CI_JOB_STATUS. GitHub Actions can use community actions. Use green cards for success and red for failure, with build-log links for quick investigation.

Scenario 3: Production service alerts

When API latency spikes, error rates surge, disks fill up, or pods repeatedly restart, faster awareness means faster damage control.

Problems it solves: Deliver alerts from Prometheus, Zabbix, Nightingale, cloud monitoring, and similar platforms to the on-call group promptly, reducing mean time to repair (MTTR).

Configuration approach: With Prometheus Alertmanager, configure a webhook receiver pointing to your relay and map alert labels and annotations into Feishu messages. Classify severity: P0 alerts mention all on-call staff, P1 sends messages without mentions, and P2 aggregates low-priority alerts for scheduled delivery. Deduplicate and silence flapping alerts in the relay to avoid flooding the group with an alert storm.

Scenario 4: Security and audit events

Security events are often subtle and highly sensitive, requiring immediate awareness by security leads or managers.

Problems it solves: Detect unusual logins, such as from unexpected locations or outside working hours; sensitive permission changes, such as granting administrator roles or making repositories public; deletion of critical resources, such as production configurations; and high-frequency attacks blocked by a WAF.

Configuration approach: Most cloud ActionTrail and audit services support delivery to HTTP endpoints. Use a serverless function such as Alibaba Cloud Function Compute or AWS Lambda as a relay, filter event types, and forward to Feishu. For particularly sensitive events, send direct messages to designated people through the bot API as well as the group to ensure the responsible person sees them.

Scenario 5: Business-metric changes

Changes in business data deserve attention alongside technical metrics.

Problems it solves: Warn promptly when critical metrics fall unexpectedly, such as order volume or payment success rate; announce milestones, such as daily active users exceeding a threshold; and deliver completed reports proactively to the group.

Configuration approach: If your data platform supports scheduled queries and webhooks, such as Apache DolphinScheduler, Airflow, or a custom scheduler, decide whether to send a Feishu message from query results at task completion. For example, an Airflow PythonOperator can use requests to post a card summarizing yesterday's GMV. You can also point a BI system's data-alert feature to the bot to send automatic report-anomaly notifications.

Scenario 6: Closing the operations-feedback loop

Beyond receiving alerts, a bot can report the results of operational actions.

Problems it solves: After you ask the bot in a Feishu group to restart a service or scale a cluster, it posts the result back so everyone can see that the action took effect.

Configuration approach: This requires both receiving commands and sending messages, so a webhook alone is insufficient. Build a lightweight bot service and register Feishu event subscriptions. When someone mentions the bot with a command, it parses and executes the action, then returns the result through a webhook or OpenAPI. This is particularly useful in on-call groups: actions leave a record and results remain visible.

4. Making alerts more effective

First, control noise. Not every event belongs in a group chat; excessive notifications teach people to ignore them. Define clear severity levels, send immediate messages only for events requiring prompt action, and put summaries in daily reports or scheduled updates.

Second, include context. A good alert says what happened, what is affected, whom to contact, and where to investigate. Add direct links to cards whenever possible to reduce navigation effort.

Third, account for timezones and on-call schedules. For distributed or rotating teams, combine the Feishu bot API with the roster so alerts mention only current on-call staff rather than disturbing everyone at night.

Fourth, plan fallback channels. Feishu is an external service and may experience latency or temporary outages. Keep SMS or phone calls as backups for the highest-priority alerts.

5. Conclusion

Feishu webhook bots are not universal solutions, but they provide a lightweight, efficient hub for team information. From repositories and monitoring to security audits and business data, they offer low-cost integration whenever a group needs to learn about something promptly.

The real value lies beyond technical configuration: event severity, message design, and team response mechanisms matter most. Establish clear collaboration rules, then automate them to turn alerts from interruptions into assistance.
