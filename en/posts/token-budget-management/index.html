Token Budget Management: Dynamic Reserves and Layered Compression

Eva·2026.06.02·14 min read

 

Your LLM has a 200K “credit limit”—but you may actually be able to spend less than half of it.

How Much of Your 200K Window Can You Really Use?

Open a model vendor's documentation and the “200K context window” stands out. The number is reassuring: just keep filling it.

But engineers quickly discover the problem. Let us break it down item by item:

模型硬上限（200K）
├── 系统提示词（System Prompt）          ∼2K–8K
├── 工具/函数定义（Tool Definitions）     ∼5K–134K
├── 安全/隐藏前缀（Hidden Preamble）      ∼数百 token
├── 多模态占位符展开                      ∼不定
├── 对话历史（Conversation History）      ∼动态增长
├── 当前用户输入                          ∼可变
├── 为模型回复预留（Reserve）              ∼4K–20K
└── 思考 token（Thinking/Reasoning）       ∼不可见但计入
─────────────────────────────────────────────
    剩余可用预算                           ？？？

Each item deserves a closer look:

System prompt—the role and behavioral rules you set for the model. A moderately complex Agent system prompt easily exceeds 2,000 tokens. Add safety policies and output-format constraints, and 8,000 tokens is common.

Tool definitions—the easily overlooked hidden heavyweight. Every tool is a JSON Schema: function name, parameters, type constraints, and descriptions all count toward context. Claude Code has 30+ tools; tool definitions alone can consume 55K–134K token. Research suggests that on Claude Opus, the tool-definition portion of each call costs 0.67. Money is spent before your Agent even starts working.

Conversation history—every user message, assistant response, tool call, and tool result accumulates. Twenty turns can easily exceed 50,000 tokens. Every new message also sends the entire history to the model again.

Reserve—without a reserve, replies are hard-truncated: incomplete JSON, half a sentence, unfinished code. You must also avoid the “compression paradox”: compression needs room to write a summary into context, but no room remains even for that summary.

Thinking tokens—reasoning models such as o1 and Claude Opus “think” internally before answering.

Added together, for a real running Agent, a 200K window may offer only 30K–80K of usable budget—less than half.

Three Concepts You Must Understand

Token budget management is more than counting what remains. It needs a simple but precise conceptual framework.

2.1 Budget: How Much This Turn Can Spend

The budget is not 200K; it is what remains after all fixed overhead is subtracted from 200K.

Effective Budget = Context Window − System Overhead − History − Reserve

Treat the budget as an active constraint, not a passive remaining balance. As used tokens approach it, trigger intervention: compression, truncation, or rejection.

2.2 Reserve: Leave Room for the Model's Reply

Imagine writing a long email that hits the character limit at “Tomorrow at three, let us meet at—” and the Send button turns gray. For an LLM, this means:

  • Truncated JSON that fails to parse
  • Incomplete tool-call arguments that fail to execute
  • An abrupt reply ending halfway through a sentence

You must therefore set aside an untouchable portion of the spendable budget. The problem is that a fixed reserve, such as always using 4,096, is too inflexible. A yes/no answer may need 10 tokens; a code refactor may generate 8,000.

A better approach is a dynamic reserve:

reserve = base_reserve + 任务复杂度加成
──────────────────────────────────
是/否判断        → base_reserve × 0.1
简短解释         → base_reserve × 0.3
代码建议         → base_reserve × 1.0（基准）
代码重构/生成    → base_reserve × 2.0
长文档生成       → base_reserve × 3.0

This is exactly like operating-system memory allocation: a process requests memory, and the kernel approves or denies it based on system state.

2.3 Threshold: Act Before Space Runs Out

Claude Code's approach illustrates this best:

UtilizationBehavior
∼85%Show a warning to the user
∼90%Automatically trigger compression
∼95%Block new requests
∼98%The last line of defense for manual compression

The key idea:Warn at 85%; act at 90%. Waiting until 98% may leave too little space even for compression.

This is not a binary enough/not-enough decision, but a gradual response chain that escalates as pressure rises. Lightweight cleanup usually suffices; heavyweight compression is reserved for real emergencies.

Three Practical Problems

3.1 “I Just Divided Character Count by Four”—Your Estimate Will Be Wrong

Different models use different tokenizers. Counts for the same sentence can vary by 10–30%:

Texttiktoken (OpenAI)AnthropicDifference
"How many tokens does this sentence contain?"8 token9 token12.5%

That is just simple English. Chinese is more extreme: one character may require 2–3 tokens. A 2,000-character prompt may be 5,000–6,000 tokens. Dividing character count by four can miss by more than 20%.

A subtler problem is “tokenizer drift”: local counts often differ from the API server's billed count by 5–15%. The sources are locally invisible: JSON structures for role markers, formatted tool schemas inside the request envelope, tokenized multimodal placeholders, and reasoning-model thinking tokens.

3.2 Tool-Result Spikes: Blow the Budget in an Instant

Everything runs smoothly at 60% utilization. Then a search tool returns 50,000 tokens of web content, instantly pushing utilization to 92%.

This is a spike: one result far exceeds expectations and changes the budget state in a single step.

Responses:

Dynamic truncation thresholds: Thresholds should vary with current utilization rather than remain constant.

利用率 < 50% → 慷慨，允许大结果
利用率 50–80% → 保守，截断一半
利用率 > 80% → 告急，只留关键信息

After-the-fact remediation: Claude Code first writes the full result, then snips it afterward. The message chain remains intact—tool calls still pair with tool results—but content is replaced with [Old tool result content cleared]. This reclaims space without damaging semantic structure.

3.3 A Fixed Reserve Is Not Enough

You set reserve = 4096, but a refactoring Agent needs to generate 8,000 tokens of code. The model is capped at 4,096, and the code is cut off halfway through.

A more advanced approach is to let the Agent declare its own reserve requirement through a dedicated tool call specifying required_reserve_tokens: 8000, allowing the system to adjust the current turn's reserve.

Compression: The Question Is How, Not Whether

4.1 Layers: Try Free Options Before Spending Money

When the budget is tight, there are only three choices: stop, truncate, or compress. Compression itself costs money, information, and user waiting time through additional API calls.

Good engineering practice is to move from cheap to expensive, escalating only when needed: 

层级    策略          花费      回收能力    信息损失
─────────────────────────────────────────────────
L1     Snip/Pruning   零 LLM    中等       低（只清内容，保结构）
L2     微压缩         零 LLM    中等       低（基于时间衰减）
L3     主动重组       中等 LLM  高         中
L4     LLM 全文摘要   高 LLM    很高       高

L1 is the most underrated strategy. File contents searched ten turns ago, pages already read, and completed command output have already served their purpose. Clearing them requires no LLM call, preserves message structure, and can reclaim substantial space.

4.2 Circuit Breakers: When Compression Itself Fails

Worse still, compression fails because its prompt is too long, retries, and fails again. Before adding a circuit breaker, Claude Code observed 1,279 sessions with more than 50 consecutive compression failures, wasting about 250,000 API calls per day.

The circuit-breaker logic is simple:Three consecutive failures → open the circuit → skip further compression. One success resets it.

4.3 Compression Is Not the End

Critical context must be reinjected afterward. Claude Code's rules:

压缩后注入上限：
├── 总预算:    50,000 token
├── 单文件最多:  5,000 token
├── 最多恢复:    5 个文件
└── Skills:    25,000 token 总预算

There is also a truePostCompactTokenCount function specifically detecting immediate recompression right after compression.

Larger Windows Make the Problem Worse

A common illusion is that growing context windows from 128K to 200K to 1M will naturally solve the problem.

The opposite is true: larger windows make budget management more important.

5.1 The Cost of Waste Scales Linearly

With a fixed per-token price, filling 200K costs 6.25 times as much as filling 32K. Quality gains are far from linear. The Chroma team found that after inserting about 4,000 tokens—20 retrieved documents—accuracy dropped from 70–75% to 55–60%.Filling more space can make results worse.

5.2 More Context Can Make the Model See Less Clearly

Stanford research found a U-shaped performance curve: models attend strongly to the beginning and end (85–95%) and less to the middle (76–82%). GPT-3.5-Turbo's accuracy on documents buried in the middle fell to 56.1%—worse than giving it nothing.

The root cause is long-range decay in RoPE (Rotary Position Embedding): more distant tokens receive less attention. At 100K tokens, the model must manage roughly ten billion pairwise relationships, severely diluting attention.

5.3 The Cost Curve Is Not Linear

                         成本 ($) 持续线性增长 ↗
                        /
                      /
────────────────────
                      \
                        \  性能 / 准确率先平后降 ↘
                          \

Every additional 1,000 tokens raises cost linearly. Performance first plateaus, indicating redundancy, then declines as information overload starts harming judgment.

That is the essence of budget management: you are managing value for money, not just space.

6.2 How Do They Count Tokens?

This is the two projects' most fundamental disagreement.

Claude Code—a dual-track approach:

  • Approximate estimates on hot paths: 4 chars/token, 2 chars/token for JSON, and a fixed 2,000 for images
  • An exact API at key decision points (beta.messages.countTokens)
  • But this precision works only in Anthropic's ecosystem; OpenAI and Gemini compatibility layers fall back to estimates

Hermes Agent—estimation only:

  • 4 chars/token throughout
  • A fixed 1,500–1,600 for images
  • But it also counts tool schemas, an often-overlooked overhead that can add 20–30K for tool-heavy Agents

Why Does Hermes Avoid Exact Counting? Supporting over a dozen providers means supporting a different exact-counting API for each. Maintenance is too expensive; lowering the trigger threshold to 50% rather than 90% absorbs estimation error instead.

This is the fundamental engineering choice:

  • Spend effort to eliminate error → exact counts and thresholds near the physical limit (90%)
  • Spend effort to tolerate error → estimates with sufficient safety margin (50%)

6.3 When Does Compression Trigger?

Claude Code—four progressive levels:

200K 窗口下：
∼167K → 警告闪烁（WARNING_BUFFER = 20K）
∼180K → 自动压缩（200K - 20K 预留 - 13K 额外缓冲）
∼197K → 阻塞新请求

Anti-thrashing mechanism:A circuit breaker stops after three consecutive failures.

Hermes Agent—a single 50% threshold:

threshold_tokens = max(context_length × 0.50, 64_000)
tail_token_budget = threshold_tokens × 0.20  # 保留最近 20%

Anti-thrashing mechanism:Suppress compression after two consecutive attempts save less than 10%.

Why Does Hermes Use 50% While Claude Code Uses 90%? Again, the difference is counting: approximation needs a 30–40% error buffer.

6.4 How Are Compression Strategies Layered?

Claude Code 三层：                  Hermes 两层：
┌─ MicroCompact ── 零 LLM          ┌─ Pruning ── 零 LLM
│  清除旧工具输出                    │  去重+单行摘要+截断
├─ Session Memory ── 零 LLM        │
│  用预提取记忆做摘要                └─ LLM 摘要 ── 辅助模型
└─ API 摘要 ── LLM 全文总结           便宜模型做摘要，降级链兜底

Both go from cheap to expensive. Differences:

  • Claude Code has a Session Memory layer, relying on an internal Anthropic experimental feature
  • Hermes uses an auxiliary model: a cheap model such as Gemini Flash summarizes sessions from an expensive main model, saving over 90%

6.5 Details Worth Highlighting

Prompt Cache Sharing: During compression, Claude Code uses forkedAgent to reuse the main thread's cached prefix, raising cache hits from 2% to nearly 100%. Hermes cannot do this because caching behavior differs across providers. This is a classic **optimization exclusive to a closed ecosystem**.

Slot Optimization: Claude Code lowers the default max_tokens from 32K to 8K. The API server reserves inference slots according to max_tokens, while actual p99 output is just 4,911 tokens. At 8K, fewer than 1% of requests are truncated, and those automatically receive a 64K retry. Counterintuitive, but effective.

Session Rotation: After successful compression, Hermes rotates session_id, marking the old session with end_reason=compression and linking the new session as its child. SQLite atomic locks prevent concurrent compression. Claude Code does not need this for a single Agent. Concurrent multi-Agent systems should adopt it.

Trajectory Compressor: Hermes also has a 1,509-line offline compressor that compresses completed Agent histories to 15,250 tokens for training data. This reflects a research organization's distinctive perspective:An Agent's execution history is itself a trainable asset.

Seven Proven Engineering Patterns

Pattern 1: Layer Compression, Free Before Paid

Whether Claude Code's “MicroCompact → SM → API summary” or Hermes's “Pruning → LLM summary,” the principle is to try zero-cost methods first. Clearing old tool outputs usually suffices, with no LLM call needed.

Pattern 2: Align Compression Boundaries with Message Semantics

tool_use and tool_result must remain paired; thinking blocks must not be split, and the most recent user message must remain. Compression follows message semantics, not arbitrary token cutoffs. Both projects emphasize this.

Pattern 3: Preserve the Beginning and End; Compress the Middle

Both LLM attention distribution—primacy and recency effects—and task structure—initial goals and recent context—require this. The amount retained is adjustable, but its position must be at the beginning and end.

Pattern 4: Anti-Thrashing Is Mandatory

Use a circuit breaker or a savings-threshold check. The point is to avoid repeatedly paying for ineffective compression. Claude Code's data: 250,000 wasted calls per day before its circuit breaker.

Pattern 5: Choose Exact or Approximate; Do Not Sit on the Fence

  • Single provider → exact counting, with thresholds near the physical limit
  • Multiple providers → approximate estimates, with sufficient buffer

Demanding both precision and universality is an engineering disaster.

Pattern 6: Separate the Summarization Model

Hermes summarizes Claude Opus or GPT-5 sessions with Gemini Flash or Haiku, potentially saving over 90%.

Pattern 7: Explicit Reinjection After Compression

Compression is more than checking remaining space. Consider that important context must be explicitly restored: files, skills, configuration, and discovered MCP tools.
