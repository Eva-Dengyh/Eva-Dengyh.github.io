I Turned Common AI Video Model Integration Pitfalls into an Open-Source Project

Eva·2026.09.15·5 min read

 

I recently put together a small project called ModelCap.

Its purpose is straightforward: organize common AI video models' capabilities, parameter limits, input requirements, error codes, and pricing information into machine-readable JSON, then provide developers with a Node.js SDK and CLI to validate parameters before calling a model.

Project repository

https://github.com/Eva-Dengyh/ModelCap

Version v0.1.0 is out now. Installing from the GitHub tag is recommended for the moment.

npm install github:Eva-Dengyh/ModelCap#v0.1.0

When integrating video-generation models, many problems arise before generation even begins.

Even for image-to-video, models differ in required image dimensions, formats, aspect ratios, and file sizes. For 5-, 10-, or 30-second videos, they impose different duration, resolution, and aspect-ratio limits. Some accept reference images, some reference videos, and others audio. Restrictions may appear in parameter tables, footnotes, or only hints inside error-code examples.

Once a product integrates multiple models, these differences quickly become scattered conditional checks. Frontend forms must know which parameters to display; backends must know which requests to reject early; routing must know whether a model supports a requirement; and failures require translating provider error codes into understandable messages.

That is the work ModelCap currently addresses.

It includes 50 AI video model versions, each represented by a JSON entry recording supported tasks and inputs, parameter ranges, input-asset limits, known error classifications, and pricing sources. JSON is the source of truth; Markdown and files in dist are generated outputs.

The SDK currently has four main functions.

getModel retrieves one model.

listModels filters models by task, input, and capability.

validateRequest checks a request against recorded hard constraints.

normalizeError maps some provider error codes into more stable categories.

Here is a simple example.

import { getModel, listModels, validateRequest } from 'modelcap-catalog'

const model = getModel('wan-3.0')

const imageModels = listModels({
  task: 'generate',
  input: 'reference_image',
})

const result = validateRequest('wan-3.0', {
  task: 'generate',
  parameters: {
    duration: 5,
    resolution: '1080p',
    aspect_ratio: '16:9',
  },
})

console.log(model.model_id)
console.log(imageModels.length)
console.log(result.valid)

For quick command-line lookups, there is also a CLI.

node node_modules/modelcap-catalog/bin/modelcap.mjs list --task generate --input reference_image
node node_modules/modelcap-catalog/bin/modelcap.mjs get wan-3.0

One choice I care about is making the project deliberately conservative.

It rejects only hard constraints explicitly recorded in structured data. Where official documentation is unclear, it tries to warn instead of inventing a rule. Prose notes are not interpreted directly as executable rules either. This sacrifices some automation, but makes it more suitable for preflight checks in real products. It should tell you the information is incomplete rather than imagine a judgment on the provider's behalf.

This information may not be glamorous, but it is useful in development.

The current v0.1.0 includes most essentials for an open-source project: a README, Chinese README, API and CLI documentation, versioning policy, release notes, CHANGELOG, contribution guide, security notes, data license, and issue templates. CI runs tests, type checks, example checks, model JSON and schema validation, freshness checks, build verification, and npm package preflight checks. Before release, npm run release:check also checks that versions match the CHANGELOG and that the CLI and release documentation are included in the package.

Several groups may find it useful now.

If you are building an AI video product and need forms to know supported parameters upfront, it can replace some hard-coded logic.

If you are building model routing and need to select models supporting image-to-video, video editing, or audio input, it provides a structured catalog directly.

If you are wrapping provider SDKs and need stable business errors from provider codes, it offers a starting point.

If you simply want to compare video-model capabilities, you can read the JSON or Markdown directly.

It is not yet a complete model gateway. It does not call provider APIs, manage keys, run queues, process callbacks, calculate bills, or evaluate generation quality. It is closer to an information and validation layer before integration.

Three areas are next.

First, expand structured parameter coverage. The catalog is usable, but providers vary in the detail of their public documentation. I will keep filling out duration, resolution, input assets, audio, and error-code fields.

Second, produce a data-completeness report for each model so users can immediately see which fields have official sources and where information is missing, making integration decisions clearer.

Third, improve installation and documentation. I plan smoother release options and may organize the API, CLI, and model catalog into easier-to-browse documentation pages.

If you are integrating AI video models, or have struggled with parameter differences across providers' documentation, give it a try.

npm install github:Eva-Dengyh/ModelCap#v0.1.0

The project is still young. Issues are welcome, as are model entries based on official documentation. ModelCap will aim to record only traceable facts and keep uncertainties visible.
