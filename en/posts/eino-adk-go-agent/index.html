Eino ADK: An Agent Runtime for Go

Eva·2026.07.19·9 min read

 

When building applications that can call tools, cancel generation, and expand to multiple Agents, calling an LLM API is not enough. You also need an Agent runtime to handle the ReAct loop, event streams, middleware, and collaboration orchestration.

Eino ADK (Agent Development Kit) is precisely that layer.

It is the Go-oriented Agent / Multi-Agent development kit in the open-source Eino ecosystem from ByteDance's CloudWeGo.

In one sentence:

It is not “another LLM SDK,” but an Agent runtime: who handles reasoning, who performs actions, how events stream out, where middleware attaches, and how multiple Agents collaborate.

What Eino and ADK Each Handle

Eino is a Go-first framework for developing LLM applications, covering infrastructure such as model adapters, component orchestration (Graph / Chain), tools, and callbacks.

ADK is Eino's dedicated Agent layer. Its design draws on abstractions for Agents and collaboration found in frameworks such as Google ADK. Core capabilities include:

  • A unified Agent interface for units that can run a turn and emit events
  • Event-driven output instead of returning one large string at once
  • Composable collaboration primitives: sequential, parallel, loop, Supervisor, Plan-Execute, and more
  • Runner as the entry point for a single execution, with runtime capabilities including streaming, cancellation, and interruption

The division of responsibilities is:

Eino handles components and the orchestration foundation; ADK handles how autonomous decision-making Agents run.

The following official diagram shows that Eino is not an isolated runtime library, but an ecosystem spanning AI application design through operations.

Read the diagram along three lines:

  1. 1. The three central layers form the main development stack: the red bottom layer is Eino (core types, component definitions, compose / callback / streaming, key Flows, and ADK); the purple middle layer is Eino-Ext (official component implementations, callbacks, third-party integrations); the yellow top layer is User Code (custom components, callbacks, Lambda).
  2. 2. The green Eino Examples on the left aligns with “Research & Design”: start from examples rather than guessing APIs in an empty project.
  3. 3. Devops Tooling at the top (visual orchestration, code generation, visual debugging, Telemetry) and Integrated 3rd-party platforms on the right (Tracing / Hosting / Evaluation) cover debugging and deployment operations respectively.

For application developers, most daily work happens in the middle column:Build on Eino's abstractions, use ready-made Eino-Ext implementations, and add your own logic in User Code. ADK is embedded in the Eino core at the bottom.

A more detailed official diagram shows the framework's internal layers:



On the left is Eino itself. From bottom to top, roughly:

  • Schema / Callbacks: Message, Document, StreamReader / StreamWriter, ToolInfo, plus callback Handler / Inject / Trigger
  • Components: Component abstractions—type definitions, inputs and outputs, Call Option, streaming paradigms, Callback Info
  • Compose: Orchestration engines (pregel / dag) and APIs (Graph / Chain / Workflow), containing Flows such as ReAct and building blocks including node, edge, branch, stream, interrupt & checkpoint
  • ADK (top layer): Higher-level abstractions for Agents—ChatModelAgent, WorkflowAgent, Agent Tool / Transfer / Middleware, Interrupt Resume; middleware such as FileSystem and Context Engineer; prebuilt forms such as DeepAgents, Supervisor, and PlanExecute

On the right is Eino-Ext: Devops Tooling, various Component Implementations (Chat Model, Retriever, Tool, Prompt, etc.), and Callback Handlers such as Tracing / Metrics. The arrows make the relationship clear:Ext implements the abstractions on the left instead of introducing a separate protocol.

Why Not Call the Model Directly?

When calling ChatModel directly, the application usually implements the ReAct loop (Reason → Act → Observe) itself:

拼 messages → 调模型 → 有 tool_calls 就执行工具 → 再调模型 → …

ADK packages this loop into framework primitives. Compare:

  • Direct model calls: Loop logic lives in application code; streaming and cancellation require manual integration; context compression / Skills / retries can intrude into the main flow; expanding to multiple Agents requires broader changes.
  • Using ADK: ChatModelAgent has a built-in ReAct Loop; Runner + context provide unified streaming and cancellation; Middleware attaches to the loop lifecycle; collaborative Agents / DeepAgents can be added incrementally.

Architecturally, making the Agent the execution unit instead of a bare model call makes it easier to inject Tools and attach Skill Middleware later, without simultaneously redesigning the chat UI, message tables, and model catalog.

The layered diagram also clarifies this: Compose already has a ReAct Flow; ADK builds on it with ready-to-use Agent primitives, so application developers need not rewrite the entire loop in User Code.

Four Core Concepts

The ADK layer in the architecture diagram boils down to the following parts.

1. ChatModelAgent: The Smallest Autonomous Decision-Making Unit

Its structure can be summarized as:

ChatModel（推理）
  + Tools（行动）
  + Instruction（约束）
  + ReAct Loop（决定何时推理、何时调用工具）

Suitable for scenarios with open-ended problem boundaries where the model needs to decide the next action.

In the official division of responsibilities, deterministic orchestration belongs more naturally to Graph / Chain / Workflow in Compose; autonomous decision-making belongs more naturally to ChatModelAgent in ADK.

2. Runner: The Entry Point for a Single Execution

Runner is the entry point for one Agent run. Typical usage: place ChatModelAgent in the configuration, then call Query / Run and consume the event stream.

It handles “this run”: whether to stream, how to emit events, and how to coordinate cancellation.

Session persistence is outside Runner's responsibilities; storing sessions and messages remains the application's job.

3. Middleware: Inject Behavior at Points in the Loop

This corresponds to ADK's Middlewares, such as FileSystem and Context Engineer, and Agent Middleware in the diagram.

Middleware preserves the ReAct “reason → act → observe” structure while injecting behavior at key points, such as:

  • Compress context before calling the model
  • Dynamically inject tools
  • Check tool-call permissions
  • Retry failures / switch to a fallback model
  • Skills: load skill instructions into the current conversation on demand

Skill capabilities can be implemented through skill middleware attached to ChatModelAgent, without creating another Agent protocol.

4. Collaboration and Prebuilt Forms

These correspond to Prebuilt and collaboration-related primitives in the diagram:

  • Workflow Agents: Deterministic flows such as Sequential / Parallel / Loop
  • Supervisor / Plan-Execute: Multi-Agent collaboration patterns
  • DeepAgents: Planning, file systems, sub-Agent delegation, and more
  • Agent Tool / Agent Transfer: Wrap an Agent as a tool, or transfer control between Agents
  • Interrupt / Resume / Checkpoint: Human-in-the-loop collaboration and checkpoint recovery

ADK addresses Agent system design, beyond merely wrapping chat completion.

Responsibility Boundaries in Practice

One common layering looks like this:

产品界面 / API
  → 业务服务（会话编排、鉴权、计费、附件）
  → 数据库（会话与消息的事实源）
  → Agent 运行时（Eino ChatModelAgent + Runner）
  → 模型网关

ADK handles “how this Agent turn executes”; it does not handle “where conversation facts are stored.”

In the lifecycle diagram, Eino / Eino-Ext / ADK fall under Development & Debugging; accounts, orders, billing, and pages remain part of User Code and business systems. In the layered diagram, concrete implementations such as Chat Model come from Eino-Ext; ADK consumes only the Components abstractions.

Pay attention to these boundaries in implementation:

  1. 1. Handlers do not call ChatModel directly; consistently go through Agent + Runner
  2. 2. Restore multi-turn context from the application database, then convert it into framework message structures; avoid using internal framework objects as a long-term storage protocol
  3. 3. Propagate cancellation signals through context so both the Agent and upstream model requests can stop
  4. 4. Separate streaming events from final persisted facts: the frontend consumes increments; the database is authoritative for persistence
  5. 5. Filter event types: ADK events may contain tool-related payloads; retain only assistant-visible output before writing the chat body

When It Fits—and When It Does Not

Good fits:

  • You need ReAct, Tools, Skills, or middleware extensions
  • The execution layer must be decoupled from session storage, authentication, and billing
  • Your stack is Go, and you want Eino's model adapters and component ecosystem
  • You need room to expand into multiple Agents or human-in-the-loop collaboration

Poor fits or lower priority:

  • Pure one-shot completion, with no tools or expected extensions → call ChatModel directly
  • Fully deterministic flow with no model deciding the next step → Graph / conventional orchestration is more suitable
  • Your main stack is not Go, or you already have a mature Agent framework → no need to change stacks just for ADK

Choose based on whether the boundaries fit, not on an abstract ranking of frameworks.
