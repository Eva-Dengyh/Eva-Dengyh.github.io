Debugging Missing Umami Events: User-Agent and Traffic Identity

Eva·2026.04.27·14 min read

 

Bug Description

While integrating Umami tracking into a desktop application, I encountered a production issue that is very easy to misdiagnose. Tracking requests appeared to leave the client successfully, and the server returned 200, yet the data never appeared in analytics. Events were missing, sessions were not created, or certain request paths consistently lost data. More confusingly, identical tracking logic persisted data through some call paths, while switching paths—or changing just one User-Agent fragment—immediately changed the outcome.

This deserves a dedicated write-up because it looks like an API problem but often is not. It looks like an unstable SDK, yet requests may already have been classified as low-trust traffic by the identity layer before reaching analytics. Without this diagnostic framework, troubleshooting can circle endlessly through request bodies, event names, site identifiers, the database, and frontend implementation without finding the actual cause.

Some background: Umami is a lightweight, open-source, privacy-focused web analytics system, often used instead of heavier commercial platforms. Integration is usually straightforward: pages or applications report pageviews and events at appropriate times, and the server receives them, attributes them, establishes sessions, and aggregates reports. Because it looks like “add a script and it works,” it is easy to blame tracking code and overlook the identity and traffic-filtering chain requests traverse before reaching the actual analytics logic.

The Essential Problem: The Request Did Not Fail; It Was Not Trusted

The most misleading part was that requests appeared to be sent successfully and the server returned 200, but the analytics system did not treat them as valid human visits.

In other words, this was neither a conventional network error nor invalid API parameter formatting, but a lower-level traffic identity problem.

From first principles, every tracking system ultimately does two things:

  1. 1. Receive a claim: The client says, “I visited a page / triggered an event.”
  2. 2. Decide whether the claim is credible: The server decides whether this is real user behavior or a script, bot, scanner, or forged request.

Engineers usually focus only on step one: Is the body correct? Is the site identifier correct? Did the API report an error? Modern analytics systems, gateways, and WAFs often put more weight on step two:Who you are matters more than what you say.

That was the essence of this issue.

Start with a Minimal Model: What Does a Tracking Request Validate?

At a minimum, a Umami report usually involves several signals:

  • Whether the request path is correct, such as the event ingestion endpoint
  • Whether the body matches the server schema
  • Whether the site identifier is valid
  • Whether Cookie / session context is recognizable
  • Whether request headers resemble a normal browser
  • Whether an upstream gateway or WAF classifies the request as high-risk traffic

It is easy to think of HTTP as a protocol where filling in all fields is enough. In production, it more closely resembles a claim system involving identity judgments.

You submit not just JSON, but a complete client profile:

  • User-Agent
  • Accept
  • Origin
  • Referer
  • TLS fingerprint
  • Header ordering characteristics
  • IP reputation
  • Cookie continuity
  • Request cadence

And User-Agent is often the first and cheapest filter: a readily available, low-cost signal that quickly indicates whether a request resembles a browser.

Therefore, if the UA triggers risk heuristics, even when the API continues to return 200, the analytics pipeline may silently downgrade, ignore, or discard the request, or fail to create a valid session.

This explains the particularly confusing symptoms:

  • Network level: no apparent error;
  • Application level: the API appears successful;
  • Data level: nothing is persisted, or key session identifiers are missing.

User-Agent Is an Identity Claim, Not a Notes Field

User-Agent is a standard HTTP request header, essentially an identity claim string.

It does not directly prove identity, but it affects the server's probabilistic judgment:

“Does this request look like it came from a real browser?”

This distinction is crucial.

The UA is neither a password nor a signature and provides no strong authentication. But it is an important input to risk systems' prior judgments. Its value lies not in absolute truth, but in fitting the normal distribution of real-world experience closely enough.

Why Are Standard Browser UAs More Readily Trusted?

Modern web infrastructure has built extensive empirical models around mainstream browsers.

A typical browser UA contains:

  • A Mozilla/5.0
  • Platform information, such as Macintosh, Windows NT 10.0
  • Rendering-engine information, such as AppleWebKit/537.36
  • A browser version, such as Chrome/132.0.xxx
  • Compatibility fields, such as Safari/537.36

These fields are not security mechanisms, but the internet's long evolution has established a stable distribution. Servers, CDNs, WAFs, and bot-detection libraries naturally place greater trust in frequently seen, statistically stable, mature client profiles.

Conversely, deviations—particularly inserted custom product names, abnormal version numbers, or suspicious placeholders—make requests statistically resemble automated traffic more closely.

Why Custom Shell Identifiers and All-Zero Placeholder Versions Trigger Blocking

This was the central difficulty. Superficially, there were just two extra fields, but to a risk system they represented two different categories of risk signals.

Custom Shell Identifiers: Unknown Fingerprints Raise Heuristic Risk

The problem is not necessarily that a library hardcodes the identifier into a blacklist, but that it disrupts the UA's natural shape.

Think of a UA as a sentence: a standard browser UA has stable grammar and a rich corpus of examples. Inserting a custom shell identifier resembles suddenly inserting an unfamiliar proper noun at an awkward position in otherwise normal English.

A WAF or bot detector may ask:

  • Is this product identifier common in mainstream browser families?
  • Is its position consistent with normal distributions?
  • Does it resemble an automation framework, test container, or private shell application?
  • Does it reduce the posterior probability of a real user's browser?

The issue is therefore not a syntax error, but a distribution anomaly.

The risk system usually does not claim certainty that you are a bot. Its more practical judgment is:

“You do not look typical or trustworthy enough as a browser, so I would rather lower my trust.”

Once trust falls below a threshold, the request may be:

  • Discarded outright;
  • Marked as bot traffic;
  • Excluded from session creation;
  • Given an apparently successful response without being persisted.

All-Zero Placeholder Versions: High-Risk Placeholders Trigger Blacklist-Style Rules

All-zero placeholder versions represent a different risk:a default-placeholder pattern.

0.0.0 almost never represents a properly released client version. It more often appears in:

  • Automation scripts with incorrectly injected version numbers
  • Default values in headless / test containers
  • Rudimentary scrapers or temporary debugging tools
  • Incompletely configured shell programs

From first principles, therefore, 0.0.0 is not merely sparse information; it is dangerous information.

Even with unconventional versioning, real released software rarely identifies itself persistently as 0.0.0. Many anti-scraping rules therefore treat it as a strong machine signal.

This explains why:

  • Custom shell identifiers resemble an unknown-device-fingerprint problem;
  • All-zero placeholder versions resemble a default-script-placeholder problem.

Both can lose data, but their mechanisms operate at different levels.

Why Does It Return 200 Without Persisting Data?

This is the most confusing point for many engineers first encountering risk-filtered data loss.

HTTP Success Does Not Mean Business Success

HTTP 200 tells you only that a service successfully received and processed your request. It does not guarantee:

  • A database write
  • Session creation
  • Inclusion in analytics reports
  • Passing every internal validation stage

Many analytics systems deliberately make such requests appear successful for two reasons:

  1. 1. Avoid exposing specific blocking rules to attackers: An explicit 403 bot detected would make it easier for attackers to iterate quickly;
  2. 2. Keep the public API behavior stable: Frontend SDKs do not flood logs with errors caused by risk-control details.

Silent dropping is therefore very common in anti-bot systems.

The Actual Decision May Happen Before the Analytics Application

A crucial point:The analytics application itself is not necessarily blocking a particular desktop container.

More often, the decision comes from:

  • CDN
  • Nginx rules
  • Cloudflare WAF
  • Libraries such as isbot
  • Custom gateway logic

These may apply UA-based risk filtering before Umami processes the event.

The failure may lie in the identity checks traversed by tracking code, rather than the code itself.

That is why changing the body or site identifier, or even suspecting the database, may never reveal the root cause.

Chrome and Electron are not the blockers in this chain; they are client runtimes sending requests. UA risk judgments are more likely made by ingress infrastructure before Umami: reverse proxies, CDNs, WAFs, or other anti-bot middleware. The “gateway before Umami” is generally not logic inside the Umami application, but rules in your server, reverse proxy, or cloud ingress. Only after passing those layers does Umami's own bot detection or event filtering make a second judgment. A more accurate description is therefore not “Umami blocked Electron,” but “the request was classified as low-trust traffic by ingress infrastructure or the server as it approached or entered Umami's processing pipeline.”

Controlled Testing: Why It Nearly Pinpoints UA as the Root Cause

The strongest part of this investigation was using controlled experiments.

Their engineering value is to break complex systems into testable hypotheses. If everything else remains unchanged and replacing only the UA consistently changes persistence, there is strong causal evidence linking UA to whether data is stored.

The results were:

No.Key UA characteristicsResult
1Gecko) followed directly by Chrome/132..., with no intervening product name and the desktop-container identifier retained✅ Persisted successfully
2Gecko) followed by an all-zero placeholder version, then Chrome + 桌面容器标识❌ Blocked and discarded
3Gecko) followed by a conventional, self-descriptive, non-placeholder client identifier, then Chrome + 桌面容器标识✅ Persisted successfully
4Plain Chrome + Safari, with no desktop-container identifier✅ Persisted successfully
5Another purely standard browser string✅ Persisted successfully
6A minimal string containing only the custom shell identifier and Safari compatibility field❌ Blocked and discarded

These results support several strong conclusions.

Conclusion 1: The Desktop-Container Identifier Is Not the Root Cause

Requests persisted successfully even with the container identifier retained. This directly rules out the crude assumption that the analytics system does not support desktop shell containers.

The real problem is that certain additional UA identifiers undermine the credibility of the entire string.

Conclusion 2: The Custom Shell Identifier Strongly Correlates with Loss

Removing the custom shell identifier restores normal behavior even with the desktop-container compatibility identifier retained. Reducing the UA to an unusual minimal structure containing only the shell identifier and Safari compatibility field consistently fails.

The custom shell identifier is therefore a clear high-risk signal, not harmless metadata.

Conclusion 3: All-Zero Placeholder Versions Match Another Set of Rules

Replacing the shell identifier with an all-zero placeholder still fails, while a conventional, self-descriptive, non-placeholder client identifier succeeds. This means custom product names are not universally fatal:

  • A custom product name may raise risk;
  • But a placeholder version such as 0.0.0 pushes it beyond a higher risk threshold.

This is a typical case of combined multidimensional heuristics: several anomalous signals jointly influence the result, rather than one Boolean rule.

First Principles: Why Looking Like a Browser Matters More Than Being One

This sounds counterintuitive, but closely reflects modern web risk control.

A server usually cannot directly prove that a real person is operating a browser. It collects low-cost signals to estimate a probability:

How likely is this request to be normal user traffic?

The UA is a cheap, high-value feature in that probabilistic system.

Risk Systems Evaluate Distributions, Not Labels

You may really be a desktop shell application or an internally developed client, but the risk model does not know your business context. It knows only client distributions historically seen at scale on the internet.

It does not ask:

  • “Are you a trusted internal application?”

It asks:

  • “Do you resemble ordinary traffic from real browsers?”

That is why the solution is not proving a custom shell identifier legitimate, but shaping outbound requests into a browser profile consistent with mainstream internet distributions.

Analytics Systems Aim to Filter Noise, Not Accept Everything

From an analytics system's perspective, mistakenly accepting bot traffic is often worse than dropping a small amount of edge-case traffic, because bots contaminate aggregate metrics:

  • UV
  • Session
  • Bounce Rate
  • Retention
  • Conversion Funnel

The system therefore prefers caution over readily accepting unusual UAs.

In other words, mistakenly blocking a few atypical clients is a cost many analytics and risk systems accept.

This explains why retrying will not cure the issue, and why an error-free API response cannot prove that everything is fine.

The Final Fix: Unify Outbound Identity Rather Than Tracking Semantics

Since the root cause was an abnormal outbound identity profile, the solution was not further payload changes, but:

Make all Umami-bound requests present the same trustworthy browser UA, verified to persist successfully, at the egress layer.

We used outbound sanitization and alignment across both paths.

The idea was straightforward:

  • Leave the analytics server's logic alone;
  • Do not rely on relaxed gateway rules;
  • Remove high-risk characteristics before requests leave the client;
  • Make page and script paths present the same external identity.

This is a typical engineering fix that corrects system boundary conditions with minimal changes.

Why Align Both Paths?

The page-originated path receives targeted sanitization at the desktop network egress, applying only to the target analytics service's unified event-ingestion endpoint. The script path does not rely on desktop interception; it directly reuses the same outbound UA constant already verified to persist successfully.

This is crucial. Fixing only the page path leaves a subtle inconsistency:

  • Page tracking persists correctly;
  • Script tracking continues to disappear unpredictably;
  • Analytics ends up measuring the same feature differently depending on its entry point.

The script runtime / command-line client must therefore switch to the same outbound UA constant too.

Summary

The root cause of this Umami data loss was neither unsent requests nor malformed bodies. Abnormal outbound User-Agent characteristics triggered risk controls, causing an upstream gateway or risk pipeline to classify the requests as machine traffic. Targeted UA sanitization at desktop network egress, combined with the same verified standard UA in the script path, aligned identity across the tracking pipeline and eliminated the misleading silent-loss problem where the API returns 200 but the data never reaches storage.
