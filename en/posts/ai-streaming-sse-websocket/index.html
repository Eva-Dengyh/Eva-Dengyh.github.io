Why Does AI Streaming Prefer SSE over WebSocket?

Eva·2026.05.28·8 min read

 

Inspect the networking layer of mainstream AI products and a consistent pattern emerges: most choose SSE (Server-Sent Events) for streaming responses, rather than the seemingly more real-time WebSocket. OpenAI's /v1/chat/completions returns SSE when stream: true, Anthropic's Messages API also uses SSE for streaming, and Hugging Face's Text Generation Inference defaults to SSE as well.

This is no coincidence. It reflects Occam's razor in software engineering—do not introduce entities unnecessarily—and the trade-off between protocol capabilities and engineering cost. Before explaining why, let's clarify the two protocols.

What Is SSE?

SSE stands for Server-Sent Events. Part of HTML5 and defined in the WHATWG HTML Living Standard, it is essentially an ordinary HTTP response whose body is not written all at once. Instead, the server keeps the connection open and continuously appends data in a specific format.

Its wire format is simple, based on the text/event-stream MIME type. Each message looks roughly like this:

data: 第一段内容

data: 第二段内容

event: custom
data: 带自定义事件类型的内容

id: 42
data: 带 ID 的内容，用于断线续传

Messages are separated by a blank line. Browsers provide a native EventSource API to consume this format:

const es = new EventSource('/api/stream');
es.onmessage = (e) => console.log(e.data);

Key protocol properties of SSE:

  • HTTP-based, with no protocol upgrade or custom frames
  • One-way, allowing only server-to-client pushes
  • Text protocol, supporting only UTF-8, not binary data; binary content must be Base64-encoded manually
  • Built-in reconnection: After disconnection, EventSource automatically reconnects by default
  • Event IDs and resumption: The Last-Event-ID request header tells the server where to resume

What Is WebSocket?

Defined in RFC 6455, WebSocket is a separate application-layer protocol. It establishes a connection through an HTTP upgrade handshake (Upgrade: websocket). After a successful handshake, the connection leaves HTTP semantics and switches to WebSocket's own framing protocol.

Its features are heavier but more general:

  • Full duplex: Both sides can send messages at any time after connecting
  • Frame-based, with its own binary frame format supporting text and binary frames
  • Persistent connection, remaining open until either endpoint explicitly closes it
  • No built-in reconnection: The application must handle disconnections
  • No built-in authentication: Although the handshake uses HTTP, the browser API does not permit custom headers

The core differences:

Why AI Streaming Chooses SSE

Applying those properties to AI streaming reveals several reasons.

1. AI Streaming Is Fundamentally One-way

LLM inference works like this: the client sends one request; the server begins generating token by token and pushes each portion to the client. During that process, the client need not send anything further—no interjections, acknowledgments, or heartbeats. When the answer finishes, the next question is a new HTTP request.

In other words, this is request–response with a response body stretched into a stream. WebSocket's bidirectional capability goes unused, so you pay for protocol complexity without receiving its benefit.

A few AI scenarios are genuinely bidirectional. OpenAI's Realtime API for voice conversations, for example, requires continuous audio frames from the client and continuous audio and transcriptions from the server. OpenAI uses WebSocket and WebRTC there. This reinforces the selection logic: use WebSocket when bidirectional communication is actually needed.

2. Reuse the HTTP Ecosystem Directly

Because SSE is an HTTP response, the entire HTTP infrastructure remains available:

  • Reverse proxies and load balancers: Streaming HTTP responses are standard capabilities in Nginx, HAProxy, and ALB
  • CDNs: Cloudflare and Fastly support SSE passthrough, with some offering SSE-specific optimization
  • Authentication: Authorization headers, cookies, and OAuth flows remain unchanged
  • HTTP/2 multiplexing: Multiple SSE streams can run concurrently over one TCP connection
  • Observability: Existing HTTP monitoring, logging, and tracing tools continue to work

After upgrading, WebSocket traffic is no longer HTTP; middleware sees an opaque byte stream. This creates practical issues: some older load balancers lack WebSocket support, some enterprise networks intercept or restrict non-HTTP traffic, and CDNs typically require separate WebSocket configuration.

3. Authentication Fits More Naturally

A frequent browser-side pitfall is that the native WebSocket constructor does not allow custom request headers. This historical limitation is written into the specification.

// 不行，没有第三个参数
new WebSocket(url, protocols, { headers: { Authorization: 'Bearer xxx' } });

Browser WebSocket authentication therefore relies on several relatively awkward approaches:

  • Put the token in the URL query string, where logs and referrers may record it
  • Use cookies, requiring the same domain
  • Put the token in Sec-WebSocket-Protocol, which is a hack
  • Send authentication information in the first message after the connection is already established

SSE uses ordinary HTTP requests, so Authorization headers work normally, without these detours.

4. A Lighter Server Implementation

WebSocket is a stateful persistent connection. Servers must manage connection objects, heartbeats, state machines, and closure procedures. SSE can be very simple: receive a request, set response headers, write chunks in a loop, and close when finished. Here is a minimal Node.js example:

app.get('/stream', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');

  for await (const token of llm.stream(prompt)) {
    res.write(`data: ${JSON.stringify({ token })}\n\n`);
  }
  res.end();
});

No dedicated WebSocket framework or connection-pool management is required. Closing the connection simply means ending the HTTP response.

5. Reconnection and Resumption Out of the Box

EventSource reconnects automatically by default, sending the last received id as the Last-Event-ID header so the server can resume. This is particularly useful on unstable mobile networks. With WebSocket, the application must implement all of this itself.

SSE Limitations and Engineering Considerations

To be fair, SSE has weaknesses. Common ones include:

Server pushes only. If the client needs to intervene during a stream—interrupt generation or adjust parameters—SSE alone is insufficient. Use WebSocket or pair SSE with a separate control endpoint, sending cancellation through another HTTP request. OpenAI and Anthropic both follow the latter approach.

EventSource supports only GET. AI request bodies are usually large, containing history, system prompts, and parameters, so POST is necessary. As a result, almost all AI vendors' SDKs avoid using EventSource directly and instead use fetch + ReadableStream to parse SSE themselves. Both OpenAI's and Anthropic's SDKs do this, which represents a real engineering cost.

HTTP/1.1 concurrent-connection limits. Browsers cap HTTP/1.1 connections per domain, usually at six, and multiple SSE connections consume those slots. HTTP/2 and later multiplexing solve this, but servers still using HTTP/1.1 need care.

Proxy buffering. Reverse proxies such as Nginx buffer responses by default, breaking streaming. Disable buffering explicitly, for example through the response header X-Accel-Buffering: no, or by disabling proxy_buffering in Nginx configuration.

Persistent-connection timeouts. Gateways and load balancers have their own idle timeouts—60 seconds by default for AWS ALB and 100 seconds on Cloudflare's free tier—which long AI responses may hit. Adjust timeouts or periodically send SSE comment lines (:\n\n) as keepalives.

Summary

SSE and WebSocket address differently shaped problems. WebSocket is designed for genuine bidirectional real-time communication. AI streaming text is an extended request–response instead. For that shape, SSE's inherited HTTP infrastructure, simple authentication, lightweight implementation, and built-in reconnection make engineering costs substantially lower.

WebSocket is not obsolete. It remains appropriate for collaboration, real-time games, signaling, and voice conversations requiring bidirectional communication. But SSE is the more convenient tool for one-way AI text streams, as the consistent choice of mainstream vendors reflects.
