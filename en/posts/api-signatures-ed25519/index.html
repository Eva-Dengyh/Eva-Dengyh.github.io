What API Signatures Protect Against: From Hashes to Ed25519

Eva·2026.08.14·16 min read

 

Let me start with the question you may already be asking: don't we already have HTTPS? Why do APIs still need signatures?

HTTPS protects the channel against eavesdropping and tampering; signatures protect data and identity. TLS terminates and decrypts at gateways and proxies, and the stretch from gateway to backend often is no longer encrypted. More importantly, on an open platform, HTTPS can establish that the channel was not intercepted, but cannot establish that a request came from the application holding the key. So even with HTTPS throughout, servers still verify signatures. Now, on to the subject.

The amount that changed

A client sends a payment request for 100 yuan. After traveling across the public internet, it reaches the server with the amount changed to 1 yuan. How can the server tell that the message was altered?

Without a signature, it cannot. The message is ordinary text: anyone can change it and send it again, and the server sees only another request. The two API parties eventually agree on a rule: the client attaches a fingerprint calculated from the content, and the server repeats the calculation and rejects any mismatch. Change even one character and the fingerprint changes.

API documentation generally calls this fingerprint a signature.

Signatures defend against people trying to interfere with messages. Changing a message is tampering; creating a valid request without the key is forgery; sending a request and later denying it is repudiation. Let's start with the first attacker and work through them one by one.

1 Three problems inside a message

1.1 Changing the message → Hashing

The first attacker is straightforward: change the amount from 100 to 1 and resend the message.

A hash, also called a digest, stands in the way. It compresses content of any length into a fixed-length number. SHA-256 always produces 256 bits, or 64 hexadecimal characters, regardless of input length. Even a tiny input change produces a completely different output.

That gives us a check: the sender hashes the content and the receiver recalculates it. If they match, the content is considered unchanged. Change any byte and the fingerprint immediately changes, exposing the tampering.

For both sides to calculate the same fingerprint, they must first agree how to assemble the input. Sort parameters by their names' ASCII values, concatenate them without separators, and finally encode the result in hexadecimal for transmission. The Taobao Open Platform documentation gives an example: sorting foo, bar, foo_bar, and foobar produces the concatenation bar2foo1foo_bar3foobar4.

Signing roughly follows three steps: remove empty values, sort and concatenate in ASCII order, and then apply the key to calculate the digest.

1. 过滤空值。{amount: 100, nonce: null} -> {amount: 100}
2. ASCII 排序。amount=100&time=1620000000
3. 套密钥计算。HMAC-SHA256(secret_key, "amount=100&time=1620000000")

This is where integrations most often fail. Key capitalization, sorting within nested objects, expanding arrays, and whether empty values and null count must all agree. A single discrepancy produces different signatures. Check the assembly rules before suspecting the algorithm.

Take empty values: the common approach excludes empty values and null from signing, while some older APIs require converting null into an empty string first. Follow the other party's documentation. The first integration step is always a painstaking reading of the “signing rules” page.

Signature length comes from this as well: MD5 and HMAC-MD5 produce 128 bits, or 32 characters; SHA-256 produces 256 bits, or 64 characters. Length alone offers a clue to the algorithm.

But hashing has a fatal problem: it requires no key. It cannot stop the second attacker.

1.2 Changing and recalculating → HMAC

The second attacker is cleverer. Instead of merely changing the hash, they alter the content and use the same algorithm to calculate and attach a new hash. Everything looks normal. A hash can detect changed content, but cannot stop someone who recalculates it. HMAC addresses this.

The solution is to add a key. Both parties share a secret in advance and incorporate it when calculating the fingerprint. Someone without the key cannot produce a valid fingerprint even after changing the content correctly. This construction is HMAC, a keyed-hash message authentication code. HMAC-SHA256 is the most common variant.

Why not simply prepend a key, as in MD5(secret + data)? Such constructions have a mathematical weakness called length extension. Without knowing the key, an attacker can use a known signature to derive a valid signature for data with additional content appended—as though continuing to write after someone has signed a message. HMAC incorporates the key into hashing through two rounds of XOR operations, specifically closing this hole. HMAC-SHA256 remains a default choice for API signing, and Feishu, Taobao Open Platform, and many internal integrations use this family of schemes.

Shared keys have two inherent shortcomings. First, they cannot establish who sent something. Both parties have the same key, so the receiver can generate the same fingerprint and cannot later prove to a third party that the other side created it. Second, delivering the key safely is difficult. It must be handed over through a reliable offline channel; if transmitted over the network and intercepted, all subsequent signatures are compromised. One-to-one integration is manageable, but distributing keys becomes a nightmare when many partners are involved.

The second shortcoming brings us to the third attacker.

1.3 Sending and denying → Public and private keys

The third attacker is the most devious. They neither alter nor impersonate: they submit an order and then claim it was not theirs. A shared key cannot resolve this because either party can calculate the fingerprint. Public and private keys address it.

Asymmetric signatures close this gap. They generate a pair of keys: one private and one public. Only the signer keeps the private key; the public key can be distributed freely to anyone.

Signing uses the private key and verification uses the public key, reversing the direction used for encryption. Encryption locks with the public key and unlocks with the private key to prevent eavesdropping; signing stamps with the private key and verifies with the public key to prevent tampering and impersonation. Think of a personal seal and a registered impression. The private key is your seal, which only you can use; the public key is the sample others compare against to confirm the impression came from you. All three problems are now addressed. Intercepting a public key does not enable anyone to stamp a signature. Nonrepudiation also holds: others can verify but cannot sign, so you cannot deny responsibility afterward.

One implementation detail first: algorithms such as RSA can process only limited amounts of data, and large-number arithmetic is slow, making direct signing of an entire message impractical. In practice, the content is hashed first, and only those few dozen bytes are signed. In paired names such as RSA-SHA256 and ECDSA-SHA256, the first part is the signing algorithm and the second is the hash it signs.

Modern APIs take this approach further. Interfaces such as WeChat Pay API v3 and AWS SigV4 use different assembly rules: first combine request elements—method, path, timestamp, nonce, and the request body or its hash—into a canonical string, then sign it. Each provider specifies its own details, but the principle remains the same: compress the content into a short string, then stamp that string.

Several implementations are common. RSA is the oldest and most widespread, with the best compatibility. Its strength depends on key length, now starting at 2048 bits, and it is widely used by payment platforms and HTTPS certificates. Before signing, RSA wraps the hash in padding. The older scheme is PKCS#1 v1.5; the more robust RSA-PSS is now recommended. ECDSA uses elliptic curves, offering much shorter keys, faster computation, shorter signatures, and lower bandwidth at equivalent strength. It is used almost universally in blockchains, but has extremely strict randomness requirements: get a nonce wrong once and the private key is lost. Section 3.2 discusses that pitfall. Ed25519 is a younger generation using deterministic signatures: the nonce is derived from the private key and message, without an external random-number generator, eliminating the possibility of such reuse (RFC 8032). SSH and many newer systems use it. Chinese regulatory compliance may require the national cryptographic algorithm SM2.

These algorithms resist attack because of two types of mathematical problems. RSA relies on integer factorization: multiplying two large primes is easy, but splitting their product back into its primes is extremely hard. Recovering the private key from the public key requires solving that difficult problem. DSA, ECDSA, and Ed25519 rely on the discrete logarithm problem: given a number and a power of it, recovering the exponent is practically impossible. Both problems are one-way: calculation in one direction is easy, while reversing it is futile. Signature security rests on that asymmetry. DSA itself was specified by the US Digital Signature Standard, DSS, and supports signing but not encryption. ECDSA and Ed25519 have largely replaced it, leaving mainly historical significance.

Those three attackers all meddle with the contents of a message. The fourth does not even change it.

2 Two loopholes outside the message

2.1 Replaying unchanged → Timestamps and nonces

The fourth attacker has the easiest job: resend the exact same request and the server accepts it again. Timestamps and nonces stop this. Replay a 100-yuan payment request ten times and it charges ten times. Signatures detect changed content; they do not prevent unchanged content from being sent again.

API specifications therefore require a timestamp and nonce. Requests older than the permitted interval are rejected, and each nonce is accepted only once. Nonces need not be stored forever: they matter only within the timestamp's validity window and can be deleted after expiry to prevent endless database growth. The timestamp in Taobao's common parameters serves this purpose.

2.2 Guessing character by character → Constant-time comparison

The fifth attacker uses timing to guess the signature. Constant-time comparison addresses this. If the server compares characters one by one and returns immediately on a mismatch, a 32-character signature with the first three characters correct takes a different amount of time than one that is completely wrong. Repeated attempts let an attacker gradually infer the signature from response times. This is a timing attack.

The correct approach is to finish the entire comparison regardless of where the mismatch occurs, keeping the time constant. Many mature SDKs provide a dedicated function for this.

3 Algorithms age, and keys get lost

3.1 Hash collisions → Retiring MD5 and SHA-1

Set attackers aside for a moment: algorithms themselves can have flaws, most famously hash collisions. The remedy for a flawed algorithm is retirement. In 2004, Wang Xiaoyun's team announced at a cryptography conference that they had found MD5 collisions: two different inputs with the same hash. This means an attacker can prepare a malicious message with the same hash as a legitimate one, undermining the signature. Since then, MD5 has largely retired from signing. Most APIs still documenting an MD5 option retain it for legacy compatibility.

In February 2017, Google and the Netherlands' CWI jointly announced the first practical SHA-1 collision, a project named SHAttered. SHA-1 followed the same path.

3.2 Stealing private keys → The PS3 lesson

The worst attacker comes last: they skip the message and steal the private key directly. Key custody is the defense. In late 2010, security team fail0verflow disclosed how Sony's PS3 private key had been recovered because Sony reused the same nonce across multiple signatures. ECDSA requires a fresh, unpredictable nonce for every signature. Expose a nonce once and the private key is lost with it. One advantage of Ed25519 is that its signing process does not depend on random numbers, eliminating this class of mistake at its root.

Such incidents also show that key custody is the weakest part of the entire system, far more fragile than the algorithm itself.

4 Applying this to a project

4.1 Choosing in practice

For your own project, the decision is simple: look at who is integrating with whom.

For a private, one-to-one API where keys can be delivered offline, HMAC-SHA256 is enough: simple, fast, and inexpensive to implement. For multiple parties, or when a third party must be able to prove that a request came from you, use RSA or Ed25519. JWT offers a ready comparison: within the same standard, HS256 uses HMAC for mutual recognition inside systems, while RS256 uses RSA when third parties also need to verify signatures. Payment platforms almost uniformly use RSA-SHA256, called RSA2 in Alipay's documentation and also used by WeChat Pay API v3.

One unavoidable question remains: if public keys can circulate freely, how do you know a key really belongs to a particular company? Anyone can generate a key pair and claim to be Alipay. Certificates provide the answer. A recognized certificate authority, or CA, signs the company's public key with its own private key, creating a chain of trust. That is the mechanism behind the HTTPS padlock in your browser. Open platforms publish their public keys through official channels for the same purpose, simply omitting the CA step.

4.2 Common signing algorithms in one table

The algorithms mentioned throughout the article are collected here in three groups based on their use of keys, for easy reference.

Symmetric schemes share one key and produce a message authentication code. Cryptography calls this a MAC; only asymmetric schemes produce digital signatures. Chinese development terminology often calls all API authentication codes “signatures.” Keep these meanings separate when reading English documentation or talking with security specialists.

4.3 A few final words

Put priorities in order. Key management matters more than algorithm selection; replay protection and timing-attack defenses matter more than algorithm strength; mature standards matter more than inventing your own. A poor algorithm can be replaced, but changing algorithms cannot undo hard-coded keys or reused nonces.

The next time you read a platform's signing documentation, whether Taobao's MD5 and HMAC or WeChat Pay's RSA-SHA256, break it down into these layers: hash to compress, sort and assemble, stamp with your key system, then encode in hexadecimal and compare. That is what signing amounts to from start to finish.
