每天被信息轰炸？TrendRadar 帮你从噪音里找到真正有用的信号

Eva·2026.04.23·15 分钟阅读

 

你有没有这样的烦恼？

每天早上打开手机，微博热搜 50 条，知乎推荐 30 篇，B 站通知一堆，还有群里转发的各种文章……刷了一个小时，脑子里却一片模糊——感觉什么都看了，又感觉什么都没看。

更难受的是：真正和你有关的信息——你关注的行业动态、你在意的公司新闻、你需要的技术趋势——往往被淹没在明星八卦和热搜话题里，根本来不及看到。

这不是你的问题，是现在所有信息平台的商业逻辑决定的。它们的目标是让你多停留，不是让你获取有价值的信息。

如果有一个"信息私人助理"呢？

想象一下这样的场景：

每天早上 8 点，你的飞书/邮件/手机推送收到一条消息。打开来，里面已经帮你从知乎、微博、36氪、B站等十几个平台筛选好了你真正关心的内容，还附上了一段 AI 分析："今天科技板块情绪偏乐观，有两个异常信号值得关注……"

全程不需要你打开任何 App，不需要手动筛选，不需要被算法牵着鼻子走。

这就是 TrendRadar 在做的事。

它是一个完全开源、可自托管的智能信息雷达，核心逻辑很简单：你定义自己关心什么，它帮你从噪音中找到信号。

适合这些人：

  • 📈 投资者：实时监控市场情绪、行业动态、相关公司新闻
  • ✍️ 内容创作者：追踪热点，找选题灵感，不错过流量风口
  • 📣 公关/品牌从业者：监测品牌提及、竞品动态，第一时间响应舆情
  • 🔬 技术研究者：关注开源生态、技术趋势，过滤掉无关信息
  • 😩 普通人：单纯不想每天被信息轰炸，只想知道"和我有关的事"

它和普通的新闻 App 有什么区别？


普通新闻 App / RSS 阅读器TrendRadar
谁决定你看什么平台算法你自己定义的规则 + AI
有没有趋势分析没有有，LLM 驱动的多维度分析
数据在哪里平台服务器你自己的机器或云存储
能推送到哪里应用内通知飞书、钉钉、Telegram、邮件等 9+ 渠道
能不能编程扩展基本不行支持 MCP 协议，可接入 AI 工具链

简单说：普通信息工具是被动接收，TrendRadar 是主动获取。

用一个例子感受一下

假设你是一位关注 AI 行业的投资者，你在 ai_interests.txt 里写了一句话：

我关注 AI 创业公司的融资动态、大模型的新产品发布，以及 AI 监管政策的变化

TrendRadar 会把这段自然语言交给 LLM，让它帮你从今天抓取的所有热榜内容里，找出符合你意图的条目——不需要你手动维护关键词列表。

过滤完之后，它还会生成一段分析：

今日核心趋势：AI Agent 赛道讨论热度上升 40%，多家媒体跟进报道某大模型发布...

异常信号：某 AI 公司股价相关讨论在过去 2 小时内出现异常增长，情绪偏负面...

展望建议：建议关注明日政策相关新闻...

然后把这些内容推送到你的飞书或邮箱。整个过程全自动，你只需要读报告。

好了，感性认识有了，下面我们进入技术层面，看看 TrendRadar 是怎么实现这一切的。

引言：信息时代的结构性困境

互联网的普及将人类带入了信息过剩（information overload）的时代。根据 IDC 的数据，全球每天产生的数据量已超过 2.5 quintillion 字节，其中绝大多数对任何单一个体而言都是噪声。对于投资分析师、内容创作者、舆情监控人员或技术研究者来说，这一问题尤为突出——他们需要在有限时间内，从海量平台的信息流中提取具有高信噪比的有效信号。

传统的解决方案——RSS 阅读器、信息聚合 App、人工订阅——均停留在"聚合"层面，并未真正解决过滤与分析的核心问题。更深层的困境在于：平台算法的推荐机制并不以用户的实际信息需求为优先目标，而是以用户留存时长为优化目标，这本质上是一个利益错位问题。

TrendRadar 是一个开源的智能信息雷达系统，旨在通过"聚合 → 过滤 → 分析 → 推送"的完整数据管道，将被动的信息消费转化为主动的信息获取。本文将从系统架构、核心机制和工程设计三个维度对其进行深度解析。

系统定位与设计边界

核心问题域

TrendRadar 主要解决以下三类问题：

问题维度传统方案的局限TrendRadar 的解法
信息过载人工筛选效率低，依赖算法推荐关键词引擎 + AI 语义过滤，主动定义兴趣范围
平台碎片化多平台切换，无统一视图统一数据获取层，11+ 平台单一入口
分析缺失只提供原始信息，缺乏趋势洞察LLM 驱动的五维趋势分析

目标用户画像

系统在设计上针对以下典型场景进行了优化：

  • 量化投资者：需要低延迟捕获市场情绪信号，对数据时效性敏感
  • 公关与舆情监控：需要近实时追踪品牌提及和竞品动态
  • 内容创作者：追踪热点话题，需要跨平台的热度聚合视图
  • 技术研究者：关注开源生态、技术趋势，需要去噪后的高质量信息

系统架构设计

TrendRadar 采用清晰的六层垂直架构，每层职责单一，层间通过标准接口解耦。

1. 数据获取层（Data Acquisition Layer）

数据获取层是系统的数据入口，负责从异构来源获取原始数据并进行标准化处理。

NewsNow API 客户端封装了 11+ 个主流平台（知乎、微博、B站、抖音、百度热搜、36氪等），通过统一接口屏蔽各平台的 API 差异。核心设计要点：

  • 自动处理限流与指数退避重试
  • URL 规范化（去除 UTM 追踪参数、统一 scheme、路径归一化）
  • 时区转换，统一为用户配置的本地时区

RSS/Atom 抓取器基于 feedparser 库实现，支持用户自定义订阅源。通过字段映射将不同 Feed 格式（RSS 2.0、Atom 1.0）的数据结构转换为系统内部统一的 NewsItem 数据类。

2. 调度与控制层（Scheduling & Control Layer）

调度层是系统的控制平面，驱动整体工作流的时序执行。

Scheduler 类（位于 trendradar/core/scheduler.py）读取 config/timeline.yaml，将用户定义的时间计划转换为 ResolvedSchedule 数据类：

@dataclass
class ResolvedSchedule:
    collect: bool    # 当前时间点是否采集数据
    analyze: bool    # 是否触发 AI 分析
    push: bool       # 是否推送通知
    report_mode: str # daily / current / incremental

执行去重机制通过 period_executions 数据库表跟踪每日执行记录。once_per_day 标志确保即使服务在同一时段内重启，也不会产生重复推送，这对于生产环境的稳定性至关重要。

3. 核心处理引擎（Core Processing Engine）

核心引擎是系统最复杂的部分，实现了多阶段串行的数据处理管道：

原始数据
   ↓ [1] URL 规范化
   ↓ [2] 全局过滤器（[GLOBAL_FILTER] 排除规则）
   ↓ [3] 关键词匹配（正则 / 纯文本 / AI 语义兴趣）
   ↓ [4] 必需词检查（+前缀词 AND 逻辑）
   ↓ [5] 分组过滤（!前缀词触发组内互斥排除）
   ↓ [6] 权重计算
   ↓ [7] 新内容检测（对比历史数据，标记 🆕）
   ↓ [8] AI 处理（翻译 / 分析 / 摘要）
   ↓ [9] 输出生成（HTML + 多渠道通知）

权重计算模型采用加权线性组合：

综合权重 = 排名得分 × 0.6 + 频次得分 × 0.3 + 平台热度 × 0.1

其中排名得分来源于平台原始热榜排名，频次得分衡量同一话题在多平台的出现次数（跨平台共振是高价值信号的强指标），平台热度系数则根据平台受众规模预设。

关键词过滤语法设计得较为精妙，支持三种过滤模式：

语法语义示例
word普通关键词（OR 逻辑）AI
+word必需词（AND 逻辑）+股票
!word组内排除词!明星
[GROUP]分组定义[科技]

这套语法允许用户定义复杂的过滤规则而无需编写代码，降低了使用门槛。

AppContext（trendradar/context.py）作为依赖注入容器，统一管理所有核心服务的生命周期，避免了全局单例和紧耦合问题。

4. 存储层（Storage Layer）

存储层采用策略模式（Strategy Pattern），根据部署环境自动选择合适的后端：

  • LocalStorageBackend：写入本地 SQLite，按日期分库（output/news/YYYY-MM-DD.db），适合单机部署
  • RemoteStorageBackend：支持 Cloudflare R2、AWS S3、阿里云 OSS、腾讯云 COS。工作流为"下载现有 DB → 合并增量数据 → 上传回云端"，实现了无状态容器下的持久化方案

SQLite 按天分库的设计兼顾了查询性能（历史数据不参与扫描）和管理便利性（直接删除文件即可清理旧数据）。

5. AI 处理层（AI Integration Layer）

AI 处理层通过 LiteLLM 统一接入 100+ 个 LLM 提供商（OpenAI、Anthropic、Google、本地 Ollama 等），用户只需更换配置即可切换底层模型，不存在厂商锁定。

系统内置了五个分析维度，由结构化 Prompt 驱动：

  1. 1. 核心趋势：识别当前信息流中的主导叙事和话题集群
  2. 2. 情绪与争议：分析舆论情绪倾向，识别高争议话题
  3. 3. 异常信号：检测突发事件、黑天鹅信号和统计异常
  4. 4. RSS 洞察：对订阅源数据进行深度摘要
  5. 5. 展望与策略：基于当前趋势提供前向性建议

max_news_for_analysis 配置项（默认 150 条）控制单次送入 LLM 的最大数据量，在分析质量和 token 成本之间取得平衡。

6. 输出与分发层（Output & Distribution Layer）

系统支持 9 个推送渠道，每个渠道针对其平台特性进行了定制化适配：

渠道内容大小限制格式特点
飞书29 KB富文本卡片企业内部协作首选
钉钉20 KBMarkdown适合团队场景
企业微信4 KBMarkdown/文本限制较严，需内容压缩
Telegram4 KBHTML支持超链接，个人用户友好
ntfy3.8 KB反向排序轻量推送，适合移动端
Bark3.6 KBMarkdowniOS 原生推送体验
Slack4 KBmrkdwn团队协作，支持频道分发
Email无限制HTML内容最完整，支持历史归档
Webhook4 KB自定义 JSON最灵活，可对接任意系统

对于内容大小限制差异较大的渠道，系统实现了自动内容截断和摘要生成逻辑，确保核心信息不丢失。

架构设计原则分析

TrendRadar 的工程实践体现了几项值得借鉴的设计原则：

1. 关注点分离（SoC）：六层架构每层职责边界清晰，数据获取层不涉及业务逻辑，AI 层不关心数据来源，分发层不感知数据内容。

2. 依赖注入（DI）：AppContext 作为 IoC 容器统一管理服务实例，避免了散落各处的全局状态和硬编码依赖，提升了可测试性。

3. 策略模式（Strategy Pattern）：存储后端、过滤模式、通知渠道均以策略模式实现，运行时根据配置选择具体实现，新增扩展无需修改核心逻辑。

4. 管道模式（Pipeline Pattern）：数据处理流程被分解为有序的、可组合的处理阶段，每个阶段的输出是下一阶段的输入，便于调试和单元测试。

5. 优雅降级（Graceful Degradation）：AI 分析失败时降级为关键词过滤；远程存储不可用时降级为本地 SQLite；单平台抓取失败不影响整体流程。

6. 幂等性设计：执行去重机制确保同一时段的操作幂等，系统可以安全地重启和重试，符合生产环境对稳定性的要求。

7. 配置驱动（Configuration-Driven）：核心行为通过声明式配置定义，而非命令式代码，降低了二次开发和定制的门槛。

总结

TrendRadar 代表了一种从"信息消费工具"向"信息分析系统"演进的设计思路。它将原本分散在多个 App 中的信息获取流程，整合为一条可配置、可扩展、AI 增强的自动化管道。

从工程视角看，其六层架构、策略模式的存储后端、依赖注入的服务管理，以及配置驱动的核心行为，都体现了成熟工程实践的积累。对于有信息密集型需求的个人或团队，TrendRadar 提供了一个高度可定制的开源基础设施，可在此之上构建符合自身需求的信息获取工作流。

信息不对称本质上是决策质量的护城河。TrendRadar 试图将这条护城河向更广泛的用户群体开放——这或许才是其最重要的价值所在。
