Eino ADK：Go 开发者的 Agent 运行时

Eva·2026.07.19·10 分钟阅读尚无英文译文

 

构建可调用工具、可取消生成、可扩展为多 Agent 的应用时，除了调用大模型 API，还需要一层 Agent 运行时：负责 ReAct 循环、事件流、中间件与协作编排。

Eino ADK（Agent Development Kit） 正是这一层。

它是字节跳动 CloudWeGo 开源的 Eino 生态中，面向 Go 的 Agent / Multi-Agent 开发套件。

一句话概括：

它不是「又一个 LLM SDK」，而是一套 Agent 运行时——谁负责推理，谁负责行动，事件怎么流式吐出，中间件挂在哪里，多 Agent 怎么协作。

Eino 和 ADK，分别管什么

Eino 是大模型应用开发框架（Go first），覆盖模型适配、组件编排（Graph / Chain）、工具、回调等基础设施。

ADK 是 Eino 里专门做 Agent 的一层。设计上参考了 Google ADK 一类对 Agent 与协作的抽象，核心能力包括：

  • 用统一的 Agent 接口，描述「能跑一轮、能产出事件」的单元
  • 用事件驱动输出，而不是「一次性返回一个大字符串」
  • 提供可组合的协作原语：顺序、并行、循环、Supervisor、Plan-Execute 等
  • 用 Runner 作为单次执行入口，并支持流式、取消、中断等运行时能力

分工可以概括为：

Eino 管组件与编排底座，ADK 管「自主决策型 Agent」怎么跑。

官方用下面这张图说明：Eino 不是孤立的运行时库，而是覆盖 AI 应用从设计到运维的一整套生态。

读图时可以抓住三条线：

  1. 1. 中间三层是开发主栈：最下面红色是 Eino（核心类型、组件定义、compose / callback / streaming、关键 Flow，以及 ADK）；中间紫色是 Eino-Ext（官方组件实现、回调、第三方集成）；最上面黄色是 User Code（自定义组件、回调、Lambda）。
  2. 2. 左侧绿色 Eino Examples 对齐「Research & Design」——从示例起步，而不是从空白项目猜 API。
  3. 3. 顶部 Devops Tooling（可视化编排、代码生成、可视化调试、Telemetry）和右侧 Integrated 3rd-party platforms（Tracing / Hosting / Evaluation）分别覆盖调试与部署运维。

对写业务的人来说，日常接触最多的是中间那一列：站在 Eino 提供的抽象上，用 Eino-Ext 的现成实现，再在 User Code 里补自己的逻辑。 ADK 就嵌在最底层的 Eino 核心里。

框架内部怎么分层，官方还有一张更细的结构图：



左侧是 Eino 本体，自下而上大致是：

  • Schema / Callbacks：Message、Document、StreamReader / StreamWriter、ToolInfo，以及回调的 Handler / Inject / Trigger
  • Components：组件抽象——类型定义、输入输出、Call Option、流式范式、Callback Info
  • Compose：编排引擎（pregel / dag）与 API（Graph / Chain / Workflow），内含 ReAct 等 Flow，以及 node、edge、branch、stream、interrupt & checkpoint 等积木
  • ADK（顶层）：面向 Agent 的高级抽象——ChatModelAgent、WorkflowAgent、Agent Tool / Transfer / Middleware、Interrupt Resume；中间件如 FileSystem、Context Engineer；预置形态如 DeepAgents、Supervisor、PlanExecute

右侧是 Eino-Ext：Devops Tooling、各类 Component Implementations（Chat Model、Retriever、Tool、Prompt 等），以及 Tracing / Metrics 等 Callback Handlers。箭头很清楚——Ext 实现左侧的抽象，不另起一套协议。

所以读这两张图可以收成一句：

生命周期图回答「Eino 生态覆盖开发的哪些阶段」；分层图回答「ADK 在框架里站在哪一层、底下靠什么撑着」。

为什么不直接调模型？

直接调 ChatModel 时，ReAct 循环（Reason → Act → Observe）通常由业务侧自行实现：

拼 messages → 调模型 → 有 tool_calls 就执行工具 → 再调模型 → …

ADK 将上述循环收成框架原语，对比如下：

  • 直接调模型：循环逻辑在业务代码中；流式与取消需自行对接；上下文压缩 / Skill / 重试容易侵入主流程；扩展为多 Agent 时改动面较大。
  • 使用 ADK：ChatModelAgent 内置 ReAct Loop；Runner + context 统一承载流式与取消；Middleware 挂在循环生命周期上；协作 Agent / DeepAgents 可渐进接入。

从架构上看，将执行单元定为 Agent（而非裸模型调用），有利于后续注入 Tool、挂载 Skill Middleware，而不必同步推翻聊天界面、消息表与模型目录。

对照分层图也能理解这一点：Compose 层已经有 ReAct Flow；ADK 再往上收成可直接用的 Agent 原语，业务不必自己在 User Code 里重写整套循环。

四个核心概念

结合分层图里 ADK 那一层，核心可以收成下面几块。

1. ChatModelAgent：自主决策的最小单元

结构可概括为：

ChatModel（推理）
  + Tools（行动）
  + Instruction（约束）
  + ReAct Loop（决定何时推理、何时调用工具）

适用于问题边界不固定、需要模型决定下一步动作的场景。

按官方分工：确定性编排更偏 Graph / Chain / Workflow（Compose 层）；自主决策更偏 ChatModelAgent（ADK 层）。

2. Runner：单次执行入口

Runner 是单次 Agent 运行的入口。典型用法是：把 ChatModelAgent 放进配置，再 Query / Run，消费事件流。

它负责「这一跑」：是否流式、如何吐事件、如何与取消联动。

会话持久化不属于 Runner 职责——会话与消息的存储仍由应用侧完成。

3. Middleware：在循环节点注入行为

对应图中 ADK 的 Middlewares（如 FileSystem、Context Engineer）与 Agent Middleware。

Middleware 不改变 ReAct「推理 → 行动 → 反馈」的骨架，但可在关键节点注入行为，例如：

  • 调模型前压缩上下文
  • 动态注入工具
  • 工具调用权限校验
  • 失败重试 / 切换备份模型
  • Skill：按需把技能说明书加载进当前对话流

技能类能力可通过挂载在 ChatModelAgent 上的 skill middleware 实现，不必另起一套 Agent 协议。

4. 协作与预置形态

对应图中 Prebuilt 与协作相关原语：

  • Workflow Agents：Sequential / Parallel / Loop 等确定性流程
  • Supervisor / Plan-Execute：多 Agent 协作模式
  • DeepAgents：规划、文件系统、子 Agent 委派等
  • Agent Tool / Agent Transfer：把 Agent 封装为工具，或在 Agent 间转移控制权
  • Interrupt / Resume / Checkpoint：人机协同与断点恢复

ADK 面向的是 Agent 系统设计，而不仅是聊天补全封装。

落地时的职责边界

一种常见分层如下：

产品界面 / API
  → 业务服务（会话编排、鉴权、计费、附件）
  → 数据库（会话与消息的事实源）
  → Agent 运行时（Eino ChatModelAgent + Runner）
  → 模型网关

ADK 负责「这一轮 Agent 怎么执行」；不负责「会话事实存在哪」。

对照生命周期图：Eino / Eino-Ext / ADK 落在 Development & Debugging；账号、订单、计费、页面仍属于 User Code 与业务系统。对照分层图：Chat Model 等具体实现来自 Eino-Ext，ADK 只消费 Components 抽象。

落地时可关注这些边界：

  1. 1. Handler 不直接调用 ChatModel，统一走 Agent + Runner
  2. 2. 多轮上下文由业务库恢复，再转换成框架消息结构；避免把框架内部对象直接作为长期存储协议
  3. 3. 取消信号沿 context 传递，以便同时终止 Agent 与上游模型请求
  4. 4. 流式事件与最终事实分离：前端消费增量；持久化以数据库为准
  5. 5. 过滤事件类型：ADK 事件可能包含工具相关载荷；写入聊天正文前只保留助手可见输出

适用与不适用

适用：

  • 需要 ReAct、Tool、Skill、中间件扩展
  • 执行层需与会话存储、鉴权、计费解耦
  • 技术栈为 Go，并希望接入 Eino 模型适配器与组件生态
  • 需要预留多 Agent / 人机协同扩展空间

不适用或优先级较低：

  • 纯单次补全、无工具、无扩展预期 → 直接调 ChatModel 即可
  • 流程完全确定、不需要模型决定下一步 → Graph / 普通编排更合适
  • 主技术栈不是 Go，或已有成熟 Agent 框架 → 无必要仅为 ADK 换栈

选型依据是边界是否匹配，而非框架本身的优劣排序。
