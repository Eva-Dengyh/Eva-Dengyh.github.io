2. 核心问题：为什么需要适配器模式？

2.1 不同平台的消息协议差异

假设我们不用适配器模式，代码会变成这样：

# ❌ 噩梦般的耦合代码
async def handle_message(platform, message):
    if platform == "telegram":
        chat_id = message["message"]["chat"]["id"]
        text = message["message"]["text"]
        await send_telegram_message(chat_id, reply)
    
    elif platform == "discord":
        channel_id = message["d"]["channel_id"]
        content = message["d"]["content"]
        await send_discord_message(channel_id, reply)
    
    elif platform == "wechat":
        from_user = message["xml"]["FromUserName"]
        content = message["xml"]["Content"]
        await send_wechat_message(from_user, reply)
    
    # 加一个新平台 → 这里就要改代码 → 风险极大

2.2 适配器模式的核心思想

适配器 = 转换器。 每个平台的适配器负责两件事：

1. 接收：将平台特定格式 → 统一格式
2. 发送：将统一格式 → 平台特定格式
Telegram 消息格式                    统一消息格式
{"message": {"chat": {...}}}    →  {user_id, text, platform, ...}
                                      ↑
                                  Discord 适配器
{"d": {"channel_id": ...,        {user_id, text, platform, ...}
       "content": "..."}}
                                      ↑
                                  微信 适配器
{"xml": {"FromUserName": ...,    {user_id, text, platform, ...}
         "Content": "..."}}

2.3 适配器模式的好处

场景不用适配器用适配器
加新平台改 Gateway Core写新适配器文件，Core 不变
平台 API 升级改 Gateway Core只改适配器
适配器 Bug影响整个系统只影响该平台
测试需要真实 API可以 Mock 测试

3. 统一消息格式设计

3.1 统一消息对象的设计

Gateway Core 定义了一个与平台无关的消息格式：

# gateway/run.py 或 gateway/message.py

@dataclass
class UnifiedMessage:
    """所有平台适配器统一使用的消息格式。"""
    
    # 发送者信息
    user_id: str           # 用户唯一标识（在 Hermes 内部）
    platform: str          # 来源平台："telegram" / "discord" / ...
    
    # 消息内容
    text: str               # 消息文本
    attachments: List[Dict]  # 附件（图片/文件等）
    
    # 会话信息
    chat_id: str            # 平台原生的会话 ID
    thread_id: Optional[str]  # 话题 ID（支持 Discord thread 等）
    
    # 元数据
    message_id: str         # 平台原生的消息 ID（用于回复引用）
    timestamp: datetime      # 消息时间
    
    # 特殊标记
    is_bot_command: bool     # 是否是 slash 命令（如 /help）
    raw: Any                 # 平台原生消息体（保留原始数据）

3.2 统一消息的生命周期

消息进来 → 适配器解析 → UnifiedMessage
    │
    │  Gateway Core 处理
    │
    ▼
AIAgent.run_conversation(message.text)
    │
    │  AIAgent 返回回复
    │
    ▼
回复（统一格式）
    │
    │  适配器发送
    │
    ▼
平台原生消息格式 → 发送到用户

4. Telegram 适配器详解

4.1 Telegram Bot 的工作原理

Telegram Bot 使用 Long Polling 方式接收消息：

Hermes  ──HTTP GET──▶  Telegram Server
◀──等待中（最多几十秒）───
        │
        │ 有新消息
        ▼
◀──返回新消息列表────────
        │
        ▼
Hermes 处理消息
        │
        ▼
Hermes ─-HTTP POST──▶  Telegram Server  ──▶ 用户手机

Long Polling = 客户端一直问服务器"有没有新消息"，服务器等到有消息才返回。

4.2 Telegram 适配器的核心逻辑

# gateway/platforms/telegram.py（简化版）

class TelegramAdapter:
    def __init__(self, bot_token: str):
        self.bot_token = bot_token
        self.api_url = f"https://api.telegram.org/bot{bot_token}"
    
    # ========== 接收消息（Long Polling）==========
    
    async def get_updates(self, offset: int = None, timeout: int = 30):
        """
        从 Telegram 获取新消息。
        这是适配器的"耳朵"。
        """
        params = {"timeout": timeout, "allowed_updates": "message"}
        if offset:
            params["offset"] = offset
        
        response = await self._http_get(f"{self.api_url}/getUpdates", params)
        return response["result"]
    
    async def handle_updates(self):
        """
        主循环：持续获取并处理新消息。
        """
        update_id = 0
        while True:
            updates = await self.get_updates(offset=update_id)
            
            for update in updates:
                # 1. 解析 Telegram 原生格式
                tg_message = update["message"]
                
                # 2. 转换成统一格式
                unified = self._to_unified(tg_message)
                
                # 3. 交给 Gateway Core 处理
                await gateway_core.on_message(unified)
                
                # 4. 更新 offset（防止重复处理）
                update_id = update["update_id"] + 1
    
    # ========== 发送消息 ==========
    
    async def send_message(self, chat_id: int, text: str, reply_to=None):
        """
        发送消息给用户。
        这是适配器的"嘴"。
        """
        payload = {
            "chat_id": chat_id,
            "text": text,
            "parse_mode": "Markdown",
        }
        if reply_to:
            payload["reply_to_message_id"] = reply_to
        
        await self._http_post(f"{self.api_url}/sendMessage", payload)
    
    # ========== 格式转换 ==========
    
    def _to_unified(self, tg_message: dict) -> UnifiedMessage:
        """
        Telegram 格式 → 统一格式。
        """
        return UnifiedMessage(
            user_id=str(tg_message["from"]["id"]),
            platform="telegram",
            text=tg_message.get("text", ""),
            chat_id=str(tg_message["chat"]["id"]),
            message_id=str(tg_message["message_id"]),
            timestamp=datetime.fromtimestamp(tg_message["date"]),
            is_bot_command=tg_message.get("text", "").startswith("/"),
            raw=tg_message,
        )

5. Gateway Core：消息分发与路由

5.1 Gateway Core 的职责

Gateway Core（gateway/run.py）是整个 Gateway 的心脏：

┌─────────────────────────────────────────────┐
│            Gateway Core (run.py)            │
│                                             │
│  职责1：管理 Session                          │
│    - 用户第一次发消息 → 创建新 Session         │
│    - 用户继续发消息 → 找到已有 Session         │
│    - 保存会话历史到 SQLite                    │
│                                             │
│  职责2：路由消息                              │
│    - 普通消息 → 发给 AIAgent                  │
│    - Slash 命令 → 调用对应命令处理器           │
│                                             │
│  职责3：管理 Agent 实例                       │
│    - 每个 Session 对应一个 AIAgent            │
│    - 控制 Agent 的生命周期                    │
└─────────────────────────────────────────────┘

5.2 Session 管理

Session = 一段完整的对话上下文。

# gateway/session.py

class SessionStore:
    """
    管理所有会话。
    每个 chat_id + platform 组合对应一个 Session。
    """
    
    def __init__(self, db_path: str):
        self.db = sqlite3.connect(db_path)
        self._sessions: Dict[str, AIAgent] = {}
        # 内存缓存：session_id → AIAgent 实例
    
    def get_or_create_session(
        self,
        platform: str,
        chat_id: str,
        user_id: str,
    ) -> tuple[str, AIAgent]:
        """
        获取或创建 Session。
        返回 (session_id, agent_instance)。
        """
        session_id = f"{platform}:{chat_id}:{user_id}"
        
        if session_id not in self._sessions:
            # 创建新 Session
            self._sessions[session_id] = AIAgent(
                session_id=session_id,
                platform=platform,
            )
            # 从 SQLite 恢复历史（如果有）
            self._load_history(session_id)
        
        return session_id, self._sessions[session_id]
    
    def save_session(self, session_id: str):
        """把 Session 状态保存到 SQLite"""
        agent = self._sessions.get(session_id)
        if agent:
            messages = agent.get_conversation_history()
            self.db.execute(
                "INSERT OR REPLACE INTO sessions VALUES (?, ?, ?)",
                (session_id, json.dumps(messages), datetime.now())
            )
            self.db.commit()

5.3 消息路由

# gateway/run.py（简化版）

async def on_message(unified: UnifiedMessage):
    """
    处理一条统一格式的消息。
    这是 Gateway Core 的主入口。
    """
    
    # ========== Step 1：处理 Slash 命令 ==========
    if unified.is_bot_command:
        command = unified.text.split()[0][1:]  # "/help" → "help"
        await handle_slash_command(command, unified)
        return
    
    # ========== Step 2：获取或创建 Session ==========
    session_id, agent = session_store.get_or_create_session(
        platform=unified.platform,
        chat_id=unified.chat_id,
        user_id=unified.user_id,
    )
    
    # ========== Step 3：发给 AIAgent ==========
    response = await agent.run_conversation(unified.text)
    
    # ========== Step 4：把回复发回平台 ==========
    await platform_adapter.send_message(
        chat_id=unified.chat_id,
        text=response,
    )
    
    # ========== Step 5：保存 Session ==========
    session_store.save_session(session_id)

6. Session 管理：会话持久化

6.1 为什么需要持久化？

没有持久化时：

用户关掉手机 → Hermes 重启 → 用户再打开 → Hermes 不认识他了

有持久化时：

用户关掉手机 → Hermes 保存 Session 到 SQLite → 重启
用户再打开 → 从 SQLite 恢复 Session → 继续对话，像没断过一样

6.2 SQLite 存储结构

CREATE TABLE sessions (
    session_id  TEXT PRIMARY KEY,    -- "telegram:123456:user789"
    messages    TEXT,                 -- JSON 格式的对话历史
    updated_at  TEXT                  -- 最后更新时间
);

CREATE VIRTUAL TABLE sessions_fts 
USING fts5(session_id, messages);
-- FTS5 = 全文搜索索引，用于"搜索历史对话"

6.3 完整的 Session 生命周期

用户发消息 ①
    │
    ▼
SessionStore.get_or_create_session()
    │ session 存在？──是──▶ 从 SQLite 读消息历史
    │                   │
    │                   ▼
    │                重建 AIAgent.messages
    │
    └──不存在？──▶ 创建新 AIAgent，messages = []
    │
    ▼
AIAgent.run_conversation(message.text)
    │
    ▼
回复给用户，同时：
    │
    ▼
session_store.save_session()
    │
    ▼
messages[] → JSON → SQLite.updated_at

8. Slash 命令处理

8.1 什么是 Slash 命令？

在 Telegram/Discord 中，用户输入 /help、/model 等命令，Hermes 需要特殊处理，而不是当作普通消息发给 AI。

8.2 Slash 命令处理流程

async def on_message(unified: UnifiedMessage):
    
    # 检测是否是 Slash 命令
    if unified.is_bot_command:
        # "/model claude-3" → ("model", ["claude-3"])
        parts = unified.text.split()
        command_name = parts[0][1:]  # 去掉 /
        command_args = parts[1:]
        
        # 从命令注册表找到处理器
        handler = COMMAND_REGISTRY.get(command_name)
        
        if handler:
            await handler(unified, *command_args)
        else:
            await platform_adapter.send_message(
                unified.chat_id,
                f"Unknown command: /{command_name}\nUse /help for available commands."
            )
        
        return  # Slash 命令不走 AIAgent
    
    # 普通消息 → 走 AIAgent
    ...

# 每个命令有自己的处理器
async def handle_model_switch(unified, *args):
    """切换 AI 模型"""
    if not args:
        return await send(unified.chat_id, "Usage: /model <model_name>")
    
    new_model = args[0]
    session_store.set_model(unified.session_id, new_model)
    await send(unified.chat_id, f"Model switched to {new_model}")
