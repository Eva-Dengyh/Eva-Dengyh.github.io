第一章：Hermes 是什么？

一句话定义：

Hermes Agent 是由 Nous Research 构建的自改进式 AI Agent 框架。它是目前最完整的开源 Agent 方案之一，集成了多平台接入、持久记忆、技能进化、子 Agent 并行执行等能力。

你能用它做什么：

在终端里跟它聊天                    ✅
在 Telegram 里跟它聊天              ✅
在 Discord 里跟它聊天               ✅
在微信里跟它聊天                    ✅
让它帮你读写文件、搜索网页、跑代码     ✅
让它记住你说过的重要事情              ✅
让它从错误里学习，下次做得更好         ✅
设置定时任务让它自动执行              ✅
同时做多件独立的事（子Agent）         ✅
切换到任何一个 LLM 模型              ✅
把它部署在云端，省电省钱              ✅

为什么叫"Hermes"？

Hermes（赫尔墨斯）是希腊神话中的信使之神，速度最快、消息最灵通。这个名字恰好对应了 Agent 的两个核心能力：传递消息和快速响应。

第二章：为什么 Hermes 能火？

2.1 2024-2025 年 AI Agent 市场背景

市场上大多数 AI Agent 产品存在以下痛点：

竞品问题Hermes 的解决方案
绑定单一模型（只能用 Claude 或 GPT）一个配置切换任意模型，不改代码
绑定单一平台（只能 Telegram 或只能 Discord）一个 gateway 接所有主流聊天平台
每次对话都是全新开始，不记得之前的事持久记忆 + Skills 跨会话积累
功能固定，无法扩展新能力60+ 内置工具 + MCP 扩展协议
占用资源，常驻运行成本高Daytona/Modal 云端休眠，近零空闲成本
闭源，不可定制完全开源 MIT 协议

2.2 Hermes 的核心差异化

你想要的                        Hermes 做到的
─────────────────────────────────────────────────────
换模型（Claude → GPT → 开源模型）    ✅ 一个 /model 命令，秒级切换
换平台（终端 → Telegram → 微信）     ✅ 一个 gateway，配置即接
Agent 记住重要信息                  ✅ 跨会话持久记忆
Agent 学会新技能                   ✅ Skills 系统，经验可复用
后台自动跑任务                      ✅ Cron 定时任务，自然语言配置
同时做多件事                       ✅ 子 Agent 并行执行
省成本（不用时休眠）                ✅ Daytona/Modal 云端休眠，近零费用
本地运行，保护隐私                  ✅ 全开源，可私有化部署
─────────────────────────────────────────────────────

2.3 技术亮点

Hermes 的多个模块在各自领域达到了行业领先水平：

  • 记忆系统：基于 SQLite FTS5 的全会话历史搜索 + LLM 摘要
  • Skills 系统：Agent 驱动的自动经验提取和复用
  • 上下文压缩：智能摘要式压缩，不丢失关键信息
  • 终端后端：支持本地/Docker/SSH/Daytona/Modal/Singularity 六种后端
  • MCP 集成：支持接入任何 Model Context Protocol 外部工具服务器

第四章：核心模块设计详解

Hermes 的架构围绕三个核心问题展开：

问题1：工具越来越多，怎么管理？       → 注册表模式（Registry Pattern）
问题2：模型越来越多，怎么切换？       → Provider 抽象层
问题3：功能越来越多，代码怎么改？      → 插件化（Plugins）+ Skills

第五章：工具系统（注册表模式）

5.1 问题背景

  • Hermes 内置 60+ 工具，且支持通过 MCP 动态扩展
  • 工具数量持续增长，代码不能因此变得混乱
  • 不同工具有不同的依赖（有的要 API Key，有的是纯本地文件操作）
  • 工具需要按平台启用/禁用（比如某些敏感工具只在 CLI 模式开启）

5.2 三层架构

第1层：定义层（每个工具文件）
  tools/file_tools.py  ─┐
  tools/terminal_tool.py ─┼─ 每个文件末尾调用 registry.register()
  tools/web_tools.py    ─┘

第2层：注册中心（tools/registry.py）
  唯一真相来源：_registry[name] = ToolEntry(...)
  提供 register() / get() / dispatch() 三个接口

第3层：分发层（model_tools.py）
  handle_function_call(name, args)
  根据 name 找到 registry entry，调用 handler，返回 JSON 字符串

5.3 工具的注册过程

每个工具文件（例如 todo_tool.py）的结构如下：

# ============ 第1步：定义 Schema（给 AI 模型看的说明书）============

TODO_SCHEMA = {
    "name": "todo",
    "description": (
        "管理任务清单。..."
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "todos": {
                "type": "array",
                "description": "任务列表..."
            },
            "merge": {
                "type": "boolean",
                "description": "是否合并..."
            }
        },
        "required": []
    }
}

# ============ 第2步：实现 Handler（真正做事的 Python 函数）============

def todo_tool(todos=None, merge=False, store=None):
    # ... 实际逻辑 ...
    return json.dumps({"todos": current_list})

# ============ 第3步：注册到全局注册表（末尾调用一次即可）============

registry.register(
    name="todo",                    # 工具名
    toolset="todo",                 # 属于哪个工具组
    schema=TODO_SCHEMA,              # Schema 说明书
    handler=lambda args, **kw: todo_tool(...),  # 执行函数
    check_fn=check_todo_requirements,  # 可用性检查
    emoji="📋",                      # UI 图标
)

关键洞察：Schema 和 Handler 完全分离

  • Schema 是"说明书"，给 AI 模型看，告诉它这个工具叫什么、接受什么参数、做什么
  • Handler 是"执行者"，真正的 Python 逻辑
  • 改 Schema 不影响 Handler，反之亦然

5.4 工具发现机制

工具的加载是全自动的，发生在 model_tools.py 导入时：

def _discover_tools():
    """Import all tool modules to trigger their registry.register() calls."""
    _modules = [
        "tools.todo_tool",
        "tools.file_tools",
        "tools.terminal_tool",
        "tools.web_tools",
        # ... 60+ 个模块
    ]
    for mod_name in _modules:
        importlib.import_module(mod_name)  # 导入时自动注册

_discover_tools()  # 模块加载时立即执行

这意味着：新增一个工具 = 新增一个 Python 文件 + 在底部写一行注册代码，零配置。

5.5 工具集（Toolset）分组

工具按功能分组，每组可以整体启用/禁用：

toolset "file"      → read_file, write_file, patch, search_files
toolset "terminal"  → terminal, process (background process)
toolset "web"       → web_search, browser_navigate, browser_snapshot
toolset "delegate"  → delegate_task (子 Agent)
toolset "session"  → session_search (跨会话搜索)
toolset "skills"    → skill_view, skill_manage, skills_list

用户通过 hermes tools 命令可以按组配置，不需要一个个工具单独设置。

第六章：消息网关（适配器模式）

6.1 问题背景

不同的聊天平台有完全不同的消息协议：

Telegram：     通过 Bot API (HTTP Long Polling)
Discord：      通过 WebSocket Gateway API
Slack：        通过 WebSocket + HTTP
WhatsApp：     通过 Baileys/Meta 官方 API
Email：        通过 IMAP/SMTP

如果核心代码直接写每个平台的处理逻辑，加一个新平台就要改核心代码，风险极大。

6.2 适配器模式架构

                        统一消息格式
                         ▲
                         │ Gateway Core (run.py)
                         │
┌────────────────────────┼─────────────────────────────────────────────┐
│                        │                                             │
│    ┌───────────────────┴───────────────────┐                         │
│    │                                       │                         │
│    ▼                                       ▼                         │
│  Telegram 适配器                        Discord 适配器                  │
│  platform/telegram.py                   platform/discord.py           │
│                                         │                             │
│  解析 Telegram API                      解析 Discord WebSocket         │
│  → 统一消息                             → 统一消息                     │
│                                         │                             │
│  发送：统一回复                         发送：统一回复                 │
│  → Telegram API                         → Discord API                │
└───────────────────────────────────────────────────────────────────────┘

统一消息格式（Gateway Core 定义）：

class UnifiedMessage:
    user_id: str          # 用户唯一标识
    platform: str         # "telegram" / "discord" / ...
    text: str             # 消息文本
    attachments: list      # 图片/文件等附件
    chat_id: str          # 会话 ID
    thread_id: str | None # 话题 ID（支持 Discord thread 等）
    timestamp: datetime   # 时间戳

6.3 为什么这样设计好？

  • 新平台接入：只需要新写一个适配器文件（约 500-1000 行），核心 run.py 一行不用改
  • 独立演进：每个平台适配器可以独立测试、独立升级
  • 故障隔离：某个平台适配器崩溃不影响其他平台和核心

第七章：AI 循环核心（ReAct 模式）

7.1 什么是 ReAct？

ReAct = Reason + Act。这是目前 AI Agent 最主流的设计模式：

Reason（思考）：AI 模型分析当前情况，决定下一步做什么
Act（行动）：   AI 模型调用工具执行

交替进行，直到任务完成

7.2 Hermes 的 AI 循环流程

┌─────────────────────────────────────────────────────────────┐

│      │      │      role:"tool",                          │  │

7.3 为什么需要循环？

因为复杂任务不可能一步完成。例如：

用户："帮我分析 /project 目录的代码，写一份报告"

AI 第1轮思考："我需要先看看目录里有哪些文件"
  → tool_call: terminal("ls -la /project")

AI 第2轮思考："好，我看到有 main.py, utils.py, tests/ 等"
  → tool_call: read_file("main.py")
  → tool_call: read_file("utils.py")

AI 第3轮思考："文件内容读完了，我来写报告"
  → 最终回复（无 tool_call，break 出去）

7.4 循环控制：iteration_budget

防止 AI 无限循环调用工具，设置最大迭代次数：

class IterationBudget:
    max_total = 90        # 最多 90 次 API 调用
    remaining = max_total

    def consume(self) -> bool:
        """返回 False 表示预算耗尽，强制退出"""
        if self.remaining <= 0:
            return False
        self.remaining -= 1
        return True

场景： 如果 AI 的工具返回了错误（比如网络超时），AI 可能反复重试同一个工具。预算耗尽后强制退出，防止无限循环。

7.5 上下文太长怎么办？

如果对话历史越来越长，接近模型的上下文上限，触发上下文压缩：

压缩前：
messages = [系统提示词, 用户问题1, AI回答1, 用户问题2, AI回答2, ... 100轮...]

压缩后：
messages = [
    系统提示词,
    [摘要: 前50轮对话的核心信息],
    最近10轮完整对话  ← 总是保留最新的对话
]

压缩策略（context_compressor.py）：

  • 保护最新：最近 N 轮对话从不压缩
  • 摘要中间：早期对话用 LLM 生成摘要，保留要点
  • 重新计数：压缩后重新估算 token 数量，确保在限制内

第八章：提示词构建（分层组装）

8.1 问题背景

AI 模型本身是通用的（GPT-4、Claude 都不知道自己是谁）。要让模型"变成"Hermes，需要通过系统提示词赋予它身份、能力、偏好和上下文。

8.3 prompt_builder.py 的职责

prompt_builder.py 负责动态组装以上各层，根据以下因素决定包含什么：

def _build_system_prompt(self) -> str:
    layers = []

    # 第1层：基础身份
    layers.append(self._get_identity_block())

    # 第2层：工具列表（只包含当前启用的工具）
    layers.append(self._get_tools_block())

    # 第3层：用户偏好（从 memory 读取）
    if self.memory_enabled:
        layers.append(self._get_user_preferences_block())

    # 第4层：当前上下文
    layers.append(self._get_context_block())

    # 第5层：Skills 指令
    layers.append(self._get_skills_block())

    return "\n\n".join(layers)

第九章：记忆与 Skills 系统

9.1 普通记忆 vs Skills

普通记忆（Memory）         → 存储事实（"用户叫 Eva"）
Skills                   → 存储经验（"遇到 X 类型问题，用 Y 方法解决"）

9.3 Skills 系统工作原理

Skills 是 Hermes 最独特的创新。 它的核心理念是：

"与其告诉 Agent 怎么做事，不如让它自己学会怎么做事。"

用户让 Hermes 完成一个复杂任务
  → Hermes 执行完成
  → Hermes 问自己："我应该把这次经验记成一个 Skill 吗？"
  → 如果值得记住：
      创建 ~/.hermes/skills/my-skill/SKILL.md
      内容包括：
        - 这个 Skill 在什么场景下触发
        - 具体操作步骤
        - 注意事项和陷阱
  → 下次遇到同类任务：
      Hermes 自动检索相关 Skill → 加载步骤 → 执行

Skills 的存储格式（Markdown）：

# python-debug

## 触发条件
当用户描述了 Python 错误、异常、或要求"帮我调试"时触发。

## 操作步骤
1. 首先让用户提供完整的错误信息
2. 使用 terminal_tool 运行出错命令，获取完整 stack trace
3. 分析错误类型：
   - SyntaxError → 检查拼写和缩进
   - ImportError → 检查包是否安装、路径是否正确
   - IndexError  → 检查列表边界
4. 根据错误类型逐一排查
5. 提供修复方案和修改后的代码

## 注意事项
- 不要在看到完整错误前就猜测原因
- stack trace 从下往上看，找到第一个 ERROR 行

9.4 Skills 检索和调用

当用户描述一个任务时，Hermes 自动：

  1. 1. 检索 — 在 Skills 目录里搜索相关的 Skill
  2. 2. 加载 — 找到后把 Skill 的 Markdown 内容注入提示词
  3. 3. 执行 — 按照 Skill 里的步骤操作

第十章：模型抽象层（Provider 模式）

10.1 问题背景

市场上有几十种 LLM 提供商，API 格式和认证方式各不相同。如果代码直接写死某个 API，切换模型就要改大量代码。

10.2 Hermes 的解决方案

Hermes 代码里只使用 OpenAI 兼容格式：

from openai import OpenAI

client = OpenAI(
    api_key="sk-xxx",
    base_url="https://api.anthropic.com"  # 可以指向任何兼容端点
)

# 这个调用格式，可以是：
#   - Claude（通过 Anthropic 或 OpenRouter）
#   - GPT-4（原生 OpenAI）
#   - 任何 OpenRouter 支持的 200+ 模型
#   - 本地 Ollama 模型
client.chat.completions.create(
    model="claude-3-opus",
    messages=[...],
    tools=[...]
)

第十一章：架构好在哪里？

11.1 评价架构的四个维度

可维护性：加功能需要改多少代码？

新增一个工具        → 新建 1 个 Python 文件 + 1 行注册代码
新增一个平台适配器   → 新建 1 个适配器文件
新增一个模型支持    → 改配置，不改代码
修复工具 Bug        → 只改该工具文件
核心重构            → 工具和适配器都不受影响

可测试性：每个模块能单独测吗？

工具函数           → ✅ 可以单独写单元测试
注册表             → ✅ 可以注册假工具后测试分发逻辑
适配器             → ✅ 可以 Mock 测试，不依赖真实 API
prompt_builder     → ✅ 可以构造不同配置测试输出

可扩展性：能跑在更多地方吗？

终端后端：        本地 / Docker / SSH / Daytona / Modal / Singularity
消息平台：        Telegram / Discord / Slack / WhatsApp / Signal / Email
外部扩展：        MCP（Model Context Protocol）支持任意外部工具服务器

灵活性：能关掉不需要的部分吗？

工具集（toolsets）  → 按组启用/禁用
平台适配器          → 配置文件开关
记忆系统            → 可关闭（节省资源）
Skills 系统         → 可关闭

12.1 按使用频率排行

12.2 最独特的功能：Skills 自进化

这是 Hermes 与其他所有 Agent 框架最大的区别。

传统 Agent：

用户每次遇到同类问题 → 都要重新描述一遍 → Agent 每次重新摸索

Hermes（带 Skills）：

第1次遇到问题 → Agent 解决 → 判断值得记住 → 存入 Skill
第2次遇到同类问题 → Agent 自动找到 Skill → 直接套用经验
第N次 → Skill 越来越完善，Agent 越来越专业

这意味着 Hermes 真正实现了"学习"——不是模型参数的学习，而是经验知识的积累。

12.3 最实用的功能：多平台统一

大多数用户的真实工作流：

在地铁上（微信）     → 发一条消息给 Hermes："帮我看看代码有没有 Bug"
到公司（电脑）        → 打开终端 → 继续同一个对话，Hermes 已经记住了任务
下班路上（Telegram）  → 再发一条："帮我写个报告总结今天的发现"
回家（躺在床上）      → 语音问 Hermes："今天完成了什么？"

整个过程是连续的，同一个 Agent、同一个记忆系统、同一个 Skills 积累。
