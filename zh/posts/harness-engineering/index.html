AI 与智能体

Harness Engineering：让 AI Agent 真正可用的工程原则

Eva·2026.04.22·20 分钟阅读

 

 

Agent = Model + Harness

理解 Harness Engineering，从一个定义开始：

Agent = Model + Harness

Model 是智能的来源，Harness 是让这个智能变得有用的系统。反过来说也成立：如果某个组件不是 Model 本身，它就是 Harness 的一部分。

一个裸模型不是 Agent。它接受文本、图像、音频作为输入，输出文本。仅此而已。它开箱即用时无法维持跨 Session 的持久状态、无法执行代码、无法访问实时知识、无法搭建环境完成工作。Harness 的作用就是在 Model 之外构建这些能力。

Harness 的组成包括：

  • System Prompts：注入初始指令和上下文
  • Tools、Skills、MCPs：给 Model 可调用的能力接口
  • 基础设施：文件系统、沙盒、浏览器等执行环境
  • 编排逻辑：子 Agent 调度、任务分发、模型路由
  • Hooks / Middleware：检查点、Lint、压缩等确定性执行层

从 Model 的局限推导 Harness 的结构

Harness 的每一个组件，都可以从"我们希望 Agent 做到什么、但裸 Model 做不到"这个问题反推出来。

文件系统：最基础的 Harness 原语

Model 只能直接操作当前上下文窗口内的信息。在有文件系统之前，向 Model 提供数据的方式是把内容直接粘贴进对话，这在自治 Agent 场景下完全不可行。

文件系统是 Harness 中最核心的原语，因为它解锁了一系列上层能力：

  • Agent 有了工作区，可以读取代码、数据、文档
  • 中间产物可以增量写入和读取，不需要把所有内容都撑在上下文里
  • 任务状态可以跨 Session 持久化
  • 多个 Agent 或人类可以通过共享文件协作，文件系统天然是协作界面
  • 加上 Git，Agent 可以追踪变更、回滚错误、并行实验

Bash + 代码执行：通用工具

今天主流的 Agent 执行模式是 ReAct 循环：Model 推理 → 调用工具 → 观察结果 → 继续推理。但 Harness 只能执行它预置了逻辑的工具，如果为每种可能的操作都预先设计工具，工程成本极高且灵活性极差。

给 Agent 一个 Bash 工具是更好的解法——Model 可以通过写代码来设计自己需要的工具，而不是被一组固定的预配置工具所限制。代码执行已经成为自治问题求解的默认通用策略。

沙盒：安全的执行环境

有了文件系统和代码执行能力，还需要一个地方来运行它们。在本地执行 Agent 生成的代码存在安全风险，且单一本地环境无法支撑大规模并发的 Agent 任务。

沙盒让 Agent 在隔离环境中运行代码、检查文件、安装依赖。Harness 负责决定 Agent 在哪里运行、能访问什么、可以执行哪些命令。这些全是 Harness 层的设计决策，Model 本身不能配置自己的执行环境。

沙盒还解锁了规模化：执行环境可以按需创建、并行分发、任务完成后销毁。

Memory 与搜索：对抗知识局限

Model 的知识被锁定在训练权重里，上下文之外的信息对它不可见。解决方法是上下文注入。

文件系统在这里再次发挥作用。AGENTS.md 等记忆文件标准让 Agent 可以在会话间积累和传递知识：Agent 把当前 Session 学到的内容写入文件，下一个 Session 开始时 Harness 把文件注入上下文，形成一种持续学习机制。

对于训练截止日期之后的实时知识，Web Search 和 Context7 等 MCP 工具让 Agent 可以访问最新的库版本、当前数据等训练时不存在的信息。

两个核心工程挑战

Context Rot（上下文腐烂）

Agent 性能不应该随着工作时间的延长而下降，但实际上会。这个现象叫 Context Rot：随着上下文窗口填满，模型的推理质量和任务完成能力持续下降。

Harness 需要专门的机制来对抗 Context Rot：

压缩（Compaction）：当上下文窗口接近上限时，Harness 需要有策略地对现有上下文进行摘要和卸载，让 Agent 可以继续工作而不是因 API 报错中断。

工具调用输出截断：大型工具返回值会把上下文窗口填满，但往往真正有用的信息只在头部和尾部。Harness 保留输出的首尾 Token，把完整输出卸载到文件系统，需要时再按需读取。

Skills 的渐进式披露：一次性把所有工具和 MCP Server 加载进上下文会在 Agent 开始工作前就消耗大量 Token。Skills 通过渐进式披露解决这个问题：只在需要时把相关 Skill 的元数据注入上下文。

这些机制的共同逻辑是：上下文是稀缺资源，Harness 是上下文工程的执行层。

Long Horizon Execution（长时自治执行）

让 Agent 在较长时间内自治地完成复杂任务，是当前 Agent 工程的核心挑战之一。裸 Model 面临的问题包括：过早退出、无法分解复杂问题、跨多个上下文窗口后的行为不一致。

Ralph Loop：一种 Harness 模式，通过 Hook 拦截 Model 的退出尝试，在一个全新的上下文窗口里重新注入原始任务目标，强制 Agent 继续推进，直到达成完成条件。文件系统使这个模式成为可能——每次迭代都以干净的上下文开始，但从文件系统读取上一次的状态。

规划与自验证：Harness 通过 Prompt 注入和文件系统支持让 Agent 把目标分解成步骤，完成每一步后对产出做验证（运行测试、检查日志、对比预期结果）。测试结果和错误信息作为反馈信号回传给 Model，形成自我修正闭环。

Design by Contract：Harness 的约束层

除了能力供给（给 Model 它需要的工具和环境），Harness 还需要一套约束层来管理 Model 的非确定性行为。

LLM 的每一步输出是概率采样的结果，行为对上下文极度敏感。更关键的是，Prompt 中的约束在工程意义上是软性的：

  • 注意力稀释：随着对话轮次增加，System Prompt 中的约束条目在整个上下文中的权重持续下降
  • 物理截断：上下文窗口填满时，最早写入的内容（通常是约束规则）最先被丢弃
  • 无执行语义：自然语言指令对 Model 的约束是概率性的，不是强制性的

Harness 的约束层用 Design by Contract 的框架来理解最为清晰：

前置条件（Pre-conditions）：在 Model 进入高影响操作前，Harness 强制插入检查点。Model 必须输出结构化的执行意图（目标、范围、副作用、验证方式），由外部逻辑（不是 Model 自己）做验证，验证通过后才放行。关键在于验证逻辑在 Model 外部。

后置条件（Post-conditions）：操作完成后，Harness 要求从外部系统收集验证证据——单测结果、运行时日志、接口回包、文件系统 diff。这些证据回传给 Model 作为下一轮输入，把 Model 从"自评估"模式切换到"证据驱动"模式。

不变式（Invariants）：维护一份外部状态文档，记录任务目标、已完成工作及验证证据、技术决策和原因、遗留问题。Model 的内部 Context 随时可能消失，但这份文档是任务的唯一真相源，任何 Session 都可以从它恢复状态。

Capability 设计：收窄 Model 的决策空间

Harness 解决执行边界问题，Capability 设计解决能力边界问题。

给 Model 暴露粒度过细的工具会带来两个问题：工具组合空间过大导致决策难以验证；工具间的依赖和副作用没有封装，任何一步错误都可能产生连锁影响。

更好的做法是把工具封装成业务语义明确的 Capability：

# 暴露基础工具：Model 需要自己组合和判断副作用
tools = [read_file, write_file, run_sql, call_api, ...]

# 封装成 Capability：Model 只需选择业务操作
capabilities = [
    update_user_profile,    # 内部封装校验、写库、缓存失效
    run_regression_suite,   # 内部封装环境准备、执行、结果收集
    deploy_to_staging,      # 内部封装构建、推送、健康检查
]

每个 Capability 内部包含自己的 Validator，Model 的决策单元从"调哪个 API、传什么参数"变成"选择哪个业务操作"。决策空间越小，验证越容易，失控风险越低。

识别错误的 Harness 设计

在讨论如何正确构建 Harness 之前，有必要先区分两类不同性质的问题：根本没有 Harness，和Harness 质量差。这两类问题的表现形式不同，解决路径也完全不同。

根本没有 Harness

这类设计的共同特征是：Model 之外没有物理约束，所有控制都依赖模型内部的"自我约束"。

软约束陷阱：在 System Prompt 里堆砌大量规则和禁止项，期望 Model 自觉遵守。这本质上是把执行边界的控制权交给了概率引擎本身。规则越长，在长链路中被稀释和遗忘的概率越高，且没有任何外部机制能保证这些规则在任意时刻都被执行。

工具边界缺失：给 Model 暴露大量细粒度工具而不设定使用边界，Model 的工具选择完全依赖其推理判断。这不只是 Capability 设计问题，更是 Harness 层面的失控——没有任何机制能在危险工具调用发生前介入。

这两种情况都不构成 Harness，因为控制面不在 Model 外部。

Harness 存在但质量差

这类设计已经有外部控制流，但控制方式引入了新的问题。

裸循环重试：检测到错误后，把错误信息直接塞回 Model 上下文，让它不断重试。这确实是外部控制，但没有在重试前重新对齐目标和边界。Model 在这种循环中会朝它认为能消除报错的方向收敛，而不是朝正确的解决方案收敛——修语法错的代价可能是删掉整个模块。有效的重试需要在每次循环前强制 Model 重新复述当前目标，确认修复范围，而不是裸奔地继续执行。

过重的文档前置：强制 Model 在执行任何操作前先生成大量设计文档，把文档产出当作执行授权的前置条件。这是状态管理的一种形式，但文档的粒度和时机如果不对，会带来两个代价：大量 Token 消耗在文档生成上，以及文档一旦与实际执行脱节就变成无法维护的负担。状态管理的目标是轻量、可持续同步的真相源，而不是重型的一次性文档。

区分这两类问题的意义在于：前者需要的是引入 Harness，后者需要的是改进 Harness 的设计质量。把两者混为一谈，会导致错误地用"加更多文档"来解决"根本没有外部约束"的问题，或者用"完全去掉控制"来回避"控制太粗暴"的问题。

长任务中的目标层级管理

在 Long Horizon Execution 场景中，除了 Ralph Loop 和规划机制，还有一个容易被忽视的运行时问题：Model 倾向于绕过当前阶段的具体目标，直接向它理解的总目标推进。

这在行为上表现为：任务执行表面上很活跃，但每一步都在尝试一次性解决所有问题，而不是按照分解后的步骤逐步推进。结果是链路越长，实际偏离既定计划越远。

有效的 Harness 需要在运行时维护三个层级的目标，并保持它们之间的隔离：

总目标：整个任务或当前大阶段的完成标准。这是锚点，不随单轮执行的结果改变。

阶段目标：当前若干轮对话允许处理的问题范围。一个阶段结束前，禁止 Model 把下一阶段的内容纳入当前执行范围。

本轮动作目标：当前单次执行允许的操作数量和边界，通常控制在 1-3 个具体动作以内。

这三个层级的关键约束是：阶段完成不等于总目标完成。当一个阶段收敛后，Harness 需要显式地把这个结论同步给 Model，而不是让 Model 自行判断是否可以继续推进下一阶段。

运行时目标重定义

目标层级不是在任务开始时一次性确定就不变的。当执行过程中的外部证据（测试失败、日志异常、接口报错）与当前阶段目标冲突时，阶段目标需要被重新定义。

这个重定义不是对计划的否定，而是 Harness 响应真实反馈的正常机制。典型的场景是：原计划的阶段目标是"完成 X 功能"，但运行时日志显示某个依赖链路存在系统性问题，此时阶段目标应该收窄为"先定位链路问题的根因"，等问题被解决并通过验收后，再重新推进原有阶段目标。

Harness 在这里的作用是提供触发重定义的外部证据，以及在重定义后强制 Model 确认新的阶段边界，防止它在新目标下又立刻滑向总目标的方向。

Harness 在单轮执行中的控制节点

理解 Harness 的架构设计是一回事，理解它在实际执行节奏中如何体现是另一回事。一个完整的执行回合，Harness 的控制逻辑会在以下几个关键节点发挥作用。

节点一：目标收敛，先于任何实现

任务开始时，Harness 的第一个控制点不是让 Model 立即执行，而是让它先复述对任务的理解——它看到的总目标是什么、当前阶段的主线是什么、边界和疑问在哪里。

这一步的工程价值在于：它是对 Model 意图的显式提取，暴露出 Model 对任务理解的偏差，在任何代码被写出之前就完成纠正。跳过这个节点，后续执行越快，偏离越难察觉。

节点二：最小 Spec，锁定本轮范围

目标收敛之后，不直接进入实现，而是先要求 Model 输出一份轻量的执行 Spec：本轮目标是什么、范围边界在哪里、明确不处理哪些内容、验证方式是什么。

这份 Spec 的核心作用是防止 Model 把上层目标"偷渡"进当前轮次。没有显式的范围边界，Model 在执行过程中会自然地向总目标扩展，把一个应该只做 A 的轮次，变成 A + B + C 全部开始动的状态。Spec 是本轮执行的合同，只有 Spec 里的内容才能被执行。

节点三：执行前 Checkpoint

在 Model 开始任何实际修改前，Harness 强制插入一个 Checkpoint：Model 必须用自己的语言说清楚当前理解、接下来的具体动作、预期的副作用、以及完成后如何验证。这个输出由人工或规则引擎确认后，才进入执行阶段。

Checkpoint 不是形式上的确认，而是对执行意图的最后一次外部校验。如果 Model 在这一步说不清楚，这通常意味着它实际上还没有形成稳定的执行计划，强行放行只会把问题延迟到执行阶段暴露。

节点四：基于外部证据验收

执行完成后，Harness 拒绝接受 Model 的自我评估作为完成信号。验收依据只有三类：测试结果、运行时日志和链路现象、测试环境或手动验证的现场证据。

这个约束的意义在于把"完成判断"的权力从 Model 转移到外部系统。Model 在完成一个任务后有强烈的倾向宣布成功，但这个倾向和实际结果是否正确无关，只和它的生成概率有关。外部证据是唯一可靠的验收标准。

验收时还需要显式区分两个层级：本轮阶段目标是否完成，和总目标是否完成。这两个问题必须分别回答，不能用前者代替后者。

节点五：运行时纠偏

当执行过程中出现意外——日志报错、接口异常、测试失败——Harness 的运行时纠偏机制开始介入。

纠偏的关键不是让 Model 继续推进原计划，而是先缩小当前轮次的目标范围。如果日志显示某条链路有系统性问题，本轮目标就从"完成功能 X"收窄为"定位链路问题的根因"，等根因被验证解决后，再重新推进原有目标。

这个过程里最重要的一点是：Model 在收到错误反馈时，会自然地倾向于"顺手多修几个地方"。Harness 的作用是强制它把修复范围控制在当前最小目标内，而不是在没有完成当前修复的前提下扩展到其他问题。

纠偏完成后，同样需要基于外部证据验收——这次最小目标是否真正完成了，而不是依赖 Model 的主观判断。

Harness 工程的未来方向

Harness Engineering 目前处于活跃的演进阶段，几个值得关注的方向：

模型训练与 Harness 设计的协同进化：当前的 Agent 产品在训练时已经把 Harness 纳入循环，模型会在和 Harness 的交互中被后训练，逐渐在文件系统操作、Bash 执行、任务规划、子 Agent 并行等方面有更强的原生能力。这个循环持续运转，模型在它被训练的 Harness 中会越来越强，但也因此对 Harness 细节产生过拟合——改变工具的调用逻辑可能导致模型性能下降。这意味着 Harness 设计本身是影响 Agent 能力的重要变量。

Harness 的动态组装：当前的 Harness 大多是静态预配置的，工具列表和上下文在任务开始前就确定。未来的方向是 Harness 能根据当前任务的需求，即时组装恰好合适的工具和上下文，而不是预先加载所有可能用到的内容。

Agent 自分析 Harness 失败：让 Agent 分析自己的执行追踪，识别 Harness 层面的失败模式并提出改进建议，形成 Harness 自我优化的能力。

什么时候需要引入 Harness

Harness 的引入有工程成本，适用场景可以用以下框架判断：

场景特征需要的 Harness 组件
单次调用，无状态，任务可重复几乎不需要
操作有副作用（写库、调接口、修改文件）执行门禁（Pre-conditions）
跨 Session 的持续任务State Store + 不变式
需要证据验收，不信任 Model 自评估Evaluator（Post-conditions）
长时间自治执行Ralph Loop + 规划 + 自验证
多 Agent 或多人协作文件系统作为共享协作层
完整企业级交付以上全部

任务链路越长、副作用越大、协作角色越多，Harness 的价值越高。

小结

Harness Engineering 是围绕 Model 智能构建系统的工程方法。Model 负责推理和决策，Harness 负责让这个智能在真实工程环境中稳定、可验证、可持续地工作。

它的核心组件来自两个方向的推导：从 Model 的局限向外推导需要哪些能力供给（文件系统、代码执行、沙盒、记忆），从工程系统对可靠性的要求向内推导需要哪些约束机制（前置断言、后置断言、不变式）。

Prompt Engineering 决定 Model 在给定上下文下能生成什么；Harness Engineering 决定这些生成结果在什么条件下被接受、在什么条件下被拒绝、任务状态如何跨 Session 保存和恢复。 两者解决的是不同层面的问题。
