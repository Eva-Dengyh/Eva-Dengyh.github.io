FastSAM-Demo/V3:基于 SAM 2.1 + Go 网关的交互式图像分割系统

Eva·2026.05.20·13 分钟阅读

 

一个开源的「点击即分割」Web 应用——上传图片,点哪里就抠出哪个物体。
前端 Next.js,后端 FastAPI + SAM 2.1,中间用 Go 自研了一层推理网关做粘性路由 + 横向扩展。

GitHub: https://github.com/Eva-Dengyh/FastSAM-Demo
License: MIT

项目长什么样

打开页面 → 拖一张图 → 点击物体 → 实时高亮分割结果。多次点击可以挑出多个物体,不同颜色叠加,支持导出原图 / 叠加效果 / 仅掩码三种模式。

模型用的是 Meta 发布的 SAM 2.1(Segment Anything Model 2),Apache 2.0 开源,权重免申请直接下载,小到 39MB 的 tiny 版本 CPU 也能跑,大到 224MB 的 large 版本 GPU 上飞起。

这次更新:从单进程到多 worker + Go 网关

项目最早是「Next.js 直连 FastAPI 单进程」,这次重构在前后端中间塞了一层用 Go 写的推理网关,把单进程升级成了多 worker 横向扩展 + 业务感知路由的形态。

改造前后

旧:  浏览器  ──▶  FastAPI 单进程  ──▶  SAM 2.1

新:  浏览器  ──▶  Go Gateway (:8080)  ──┬──▶  FastAPI worker-0  ──▶  SAM 2.1
                                       └──▶  FastAPI worker-1  ──▶  SAM 2.1
                                       (可水平扩展到 N 个)

为什么需要这一层

直接讲核心动机——不是为了高并发,是为了粘性路由。

SAM 2.1 推理分两步:

  • set_image() 算图像 embedding:0.5–3 秒(慢,纯算力)
  • predict() 出 mask:20–100 毫秒(快,只跑 decoder)

upload 时把 embedding 算好缓存在某个 worker 的内存里,后续这张图的所有点击必须回到同一个 worker 才能命中缓存,否则要么重算(慢 30 倍),要么报错。

这种「按 image_id 路由」是业务粒度的:

  • nginx 的 ip_hash / hash $cookie_xxx 都做不到——粘性的 key 在 multipart 上传响应的 JSON body 里
  • Python 自己更做不了——多进程之间不能互相感知状态

所以加了一层 Go 网关。利用 httputil.ReverseProxy.ModifyResponse 钩子拦响应 JSON、解出 image_id 写进会话表,后续 segment 请求按 image_id 反查 worker。十几行代码,问题就解决了。

网关都做了什么

七个子包,一千多行 Go,负责:

能力实现
粘性路由image_id → worker_id 会话表,带 TTL + 后台 sweeper
并发控流每 worker 一个有界 channel + N 个消费 goroutine,队列满立即 429
负载均衡新会话选「健康 worker 中队列最浅者」
健康摘除周期 ping /health,连续失败摘除 + 清空该 worker 的会话;连续成功放回
冷启动保护worker 启动默认 unhealthy,必须探测通过才接流量
跨服务 traceX-Request-Id 入口生成 → ReverseProxy 透传 → backend 写入日志
优雅退出SIGTERM 后停止接收新连接,等 in-flight 完成
可观测7 个 Prometheus 指标 + zerolog 结构化日志

双层并发兜底

不是所有事都让 Go 干。Python 这边保留了一层 asyncio.Semaphore 兜底——即使 Gateway 配错并发数,Python 端也不会爆显存。这是个小细节,但能让系统在配置错误下仍然安全。

错误语义对前端友好

状态码含义前端动作
200成功正常处理
410image_id 失效(worker 重启 / TTL 过期 / 摘除)自动重新上传图片
429worker 队列满按 Retry-After 退避重试
503无可用 worker等待健康检查恢复

前端 lib/api.ts 把这套语义吃进去,用户端表现就是「网络抖动 / 后端重启完全无感」。

7 个 Prometheus 指标

/metrics 端点直接接 Prometheus,关键指标:

指标用途
gateway_queue_depth每 worker 当前队列深度——HPA 扩缩容的依据
gateway_inflight每 worker 正在跑的推理数
gateway_worker_healthy每 worker 健康状态
gateway_session_table_size当前活跃会话数
gateway_request_duration_secondsP50/P95/P99 延迟分布
gateway_requests_totalQPS、错误率(按 route + status)
gateway_rejections_total拒绝原因分类(queue_full / unhealthy / session_missing / upstream_error)

接 Grafana 后整个系统的健康度一眼可见。

当前完整能力

功能

  • 拖拽上传 + Canvas 实时渲染
  • 点击即分割,毫秒级响应(命中 embedding 缓存的情况下)
  • 多物体管理,不同颜色叠加,列表里增删
  • 三种导出模式:原图 / 叠加效果 / 仅掩码
  • 横向扩展 + 故障自愈,worker 挂掉用户无感
  • RLE 压缩传输 mask,压缩率 > 98%

技术栈

层技术
前端Next.js 15 (App Router) + TypeScript + Tailwind CSS v4 + Framer Motion
网关Go 1.22 + chi + zerolog + Prometheus client
后端FastAPI + Pydantic + uv + asyncio
模型SAM 2.1 Hiera (tiny 39M / small 46M / base+ 81M / large 224M)
包管理go mod + uv + npm
部署docker-compose 一键起 / start.sh 本地多 worker 形态

核心数据流

upload:
  前端 ──multipart──▶ Gateway
                       ├─ 选最低负载 worker
                       ├─ ReverseProxy 流式转发(不读进 Gateway 内存)
                       ├─ 拦响应 JSON 截 image_id
                       └─ sessions.Put(image_id, worker_id)
                          │
                          └──▶ FastAPI ──▶ SAM 2.1 set_image() 缓存 embedding

segment:
  前端 ──{image_id, points}──▶ Gateway
                                ├─ 按 image_id 查会话表 → 命中粘性 worker
                                └─ 不命中返 410 → 前端自动重新上传
                                   │
                                   └──▶ 同一 worker ──▶ predict() 复用 embedding

五分钟跑起来

Docker(推荐)

git clone https://github.com/Eva-Dengyh/FastSAM-Demo.git
cd FastSAM-Demo

# 下载模型权重(只需一次)
mkdir -p models
wget -O models/sam2.1_hiera_tiny.pt \
  https://dl.fbaipublicfiles.com/segment_anything_2/092824/sam2.1_hiera_tiny.pt

docker-compose up --build

打开 http://localhost:3001 即可使用。

本地开发

需要 Go 1.22+、Python 3.10+ 配 uv、Node 18+。

./start.sh

会自动起 2 个 backend(:8000 / :8002)+ Gateway(:8080)+ 前端(:3000)。

验证多 worker 链路

./scripts/verify-multiworker.sh

会自动跑 8 次 upload,验证负载均衡 + 粘性路由——预期看到上传在两个 worker 间均衡分布,同一 image_id 的所有 segment 始终命中同一 worker。

接下来想做什么

项目目前是单图分割,但架构和模型本身有不少能延伸的方向。下面这些是路线图,欢迎一起来玩。

视频分割

SAM 2.1 相对 SAM 1 / MobileSAM 的核心卖点就是支持视频——通过 memory attention 机制做时序传播。当前版本没用上这块能力,补完后整个项目的「为什么选 SAM 2.1」就有了硬答案。

技术上要做的:

  • 后端引入 SAM2VideoPredictor,按帧推理 + 时序传播
  • 网关加长任务模式:POST 拿 task_id → WebSocket 推进度 → 完成后拉结果
  • 前端做时间轴 + 关键帧打点 + 逐帧 mask 叠加

文本提示分割(Grounding DINO + SAM)

把交互从「点一下」升级到「输入文本」——用户输入「猫」,Grounding DINO 检测出 bbox,SAM 出 mask。当下最热的开放词汇分割组合,做完整个项目就从单模态升级成多模态。

数据标注工具方向

加批量上传 + 标注导出(COCO / YOLO / Pascal VOC)+ mask 手动调整 + 撤销重做 + 用户体系,从 demo 变成「真的有人会用」的标注小工具。

让 Go 网关物尽其用

  • SessionTable 下沉 Redis:Gateway 自身无状态,可多实例 + 滚动升级不丢会话
  • k8s HPA 自动扩缩容:用 gateway_queue_depth 作为自定义 metrics,GPU worker 按队列深度自动扩缩
  • 从配置发现切换到服务发现:list-watch k8s endpoints,worker 上下线无需改配置

其他探索方向

  • WebSocket 实时分割,连续拖动鼠标本地预测 + 后台校正
  • 模型热切换,运行时在 tiny / small / base+ / large 之间切
  • iOS / Android 端,用 Expo + React Native 跨端
  • Grafana 仪表盘 + alert rules

写在最后

这个项目最初是想验证 SAM 2.1 在 Web 端的交互体验,做着做着把后端架构完整重构了一遍。

写出来分享是希望:

  • 给想做图像分割的同学一个能直接用的起手模板
  • 给在思考「Python 推理服务怎么做横向扩展」的同学一个具体例子(粘性路由这件事 nginx 真的搞不定)
  • 拿到一些反馈和 issue,把这套架构继续打磨下去

欢迎 Star、Fork、PR、提 issue,也欢迎挑刺——尤其是 Go 网关那部分的实现,有更优雅的写法非常想听听。
