开发工具

行业拆解、决策拆台、代码验收：用三个 Skill 定义认知外骨骼

Eva·2026.04.21·12 分钟阅读

 

摘要：与其堆「万能提示词」，不如把高频思考流程封装成 Skill——可复用的专家工作流。下文记录我写的 3 个 Skill、共同方法论，以及普通人如何起手。

本文涉及的 Skill 与仓库

这 3 个 Skill 的完整定义与源文件已开源在笔记仓库中，便于对照阅读与二次改造：

Skill定位
Industry X-Ray行业深度拆解专家
Devil's Advocate重大决策前的影子对手
Skill AcceptorAI 写完代码后的验收简报协议

仓库地址：https://github.com/Eva-Dengyh/AI-Fullstack-Notes

Skill 文件位于仓库的 skills/ 目录（如 industry-xray-teardown、devils-advocate、skill-acceptor 等），与文中命名一一对应。

最近我做了一件很小，但我认为有意思的事情：我没有再继续写一堆「万能提示词」，而是写了上面这 3 个 AI Skill。

它们看起来服务于完全不同的场景——一个用来研究行业，一个用来反驳决策，一个用来验收代码。但写完之后我发现，它们其实指向同一个问题：

我们到底应该怎样把 AI 从「聊天工具」，训练成一个真正可复用、可交付、可协作的专家分身？

这篇文章想聊聊我写这 3 个 Skill 的过程，以及它们背后共同的方法论。

一、为什么我不再满足于「提示词」

很多人用 AI，还是停留在一句话阶段：

「帮我分析一下这个行业。」
「帮我看看这个决策对不对。」
「帮我总结一下这段代码。」

这种问法当然能得到答案，但问题也很明显：输出不稳定。有时 AI 很聪明，有时很敷衍；有时结构清晰，有时像在说正确的废话；有时它真的帮你做判断，有时它只是在顺着你说。

原因很简单：你只是给了它一个任务，但没有给它一套工作协议。

而 Skill 的价值，恰恰在于把一次性的「问答」，变成一套可复用的「专家工作流」。一个好 Skill 不只是告诉 AI「你是谁」，而是明确规定：

  • 什么场景下启动
  • 什么输入算合格
  • 应该按什么步骤推理
  • 哪些行为被禁止
  • 最终必须输出什么格式
  • 如何和用户继续互动

换句话说，Skill 不是一句咒语，而是一份操作手册。

二、第一个 Skill：行业 X 光机，把黑话翻译成人话

第一个 Skill 叫 Industry X-Ray，定位是：行业深度拆解专家。

它解决的是一个很常见的问题：面对陌生行业时，很容易被一堆黑话劝退——SaaS、MCN、新能源、跨境电商、短剧、芯片、AI Agent……行业报告很厚，专家访谈很玄，媒体又爱堆概念。看完一圈，你可能记住了一堆词，但还是不知道这个行业怎么赚钱、谁在赚大钱、谁在干苦活、未来谁会被掀桌子。

所以我给这个 Skill 设计了一个非常明确的拆解框架。

1. 先说人话：这个行业本质上在干嘛？

它必须用一句通俗、甚至带点幽默的话，把行业本质讲清楚。例如：

SaaS 本质上就是软件界的「共享单车」：以前你花大价钱买断软件，现在按月付租金，随时能用。

这个要求很重要：如果一个行业连最基本的存在理由都讲不成人话，后面所有分析都可能只是术语堆砌。

2. 再剥三层：看热闹、看门道、看底牌

我把行业拆成三层：

层次关注点
表层现状、头部玩家、常见黑话
中层产业链、资金流、谁赚辛苦钱
底层第一性原理、核心驱动力、未来洗牌变量

这套结构不会让 AI 只停留在「行业很有前景」「竞争很激烈」这种空话里；它必须回答更硬的问题：上游是谁、中游是谁、下游谁买单、钱从哪里来、利润被谁拿走、行业真正依赖的是政策/资本/技术/流量还是人性、未来什么变量会把牌桌掀翻。

3. 最后必须拷问用户

这个 Skill 还有一个我很喜欢的设计：输出报告之后，不能结束。它必须抛出两个场景化问题，让用户用自己的话回答，例如：

  • 给你 500 万，你会投产业链哪一环？为什么？
  • 如果某个新技术普及，哪类公司会先死？

这一步看似多余，其实非常关键——真正的理解不是「我听懂了」，而是「我能在新场景里做判断」。AI 不应该只是内容生成器，它还应该是认知教练。

三、第二个 Skill：影子对手，在重大决策前拆掉自我说服

第二个 Skill 叫 Devil's Advocate，我把它翻译成「影子对手」。它的气质非常不讨喜：不鼓励，不安慰，不提供情绪价值。它只做一件事：

在你做重大决策之前，冷酷地扮演那个最清醒的反对者。

比如你准备辞职创业、拿积蓄开店、换城市生活、重仓某个投资、加入某个早期项目。这类决策最危险的地方，不在于没有信息，而在于我们往往已经先有了冲动，然后只想找理由证明自己是对的——这就是典型的确认偏误。

所以这个 Skill 只抓两件事：最坏情况（事前验尸），以及执行路上会踩的雷（按阶段列风险）；最后用两个压力问题收口。

1. 事前验尸：最坏情况先摆上桌

它不会温柔地问「这个计划有哪些风险？」它会直接假设：

现在是 1 到 3 年后，你的计划已经彻底失败，资金耗尽，机会成本巨大，甚至名誉受损。

然后倒推 5 个导致失败的关键节点（Pre-mortem，事前验尸）。它强迫我们从「我会成功」切换到「我为什么会死」，且必须覆盖几个死穴：

  • 资金链断裂点
  • 能力错配点
  • 外部环境突变点
  • 团队或合伙关系风险
  • 最后一击如何发生

这会把很多浪漫叙事瞬间拉回现实。

2. 执行过程风险：按阶段拆雷

光有一个「惨烈的结局」还不够，很多人死在从动第一笔钱到所谓稳定态的中间过程里。所以这个 Skill 要求按你方案里真实的执行顺序（筹备、启动、爬坡……名称随计划而变），列出各阶段最可能出事的点：尽量写成「什么情况会发生 → 可能演变成什么」，而不是泛泛的「要注意风险」。

这样你拿到的不是一篇正确的废话，而是一张和时间线对齐的风险地图。

3. 最后给出致命审问

结尾不是「祝你成功」，而是两个压力测试问题，例如：

  • 如果前三个月营业额为 0，你的现金流能撑到第几个月？
  • 如果巨头明天用补贴杀进来，你除了情怀还有什么物理防御手段？

如果答不上来，就别急着去现实里送钱。我写这个 Skill 的初衷，不是为了让 AI 更会鼓励人，而是让 AI 在关键时刻敢于反对我。

四、第三个 Skill：代码验收，不让人类淹死在 AI 生成的代码里

第三个 Skill 叫 Skill Acceptor，场景更工程化：当 AI Agent 写完一堆代码之后，人类要怎么验收？

这个问题会越来越重要。未来代码不是越写越少，而是「生成得越来越快」：以前的问题是代码写不出来，现在的问题可能是代码太多，人类看不过来。一个 Agent 可能几分钟内改完十几个文件，若人类仍逐行审查，很快就会认知过载。

所以 Skill Acceptor 的目标很明确：

不要让人类阅读未经消化的底层样板代码，而是让 AI 生成架构级验收简报。

1. 先看变更范围

必须先回答：主要入口点在哪里？核心新增或修改了哪些文件？数据库表结构有没有变化？是否引入新依赖？是否修改全局配置？——先建立边界，才知道风险在哪里。

2. 再过滤掉低价值代码

原则：不要解释基础语法，不要大段粘贴原始代码，不要流水账式罗列文件。人类需要的是：

  • 这段代码在业务上意味着什么？
  • 主链路怎么走？数据怎么流转？
  • 哪些地方用了事务、锁、重试、降级？
  • 出错时会怎么返回？

3. 最终输出验收面板

输出类似控制台面板：功能是什么、入口在哪里、变更速览、核心实现方案、主链路执行流、异常与边界防御、每个关键步骤对应的代码锚点。例如：

第 1 步：拦截器校验 Token，提取 UserId
第 2 步：并行查询库存和用户信息
第 3 步：开启事务写入订单并扣减库存
第 4 步：返回 200，同时异步发送 MQ 消息

每一步都要带文件和函数名，让人类不用迷失在代码海里，又能一键定位关键位置。

这个 Skill 背后的判断是：

AI 时代的代码审查，重点会从「逐行读代码」，转向「审查架构意图、业务链路和边界防御」。

人类不该和机器比耐心，而应把注意力放在更高层的判断上。

五、这 3 个 Skill 的共同点：把 AI 变成「有流程的专家」

这 3 个 Skill 的场景不同，但底层结构很像。我总结：一个真正好用的 Skill，至少要包含 6 个要素。

#要素说明
1明确角色，但不止于角色角色是皮肤，流程是骨架；要写清怎么拆解、先后看什么、必须追问什么、不能做什么。
2设置门禁，拒绝模糊输入例如 Devil's Advocate 要求具体计划：「我想创业」不合格，「拿 50 万辞职回三线城市开独立咖啡店」才合格。
3强制使用结构化推理Industry X-Ray 三层拆行业；Devil's Advocate 事前验尸 + 分阶段执行风险；Skill Acceptor 变更范围 + 主链路 + 边界防御。
4明确禁止项，防止 AI 偷懒如：不准堆砌空洞术语、不准只给情绪价值、不准大段贴代码、不准忽略事务与异常等。约束往往比指令更重要。
5固定输出格式，让结果可复用格式不是为了好看，而是为了降低协作成本——输出可归档、可对比、可交接，成为工作资产。
6加入互动闭环结尾的拷问或验收，逼用户完成一次思考动作；单向输出容易制造「我懂了」的错觉。

六、写 Skill，本质上是在写自己的思考操作系统

写完这 3 个 Skill 后，我最大的感受是：Skill 不是简单的提示词工程，更像把一个人的思考方式封装成可调用的模块。

  • 写 Industry X-Ray 时，我在定义：我希望自己如何理解一个陌生行业。
  • 写 Devil's Advocate 时，我在定义：我希望自己如何对抗冲动、乐观和幸存者偏差。
  • 写 Skill Acceptor 时，我在定义：我希望自己如何验收 AI 时代的代码产出。

写 Skill 的过程并不只是「教 AI 怎么做事」，它也在反过来逼你梳理：你真正重视什么？判断标准是什么？如何定义好结果？讨厌哪些低质量输出？希望哪些思考动作被稳定复现？

从这个角度看，Skill 不是 AI 的插件，而是人的认知外骨骼。

七、普通人应该怎么开始写自己的 Skill？

如果你也想开始写 Skill，建议不要一上来追求「大而全」，可以从三个问题起手。

1. 你经常重复做什么判断？

例如：选题判断、简历筛选、投资分析、客户画像、产品需求评审、会议纪要整理、代码审查、商业模式拆解……凡是你反复做、但每次都很耗脑子的事情，都适合封装成 Skill。

2. 你对这个任务的好结果有什么标准？

不要只写「帮我分析得深入一点」。要写清楚：哪些模块必须出现、哪些问题必须回答、哪些情况必须追问、哪些风险必须单列、哪些输出算不合格。越具体，AI 越稳定。

3. 你希望 AI 像谁一样工作？

不是笼统的「像专家」，而是更具体，例如：

  • 像一个毒舌但靠谱的反对者
  • 像一个能把黑话讲成人话的老师
  • 像一个只关心架构意图的技术负责人
  • 像一个极度挑剔的产品评审
  • 像一个擅长追问动机的采访者

角色越鲜明，边界越清晰。

结语

过去我们说「会提问的人更会用 AI」。但下一阶段的差距可能不只是会不会提问，而是：

你有没有把自己的高频思考流程，沉淀成可复用的 Skill。

提示词解决的是一次对话；Skill解决的是一类问题。一个人若能不断把自己的判断、经验、方法论封装成 Skill，就不只是在单纯使用 AI，而是在训练一组越来越懂自己的专家分身。

  • 行业研究时，有人帮你扒掉黑话。
  • 重大决策前，有人冷酷地反对你。
  • 代码验收时，有人把复杂实现翻译成架构简报。

这不是让 AI 替代思考；恰恰相反，这是让 AI 帮你守住更高质量的思考标准。我写这 3 个 Skill 的收获也正在这里：它们表面上是工具，实际上是我给自己装上的三个认知外挂——一个帮我看懂复杂世界，一个帮我对抗盲目乐观，一个帮我管理 AI 时代的代码复杂度。

如果说 AI 是一台越来越强的发动机，那么 Skill 就是方向盘、刹车和仪表盘。

  • 没有 Skill，你只是在和 AI 聊天。
  • 有了 Skill，你才开始真正训练自己的工作系统。
