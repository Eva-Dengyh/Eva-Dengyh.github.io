开发工具

我把 AI 视频模型接入前最容易踩的坑，整理成了一个开源项目

Eva·2026.09.15·6 分钟阅读

 

最近整理了一个小项目，叫 ModelCap。

它做的事情很朴素。把常见 AI 视频模型的能力、参数限制、输入素材要求、错误码和价格信息，整理成机器能读的 JSON，再给开发者一个 Node.js SDK 和命令行工具，用来在真正调用模型前做一次参数检查。

项目地址

https://github.com/Eva-Dengyh/ModelCap

现在发到了 v0.1.0，推荐先从 GitHub tag 安装。

npm install github:Eva-Dengyh/ModelCap#v0.1.0

接视频生成模型时，很多麻烦并不出现在生成阶段，而是出现在调用前。

同样是图生视频，不同模型对图片尺寸、格式、比例、大小的要求不一样。同样是生成 5 秒、10 秒、30 秒的视频，不同模型对时长、分辨率、宽高比的限制也不一样。有些模型允许传参考图，有些允许传参考视频，有些还支持音频。有些限制写在参数表里，有些写在备注里，有些只在错误码示例里露出来一点。

产品里一旦接了多个模型，这些差异很快就会变成一堆零散判断。前端表单要知道哪些参数能展示，后端要知道哪些请求应该提前拦住，模型路由要知道某个需求能不能交给某个模型，报错时还要把厂商返回的错误码翻译成人能看懂的话。

ModelCap 现在解决的是这一段工作。

它目前收录了 50 个 AI 视频模型版本。每个模型版本对应一个 JSON 条目，里面会记录这个模型支持哪些任务，能接哪些输入，参数有什么范围，输入素材有什么限制，已知错误码怎样归类，价格信息来自哪里。JSON 是事实来源，Markdown 和 dist 目录里的文件都是生成结果。

在 SDK 里，现在主要有四个函数。

getModel 用来取单个模型。

listModels 用来按任务、输入、能力筛选模型。

validateRequest 用来检查一个请求是否违反已经记录下来的硬约束。

normalizeError 用来把一部分厂商错误码转成更稳定的错误分类。

一个简单例子是这样。

import { getModel, listModels, validateRequest } from 'modelcap-catalog'

const model = getModel('wan-3.0')

const imageModels = listModels({
  task: 'generate',
  input: 'reference_image',
})

const result = validateRequest('wan-3.0', {
  task: 'generate',
  parameters: {
    duration: 5,
    resolution: '1080p',
    aspect_ratio: '16:9',
  },
})

console.log(model.model_id)
console.log(imageModels.length)
console.log(result.valid)

如果只是想在命令行里查一下，也可以用 CLI。

node node_modules/modelcap-catalog/bin/modelcap.mjs list --task generate --input reference_image
node node_modules/modelcap-catalog/bin/modelcap.mjs get wan-3.0

我比较看重的一点，是这个项目故意做得保守。

它只拒绝结构化数据里明确写出的硬约束。官方文档没有写清楚的地方，它会尽量给 warning，而不会自己猜一个规则出来。备注文字也不会被当成可执行规则直接解释。这样做牺牲了一些自动化程度，但比较适合放到真实产品里当预检查工具。宁可告诉你这里资料不完整，也不应该替厂商文档脑补一个判断。

这类信息没那么热闹，但开发时很实用。

现在的 v0.1.0 已经补了开源项目该有的大部分东西。README、中文 README、API 文档、CLI 文档、版本策略、发布说明、CHANGELOG、贡献指南、安全说明、数据许可证、issue template 都有了。CI 里会跑测试、类型检查、示例检查、模型 JSON 校验、schema 校验、新鲜度检查、构建检查和 npm 打包预检。发布前还有 npm run release:check，会检查版本和 CHANGELOG 是否对得上，CLI 和发布文档有没有被打进包里。

它现在适合几类人试用。

如果你在做 AI 视频产品，需要在表单层提前知道某个模型支持哪些参数，它能省掉一部分硬编码。

如果你在做模型路由，需要先筛出哪些模型支持图生视频、视频编辑、音频输入，它能直接给你一份结构化目录。

如果你在封装 provider SDK，需要把厂商错误码整理成稳定的业务错误，它也能提供一个起点。

如果你只是想看看不同视频模型的能力差异，也可以直接读 JSON 或 Markdown。

当然，它现在还不是完整的模型网关。它不负责调用厂商 API，不管理密钥，不做队列，不处理回调，不算账单，也不评价生成质量。它更像一个模型接入前的资料层和校验层。

下一步会继续补三件事。

第一，补更多模型的结构化参数覆盖。现在目录已经能用，但不同厂商公开文档的细致程度不一样，后面会继续把时长、分辨率、输入素材、音频、错误码这些字段补得更完整。

第二，做每个模型的数据完整度报告。这样使用者能一眼看出某个模型哪些字段已经有官方来源，哪些地方还缺资料，集成时心里更有数。

第三，把安装和文档体验继续往前推。后面会补更顺手的发布方式，也会考虑把 API、CLI 和模型目录整理成更容易浏览的文档页。

如果你正在接 AI 视频模型，或者被不同厂商文档里的参数差异折腾过，可以试一下。

npm install github:Eva-Dengyh/ModelCap#v0.1.0

项目还在早期。欢迎提 issue，也欢迎按官方文档补模型条目。ModelCap 会尽量只记录能追溯的事实，把不确定的地方留在明面上。
