接口签名到底在防什么，从哈希一路讲到 Ed25519

Eva·2026.08.14·14 分钟阅读

 

先说一句你可能正想问的。平时不都有 HTTPS 吗，怎么还要接口签名？

HTTPS 保护的是通道，防中间人偷看和篡改；签名保护的是数据和身份。TLS 在网关、代理那里就解密终结了，网关到后端这一段往往不再加密。更关键的是，开放平台里 HTTPS 只能证明通道没被偷听，证明不了请求是持有密钥的那个应用发的。所以哪怕全程 HTTPS，服务器照样要验签名。下面进入正题。

被改掉的金额

一个支付请求从客户端发出，报文里写着 100 元。它在公网上绕了一圈，到达服务器时，金额变成了 1 元。服务器收下报文，怎么知道它被改过？

没有签名的时候，它毫无办法。报文就是普通文本，任何人都能改，改完再传一遍，服务器看到的只是另一个请求。后来接口双方约定一个规矩，客户端在报文里附上一串由内容算出来的指纹，服务器按同样的方法重算一遍，对不上就拒掉。改动任何一个字符，指纹都会变。

这串指纹，接口文档里一般就叫签名。

签名要防的是报文背后想动手脚的人。有人改报文，这是篡改；有人拿不到密钥却造出一份合法请求，这是伪造；至于赖账的，发完就不认账。下面从第一个动手脚的人讲起，一个一个说清楚。

1 报文里的三件事

1.1 改报文 → 哈希

第一个动手脚的人很直接，改报文。把金额从 100 改成 1，改完重发。

挡他的是哈希，也叫摘要。它把一个任意长度的内容，压成一串固定长度的数字。SHA-256 的输出无论输入多长，都是 256 位，写成十六进制就是 64 个字符。它的脾气是，输入变一点点，输出面目全非。

于是校验办法出现了，发送方算出内容的哈希，接收方重算一遍，对得上就认为内容没变。改动任何一个字节，指纹立刻变样，篡改就此现形。

要让双方算出来的是同一份指纹，先得约定怎么拼。参数先按名字的 ASCII 码排序，再无分隔地拼成一个字符串，最后转成十六进制传输。淘宝开放平台文档里的例子，foo、bar、foo_bar、foobar 排完序，拼成 bar2foo1foo_bar3foobar4。

签名大致就是这三步。先过滤掉空值，再按 ASCII 排序拼成字符串，最后套上密钥算摘要。

1. 过滤空值。{amount: 100, nonce: null} -> {amount: 100}
2. ASCII 排序。amount=100&time=1620000000
3. 套密钥计算。HMAC-SHA256(secret_key, "amount=100&time=1620000000")

实际对接时，最容易出问题的就在这里。Key 的大小写、嵌套对象里层的排序、数组怎么展开、空值和 null 算不算，两边只要有一个细节不一致，算出来的签名就对不上。先核对拼装规则，再怀疑算法。

就拿空值来说，主流做法是剔除空值和 null，不参与签名；也有老接口要求把 null 转成空串再参与。以对方文档为准，对接第一步，永远是死抠文档里"签名规则"那一页。

签名长度也从这里来，MD5 和 HMAC-MD5 是 128 位，32 个字符，SHA-256 是 256 位，64 个字符，光看长度就能猜出算法。

但哈希有个致命的问题，它不需要钥匙。第二个动手脚的人，哈希就挡不住了。

1.2 改完重算 → HMAC

第二个动手脚的人高明一点，他不改哈希，他改完内容以后，顺手用同一套算法重算一个哈希附上去，一切如常。哈希挡得住改内容的人，挡不住会重算的人。治他的是 HMAC。

办法是给哈希加一把钥匙。双方事先共享一个密钥，计算指纹时把密钥掺进去，没有钥匙的人就算改对了内容，也算不出合法的指纹。这个结构叫 HMAC，带密钥的哈希消息认证码，最常用的是 HMAC-SHA256。

为什么不用土办法 MD5(secret + 数据) 那种把密钥拼在前面的写法？因为这类签名有个数学弱点，叫长度扩展。攻击者不知道密钥，也能凭一个已知签名，推导出在数据后面续一段内容的合法签名，等于在别人签过名的报文后面接着写。HMAC 把密钥经过两轮异或处理再参与哈希，结构上专门堵这个洞。HMAC-SHA256 到今天仍是接口签名的默认选择，飞书、淘宝开放平台，还有大量内部系统的对接，用的都是这一类。

共享钥匙的方案有两个天生的短板。一个是分不清谁发的。双方拿着同一把钥匙，接收方自己也能算出同样的指纹，将来出了纠纷，它没法向第三方证明这指纹是对方算的。另一个是钥匙怎么安全送达。钥匙只能走线下可靠的通道交给对方，一旦通过网络传，坏人在半路截走一把，后面所有签名都作废。一对一对接还好办，要和很多家合作时，钥匙分发就成了灾难。

第二个短板，把第三个动手脚的人引了出来。

1.3 发完赖账 → 公私钥

第三个动手脚的人最阴，他不改也不冒充，他发完一笔订单，回头说这笔不是我发的。共享钥匙防不了这个，因为两边都有钥匙，谁都算得出指纹。对付他的是公私钥。

非对称签名把这件事也补上。它生成一对钥匙，一把叫私钥，一把叫公钥。私钥只有签名方自己留着，公钥随便发，谁都可以要。

签名的时候用私钥，验证的时候用公钥，方向和加密正好反过来。加密是公钥锁上、私钥打开，防别人偷看；签名是私钥盖章、公钥验证，防篡改和假冒。可以理解成印章和印鉴卡。私钥是你的私章，全世界只有你能盖；公钥是留给别人的印鉴样本，别人拿它一比对，就能确认这个章确实出自你手。三件事就此全部解决。公钥不怕被截，截走公钥的人依然盖不出章；防抵赖也成立，别人验得了、盖不出，出了事你赖不掉。

实现上先补一个细节。RSA 这类算法只能处理有限长度的数据，大数运算也慢，直接签整份报文不现实。实际流程都是先对内容算一个哈希，只对那几十个字节做签名。文档里看到的 RSA-SHA256、ECDSA-SHA256 这种双名字，前面是签名算法，后面是它签的那个哈希。

如今现代接口把这个思路用得更远。微信支付 API v3、AWS SigV4 这类接口，拼法已经换了一套，先把请求要素拼成一段规范字符串，方法、路径、时间戳、随机数，再加上请求体本身或它算出来的哈希，再签名。具体拼法各家文档各不相同，原理还是同一个，先把内容压成短串，再对短串盖章。

常见的实现有几种。RSA 最老也最普及，兼容性最好，安全强度靠密钥长度，现在起步 2048 位，支付平台和 HTTPS 证书大量用它。RSA 签名前得先给哈希套一层填充，老的是 PKCS#1 v1.5，现在更推荐更稳的 RSA-PSS。ECDSA 基于椭圆曲线，同等强度下密钥短得多、算得快，签名也短、带宽消耗小，区块链几乎全用它，但它对随机数要求极高，随机数用错一次，私钥就没了，这个坑 3.2 再单独讲。Ed25519 是更年轻的一代，用的是确定性签名，随机数由私钥和消息一起算出来，不碰外部随机数发生器，复用无从谈起（RFC 8032），SSH 和不少新系统在用。国内合规场景还会要求国密算法，对应的是 SM2。

这一排算法撕不开，靠的是两类数学难题。RSA 靠大整数分解。把两个大质数乘起来很容易，把乘积拆回两个质数极难，攻击者想从公钥倒推出私钥，就必须去做这件极难的事。DSA、ECDSA 和 Ed25519 靠离散对数问题，给定一个数和它的若干次幂，倒推指数几乎不可能。这两类难题的共同点是单向，算过去毫不费力，算回来徒劳无功，签名体系的安全就建立在这个不对称上。DSA 本身是美国数字签名标准 DSS 的指定算法，专管签名、不支持加密，如今基本被 ECDSA 和 Ed25519 取代，只剩历史意义。

三个动手脚的人，折腾的都是报文里的内容。第四个人不一样，他连报文都不动。

2 报文之外的两个空子

2.1 原样重放 → 时间戳和随机数

第四个人最省事，一根手指都不用动，把请求原样再发一遍，服务器照样放行。治他的是时间戳和随机数。一份 100 元的支付请求被重放十次，就扣十次款。签名防的是内容被改，防不住内容根本没变。

接口规范对此的约定是，请求里必须带时间戳和随机数。时间戳超过一定时效直接拒绝，相同的随机数只收一次。随机数不用永久保存，它只在时间戳的有效期内有意义，过期即删，免得数据库越攒越大。淘宝文档里公共参数那栏的 timestamp，干的就是这件事。

2.2 逐字符猜 → 恒定时间比较

第五个人靠的是计时，靠响应时间猜签名。对付他的是恒定时间比较。服务器验证签名时，如果逐字符比对、发现不同就提前返回，比对 32 个字符的签名，前 3 个字符对上的响应时间，和全错的响应时间不一样。攻击者多试几次，就能靠响应时间一点点猜出签名，这叫时序攻击。

正确做法是不管哪个位置不同，都完整比完，让耗时恒定。不少成熟 SDK 里专门封装了这个函数。

3 算法会老，钥匙会丢

3.1 哈希碰撞 → MD5 和 SHA-1 退场

动手脚的人先放一放，算法自己也有毛病，最出名的是哈希碰撞。对付有毛病的算法，办法是让它退场。2004 年，王小云团队在密码学会议上宣布找到 MD5 的碰撞，能构造出两份内容不同、哈希相同的数据。这意味着攻击者可以准备一份恶意报文，让它的哈希和合法报文一模一样，签名就此失效。从那以后，MD5 在签名领域基本退役，现在文档里还留着 MD5 签名选项的，多数是历史兼容。

2017 年 2 月，Google 和荷兰 CWI 研究院联合公布 SHA-1 的第一次实际碰撞，项目代号 SHAttered，SHA-1 走完了同样的路。

3.2 偷私钥 → PS3 的教训

这些人里头，最坏的一个留在最后，他连报文都不碰，直接偷私钥。对付他，得靠密钥保管。2010 年底，安全团队 fail0verflow 公开了索尼 PS3 私钥被恢复的过程，起因是索尼在多次签名时复用了同一个随机数。ECDSA 要求每次签名都用新的、不可预测的随机数，随机数泄露一次，私钥就跟着没了。Ed25519 的一个优点正是签名过程不依赖随机数，从根上消除了这类错误。

这类事故也说明，密钥保管是整个体系里最脆的一环，比算法本身脆弱得多。

4 落到项目里

4.1 现实里怎么选

落到自己的项目，判断标准很简单，看谁和谁对接。

双方一对一、密钥能线下交付的私有接口，HMAC-SHA256 就够，简单、快、实现成本低。要跟多方对接，或者需要向第三方证明请求出自你手，用 RSA 或 Ed25519。JWT 是个现成的对照，同一个标准里 HS256 用的是 HMAC，适合内部系统互认；RS256 用的是 RSA，适合第三方也能验签的场景。支付平台几乎清一色用 RSA-SHA256，支付宝文档里叫 RSA2，微信支付 API v3 也是这个方案。

还有一个绕不开的问题，公钥随便发，怎么知道这把公钥真是某某公司的。任何人都能生成一对钥匙，然后说自己是支付宝。答案在证书里，公认的证书机构 CA 用自己的私钥给公司的公钥盖章，形成信任链，浏览器里 HTTPS 那个锁头背后就是这套机制。开放平台的公钥由官方渠道发布，意义相同，只是省掉了证书机构这一步。

4.2 主流的签名算法，一张表收下

前面散在各处的算法，按有没有钥匙分成三档，集中列在这里，方便对着查。

对称系，共享一把密钥，算出来的是消息认证码。密码学里它叫 MAC，只有非对称的才叫数字签名（Signature），国内开发语境把接口验签统称"签名"。看外文文档、跟安全专家交流时，这两个语境别混。

算法输出长度现状典型用途
HMAC-SHA256256 位，64 个字符主流默认内部系统对接、开放平台签名
HMAC-SHA1160 位，40 个字符可用的旧款老系统兼容
HMAC-MD5128 位，32 个字符仅历史兼容，新设计不用淘宝开放平台等老平台

非对称系，私钥签名、公钥验签，这才是严格意义的数字签名，也是支付平台和证书的标准。

算法密钥长度现状典型用途
RSA-SHA2562048 位起步最普及支付宝 RSA2、微信支付 API v3、HTTPS 证书
RSA-PSS2048 位起步新填充方式新系统推荐
ECDSA256 位左右很广泛TLS 证书、区块链（secp256k1）
Ed25519256 位新秀SSH、新兴系统
DSA1024 位起步DSS 指定算法，基本退役历史遗留
SM2256 位国密标准国内合规场景

哈希层，没有钥匙，单独不能当签名用，却是所有签名算法的地基。

算法输出长度现状
SHA-256256 位当前事实标准
SHA-512512 位高安全场景
SHA-3可变新一代，部署还不多
MD5、SHA-1128 位、160 位已退役，见 3.1

4.3 最后几句

把优先级排一下。密钥管理比算法选择重要，防重放、防时序攻击这些细节比算法强度重要，用成熟标准比自己发明重要。算法选错可以换，密钥写死在代码里、随机数复用这种错，换算法也救不回来。

下次再看任何一家平台的签名文档，不管是淘宝的 MD5 和 HMAC，还是微信支付的 RSA-SHA256，都可以在脑子里拆成这几层。先哈希压缩，再排序拼装，然后用你的密钥体系盖印，最后转成十六进制比对。所谓签名，从头到尾就是这一件事。
