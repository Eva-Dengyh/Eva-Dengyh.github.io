Token 预算管理：动态预留与分层压缩的工程模式

Eva·2026.06.02·17 分钟阅读尚无英文译文

 

你的 LLM 有一个 200K 的"银行卡额度"——但真正能花的，可能连一半都不到。

你的 200K 窗口，真正能用多少？

打开一家模型厂商的文档，可以看到醒目的"200K 上下文窗口"。这个数字让人放松，让人觉得"塞就是了"。

但动手做工程的人很快会发现问题。来，我们逐项拆：

模型硬上限（200K）
├── 系统提示词（System Prompt）          ∼2K–8K
├── 工具/函数定义（Tool Definitions）     ∼5K–134K
├── 安全/隐藏前缀（Hidden Preamble）      ∼数百 token
├── 多模态占位符展开                      ∼不定
├── 对话历史（Conversation History）      ∼动态增长
├── 当前用户输入                          ∼可变
├── 为模型回复预留（Reserve）              ∼4K–20K
└── 思考 token（Thinking/Reasoning）       ∼不可见但计入
─────────────────────────────────────────────
    剩余可用预算                           ？？？

每一项都值得仔细看：

系统提示词——你给模型设定的角色和行为规范。一个中等复杂度的 Agent 系统提示词轻松超过 2,000 token。加上安全策略和输出格式约束，8,000 token 很常见。

工具定义——这是最容易被忽视的"隐形大户"。每个工具都是一个 JSON Schema：函数名、参数、类型约束、描述文本，全部计入上下文。Claude Code 有 30+ 个工具，光是工具定义就能吃掉 55K–134K token。有研究显示，在 Claude Opus 上，每次调用的工具定义部分就要烧掉 0.67。你的 Agent 还没开始工作，钱已经花出去了。

对话历史——每一轮的 user 消息、assistant 回复、tool call 及其返回结果全部累积。20 轮对话轻松超过 50,000 token。而且每发一条新消息，整个历史都要重新发给模型。

Reserve——你不留的话，模型回复会被硬截断。一个不完整的 JSON、半句话、一段没写完的代码。同时还要防止"压缩悖论"——压缩本身需要写摘要进上下文，但你连写摘要的空间都没有了。

思考 token——o1、Claude Opus 等推理模型在给答案前会在内部"思考"。

全部加起来，一个实际运行的 Agent，200K 窗口的可用预算可能只有 30K–80K。能用的不到一半。

三个必须搞懂的概念

Token 预算管理不是"数一数还剩多少"。它需要一套简单但精准的概念框架。

2.1 Budget（预算）：这一轮总共能花多少

Budget 不是 200K，是 200K 减去所有固定开销后剩下的。

Effective Budget = Context Window − System Overhead − History − Reserve

把 budget 理解成主动约束，而不是被动的"还剩多少"。当已用 token 逼近 budget，就要触发干预——压缩、截断、或拒绝。

2.2 Reserve（预留）：给模型的回复留出空间

想象你写一封长邮件，写到字符上限时最后一句话是"明天下午三点我们在——"，发送按钮灰了。对 LLM 来说，这意味着：

  • JSON 被截断，解析失败
  • tool call 参数不完整，执行出错
  • 回复戛然而止，用户看到半句话

所以你必须从"能花的"里面再划一块不动的。问题是：固定 reserve（如始终 4,096）不够灵活。一个"是/否"回答可能只要 10 token，一次代码重构可能生成 8,000 token。

更好的做法是动态 reserve：

reserve = base_reserve + 任务复杂度加成
──────────────────────────────────
是/否判断        → base_reserve × 0.1
简短解释         → base_reserve × 0.3
代码建议         → base_reserve × 1.0（基准）
代码重构/生成    → base_reserve × 2.0
长文档生成       → base_reserve × 3.0

这个思路和操作系统的内存分配一模一样——进程向内核申请内存，内核根据系统状态批准或拒绝。

2.3 Threshold（阈值）：别等空间用完才行动

Claude Code 的做法最能说明问题：

利用率行为
∼85%用户看到警告提示
∼90%自动触发压缩
∼95%阻塞新请求
∼98%手动压缩的最后防线

关键思想：在 85% 就警告，在 90% 就动手。等到 98% 再反应，连压缩本身都可能因空间不够而失败。

这不是二元的"够/不够"，而是一个渐进式响应链——随着压力升高逐步升级响应强度。大多数情况下，轻量清理就够了；只有真正紧急时才调用重量级压缩。

三个实战问题

3.1 "我就用字符数除以 4 估算了一下"——你会算错

不同的模型用不同的 tokenizer。同一句话在不同 tokenizer 下的计数可以差 10–30%：

文本tiktoken (OpenAI)Anthropic偏差
"How many tokens does this sentence contain?"8 token9 token12.5%

这还是一句简单英文。中文更夸张——每个汉字可能 2–3 token。2,000 字的 Prompt 可能是 5,000–6,000 token。用字符数除以 4 估算就会偏出 20% 以上。

但更隐蔽的是"tokenizer 漂移"：你本地算的数，和 API 服务端实际扣费的数，之间经常差 5–15%。来源是那些本地看不到的东西——role 标记的 JSON 结构、tool schema 在请求信封中的格式化展开、多模态占位符的 token 化、推理模型的思考 token。

3.2 工具结果尖刺：一瞬间撑爆你的预算

你愉快地运行着，利用率 60%，一切正常。然后调了个搜索工具——它返回了 50,000 token 的网页内容。瞬间利用率跳到 92%。

这就是尖刺：单条返回结果远超预期，一步之内改变预算状态。

应对策略：

动态截断阈值：阈值不应该是常数，而应该根据当前利用率动态调整。

利用率 < 50% → 慷慨，允许大结果
利用率 50–80% → 保守，截断一半
利用率 > 80% → 告急，只留关键信息

事后补救：Claude Code 的做法是"先完整写入，再事后 snipping"。消息链结构保持完整（tool call 和 tool result 的对应关系不破坏），但内容被替换为 [Old tool result content cleared]。既回收了空间，又不破坏语义结构。

3.3 固定 Reserve 不够用

你设 reserve = 4096，Agent 在做重构，需要生成 8,000 token 的代码。模型被限制在 4,096 token——代码生成到一半被截断。

更进一步的方案是让 Agent 自己声明需要多少 reserve——通过一个特定 tool call 声明 required_reserve_tokens: 8000，系统据此调整当前轮次的 reserve。

压缩——不是要不要的问题，是怎么要的问题

4.1 分层：先用免费方案，再花钱

当预算告急，你只有三个选择：停止、截断、压缩。而压缩本身也要花钱——额外的 API 调用、信息损失、用户等待时间。

好的工程实践是从廉价到昂贵，只在必要时升级：

层级    策略          花费      回收能力    信息损失
─────────────────────────────────────────────────
L1     Snip/Pruning   零 LLM    中等       低（只清内容，保结构）
L2     微压缩         零 LLM    中等       低（基于时间衰减）
L3     主动重组       中等 LLM  高         中
L4     LLM 全文摘要   高 LLM    很高       高

L1 是最被低估的策略。 你已经 10 轮前搜过的文件内容、已经看完的网页、已经执行完的命令输出——这些信息已经"用过了"，清理它们不需要调用 LLM，不会破坏消息结构，却可以回收大量空间。

4.2 熔断器：当压缩本身也失败的时候

更糟的情况：压缩调用本身因为 prompt 太长而失败，然后重试，再失败。Claude Code 在引入熔断器之前，观测到 1,279 个会话出现超过 50 次连续压缩失败，每天浪费约 25 万次 API 调用。

熔断器逻辑很简单：连续失败 3 次 → 打开熔断 → 跳过后续压缩。成功一次就重置。

4.3 压缩不是终点

压缩后还要重新注入关键上下文。Claude Code 的规矩：

压缩后注入上限：
├── 总预算:    50,000 token
├── 单文件最多:  5,000 token
├── 最多恢复:    5 个文件
└── Skills:    25,000 token 总预算

还有个 truePostCompactTokenCount 函数专门检测"刚压缩完又立刻要触发压缩"的情况。

窗口越大，问题越严重

有一种常见错觉："上下文窗口从 128K 到 200K 到 1M，问题自然解决了。"

恰恰相反：窗口越大，预算管理越重要。

5.1 浪费的代价线性放大

每 token 价格固定。把 200K 窗口塞满花的钱是把 32K 塞满的 6.25 倍。但质量提升远非线性。Chroma 团队发现，塞入约 4,000 token（20 个检索文档）后，准确率就从 70–75% 掉到 55–60%。塞得越满，反而越差。

5.2 塞得越多，模型反而越"看不清"

Stanford 研究发现 U 形性能曲线：模型对开头和结尾的信息关注度高（85–95%），对中间关注度低（76–82%）。GPT-3.5-Turbo 在"埋在中段"的文档上准确率掉到 56.1%——比什么都不给它还差。

根源是 RoPE（Rotary Position Embedding）的"长程衰减"——距离越远的 token 获得越少注意力。100K token 规模下，模型要管理约 100 亿个两两关系，注意力被极度稀释。

5.3 成本曲线不是线性的

                         成本 ($) 持续线性增长 ↗
                        /
                      /
────────────────────
                      \
                        \  性能 / 准确率先平后降 ↘
                          \

每多塞 1,000 token，成本线性增加。但性能先平（说明冗余）再降（信息过载开始伤害判断）。

这就是预算管理的本质：你不是在管理"空间"，你是在管理"性价比"。

实际项目是怎么干的——Claude Code 和 Hermes Agent 分析

好了，理论讲完了。我们看看两个生产级系统是怎么做的。这两个项目的定位截然不同：


Claude CodeHermes Agent
出身Anthropic 官方 CLINous Research 开源框架
技术栈TypeScript / BunPython
模型适配专注 Claude 系列十几家 Provider 全兼容
核心哲学封闭生态极致优化开放兼容通用抽象

6.1 怎么知道模型窗口多大？

Hermes Agent——9 级解析：

一句话：Claude Code 假设你大概率在 Anthropic 生态里，所以简化。Hermes 假设你可能在任何地方，所以必须健壮。

6.2 怎么算 token 数？

这是两个项目最根本的分歧。

Claude Code——双轨制：

  • 热路径用近似估算（4 chars/token，JSON 用 2 chars/token，图片固定 2000）
  • 关键决策点用精确 API（beta.messages.countTokens）
  • 但这种精确只在 Anthropic 生态有效——OpenAI 和 Gemini 兼容层都退回近似

Hermes Agent——纯近似估算：

  • 全部用 4 chars/token
  • 图片固定 1500-1600
  • 但会额外计入 tool schemas（这点常被忽略，工具多的 Agent 可能多 20-30K）

为什么 Hermes 不做精确计数？ 因为要兼容十几个 Provider，每个的精确计数 API 都不一样。维护成本太高，不如直接降低触发阈值（50% 而不是 90%）来吸收估算偏差。

这是 token 预算管理的根本工程选择：

  • 花精力消除偏差 → 精确计数，阈值贴近物理上限（90%）
  • 花精力容忍偏差 → 近似估算，阈值留够安全边际（50%）

6.3 什么时候触发压缩？

Claude Code——四级渐进：

200K 窗口下：
∼167K → 警告闪烁（WARNING_BUFFER = 20K）
∼180K → 自动压缩（200K - 20K 预留 - 13K 额外缓冲）
∼197K → 阻塞新请求

反抖动机制：熔断器，连续失败 3 次就停。

Hermes Agent——单一阈值 50%：

threshold_tokens = max(context_length × 0.50, 64_000)
tail_token_budget = threshold_tokens × 0.20  # 保留最近 20%

反抖动机制：连续 2 次节省 < 10% 就抑制。

为什么 Hermes 用 50% 而 Claude Code 用 90%？ 又是计数的差别——近似估算必须留 30-40% 作为偏差缓冲。

6.4 压缩策略怎么分层的？

Claude Code 三层：                  Hermes 两层：
┌─ MicroCompact ── 零 LLM          ┌─ Pruning ── 零 LLM
│  清除旧工具输出                    │  去重+单行摘要+截断
├─ Session Memory ── 零 LLM        │
│  用预提取记忆做摘要                └─ LLM 摘要 ── 辅助模型
└─ API 摘要 ── LLM 全文总结           便宜模型做摘要，降级链兜底

共同点：都"先廉价再昂贵"。差异点：

  • Claude Code 有 Session Memory 层（依赖 Anthropic 内部实验功能）
  • Hermes 有辅助模型设计——让昂贵主模型的会话用便宜模型（如 Gemini Flash）做摘要，节省 90%+

6.5 几个值得专门拿出来说的细节

Prompt Cache 共享：Claude Code 压缩时用 forkedAgent 复用主线程的缓存前缀，缓存命中率从 2% 拉到接近 100%。Hermes 没有——多 Provider 下缓存行为不一致，做不了这种优化。这是**"封闭生态独享优化"的典型案例**。

Slot 优化：Claude Code 把 max_tokens 默认值从 32K 压到 8K。因为 API 服务端按 max_tokens 预留推理 slot，实际 p99 输出仅 4,911 tokens。降到 8K 后不到 1% 请求被截断（自动获得 64K 重试）。这是一个反直觉但有效的设计。

Session 轮转：Hermes 压缩成功后轮转 session_id（旧 session 标记 end_reason=compression，新 session 父子关联），加上 SQLite 原子锁防止并发压缩。Claude Code 没有——单 Agent 不需要。多 Agent 并发的系统应该抄这个。

Trajectory Compressor：Hermes 还有一个 1509 行的离线压缩器——把已完成的 Agent 运行历史压缩到 15,250 token 用于训练数据。这体现了研究机构特有的视角：Agent 的运行历史本身是可训练资产。

七个经过验证的工程模式

模式 1：分层压缩，先免费后付费

不管是 Claude Code 的"MicroCompact → SM → API 摘要"，还是 Hermes 的"Pruning → LLM 摘要"，核心都是先尝试零成本方案。大多数情况下，清理旧工具输出就够用了，根本不需要调 LLM。

模式 2：压缩边界要对齐消息语义

tool_use 和 tool_result 必须配对、thinking block 不能切断、最近 user 消息必须保留——压缩不是按 token 硬切，而是按消息语义切。两个项目都强调了这一点。

模式 3：保留头尾，压缩中间

这是 LLM 注意力分布（首因/近因效应）和任务结构（最初目标/最近上下文）的双重要求。具体保留多少可调，但保留位置必须是头尾。

模式 4：必须有反抖动

要么熔断器，要么节省阈值检查。核心：避免无效压缩反复消耗成本。Claude Code 的数据：引入熔断器前每天浪费 25 万次调用。

模式 5：精确 vs 近似，别骑墙

  • 单 Provider → 精确计数，阈值贴近物理上限
  • 多 Provider → 近似估算，阈值留够缓冲

既要精确又要通用，是工程灾难。

模式 6：摘要模型独立出来

Hermes 的思路——让 Claude Opus 或 GPT-5 的会话用 Gemini Flash 或 Haiku 做摘要。成本节省可达 90%+。

模式 7：压缩后必须显式重新注入

压缩不只是"压完了还剩多少"，还要考虑重要上下文需要显式恢复——文件、技能、配置、MCP 工具发现结果。
