开发工具

除了飞书 CLI，还有哪些你不知道的开发者命令行工具？

Eva·2026.05.06·12 分钟阅读

 

现在到底还有多少工具，已经悄悄把核心能力搬进了命令行？

过去，CLI 似乎更多属于程序员的本地工具箱：用来查文件、跑脚本、发请求、部署服务。但现在，CLI 的边界正在迅速扩展。飞书可以通过命令行连接消息、日历、文档和 Agent 工作流；GitHub 可以通过 CLI 管理 PR 和 issue；云厂商可以通过 CLI 操作服务器、数据库和存储；AI 工具也开始以 CLI 的形式进入终端。

这就带来一个很有意思的问题：除了飞书 CLI 之外，还有哪些大家可能并不知道、但已经非常重要的 CLI 工具？

如果把视野放大，我们会发现，CLI 早已不只是“程序员敲命令”的工具，而是现代软件工程的一套通用接口。它连接协作平台、云服务、AI 模型、容器、CI/CD、安全扫描和开发效率工具。尤其在 AI Agent 时代，CLI 的价值会被进一步放大，因为 Agent 要真正完成工程任务，就必须能够调用这些稳定、可自动化、可组合的命令行工具。

awesome-cli （https://github.com/Eva-Dengyh/awesome-cli） 这类工具收录企业协作、云服务、AI/LLM、文件处理、网络调试、容器与 K8s、IaC、安全扫描、开发效率等方向的高质量 CLI 工具（均为 GitHub 10k+ star 或官方出品），帮助开发者和 AI Agent 通过命令行完成各类工程任务。它并不是简单罗列命令行工具，而是在整理一个面向开发者与 AI Agent 的现代工程工具生态。

CLI 是现代工程体系的通用接口

在过去很长一段时间里，命令行工具一直被视为开发者的“效率利器”。无论是搜索文件、处理 JSON、管理云资源，还是部署应用、扫描安全风险，CLI 都以轻量、可组合、可脚本化的方式，成为工程体系中最稳定的一层基础设施。

但随着 AI Agent 进入软件工程流程，CLI 的价值正在被重新放大。

对人类开发者来说，CLI 是高效操作系统和工程环境的入口；而对 AI Agent 来说，CLI 则是连接真实世界工具链的执行接口。一个 Agent 如果只能“生成建议”，它的能力是有限的；但如果它能够调用 GitHub、云平台、CI/CD、数据库、安全扫描、文件处理等 CLI 工具，它就可以真正参与到需求分析、代码修改、测试验证、部署发布、故障排查等完整工程流程中。

CLI 之所以经久不衰，一个重要原因是它足够通用。

图形界面适合人类浏览和点击，API 适合程序之间集成，而 CLI 则处在两者之间：它既能被人直接使用，也能被脚本、CI/CD 系统和 AI Agent 调用。它天然适合自动化，输入输出清晰，容易组合，也更容易沉淀为标准化流程。

例如，开发者可以通过 GitHub CLI 查看 issue、创建 pull request、触发 workflow；通过 AWS CLI、阿里云 CLI、腾讯云 CLI 管理云资源；通过 Terraform 或 OpenTofu 声明和变更基础设施；通过 Trivy、Gitleaks、TruffleHog 扫描镜像、代码和密钥泄露风险。这些操作原本分散在不同平台和控制台中，但 CLI 将它们统一到了命令行这个共同界面下。

当 AI Agent 参与进来时，这种统一接口变得更加重要。Agent 不需要理解每个平台复杂的图形界面，只需要理解命令、参数、输出和错误信息，就能把一个个工具串联起来，完成更复杂的工程任务。

协作平台 CLI：让工程沟通进入自动化流程

现代软件开发首先是协作。代码、需求、缺陷、评审、发布和文档，往往分布在多个协作平台中。

在国际协作平台中，GitHub CLI 和 GitLab CLI 是最典型的代表。它们让开发者可以直接在终端中管理 pull request、merge request、issue、pipeline 和 workflow。Jira CLI 则进一步把任务管理和缺陷跟踪带入命令行，让开发者不必频繁切换浏览器页面。

在国内企业场景中，飞书、钉钉、企业微信等平台也开始提供或探索 CLI 能力。这意味着消息、日历、文档、审批、会议、组织协作等能力，都有机会被纳入自动化工作流。对于 AI Agent 来说，这类工具尤其关键，因为它们连接的不只是代码仓库，而是团队协作本身。

一个工程 Agent 可能不仅能修改代码，还能根据 issue 内容创建分支、完成实现、提交 PR、生成变更说明，并把结果同步到团队协作平台。这背后的基础，正是这些协作平台 CLI。

云服务 CLI：从控制台操作走向可编排基础设施

云服务是 CLI 生态中最成熟的领域之一。

AWS CLI、阿里云 CLI、腾讯云 CLI、华为云 KooCLI、京东云 CLI、火山引擎 CLI 等工具，覆盖了计算、存储、网络、数据库、权限、监控等大量云产品能力。过去需要在控制台里完成的操作，现在都可以通过命令行执行，并进一步写入脚本、CI/CD 流程或 Agent 工作流。

这带来的变化很明显：云资源管理从“人工点击”变成了“可记录、可复现、可审计”的工程过程。

对于企业来说，CLI 化的云管理能力可以降低重复操作成本，减少人为失误，也方便和权限系统、发布系统、安全系统集成。对于 AI Agent 来说，云服务 CLI 则提供了直接操作基础设施的入口。当然，这也意味着权限控制、审计日志和安全边界会变得更加重要。

AI 工具 CLI：大模型能力正在进入终端

AI 工具本身也在 CLI 化。

Ollama 让开发者可以在本地运行大语言模型，适合私有化、离线或低延迟场景。Simon Willison 的 llm 工具提供了通用的大模型命令行接口，可以把不同模型能力接入终端工作流。国内厂商也在推出面向开发者和 Agent 场景的 AI CLI，例如火山引擎 veCLI、腾讯 AI CLI 等。

这类工具的意义在于，它们让“调用模型”不再局限于网页聊天窗口或应用内功能，而是成为命令行中的一个可组合能力。

例如，开发者可以把日志通过管道传给模型总结异常原因，把代码 diff 传给模型生成 review 建议，把文档片段传给模型提取摘要。AI 能力一旦进入 CLI，就可以和 jq、rg、fzf、git、curl、kubectl 等传统工具组合，形成新的开发范式。

文件处理 CLI：开发者效率的基础层

如果说云服务和协作平台 CLI 连接的是外部系统，那么文件处理工具连接的就是开发者每天面对的本地工程环境。

ripgrep、fd、fzf、bat、jq、yq 这类工具已经成为现代命令行工作流中的基础组件。它们解决的问题看似朴素：搜索文本、查找文件、预览内容、处理 JSON、处理 YAML。但这些能力正是理解和操作大型代码库的前提。

在 AI Agent 场景下，这些工具同样重要。Agent 需要搜索代码、定位配置、读取日志、解析结构化数据、筛选关键信息。高质量的文件处理 CLI 可以让 Agent 更快、更准确地理解项目上下文，也能减少无效扫描和错误判断。

换句话说，文件处理工具不仅提升人的效率，也提升 Agent 的工程执行能力。

网络与 API CLI：调试服务的第一现场

在后端开发、微服务和平台工程中，网络与 API 调试是高频任务。

hurl 可以用纯文本文件描述和测试 HTTP 请求，适合把接口验证纳入版本管理。grpcurl 则为 gRPC 服务提供了类似 curl 的调试体验。mitmproxy 可以进行 HTTPS 代理和流量分析，用于排查请求、响应、认证和数据传输问题。

这些工具共同构成了服务调试的第一现场。相比图形化 API 工具，CLI 更容易进入自动化测试、持续集成和故障排查脚本中。

对于 AI Agent 来说，网络与 API CLI 可以让它不只是“阅读代码推测接口行为”，而是实际发起请求、观察响应、验证假设。工程智能体要从“代码助手”走向“调试助手”，这类工具不可或缺。

容器、Kubernetes 与 CI/CD CLI：现代交付链路的核心

现代应用交付高度依赖容器、Kubernetes 和 CI/CD，而这些领域几乎天然围绕 CLI 构建。

kubectl 是 Kubernetes 操作的事实标准入口，helm 负责 Kubernetes 应用打包和发布，kubectx 帮助开发者快速切换集群上下文和命名空间，dive 可以分析 Docker 镜像层，帮助优化镜像体积和排查构建问题。

在 CI/CD 领域，act 可以在本地运行 GitHub Actions，ArgoCD 支持 GitOps 持续交付，Dagger 和 Earthly 则提供更可编程、更可复现的构建与流水线能力。

这些工具让软件交付从“某台机器上的手工步骤”转变为“可声明、可执行、可验证的流水线”。当 AI Agent 能够调用这些 CLI 时，它就可以参与构建失败分析、流水线修复、部署状态检查，甚至在受控权限下完成发布前验证。

IaC 与安全 CLI：把风险控制前移

基础设施即代码和安全扫描，是 CLI 生态中非常适合自动化的两个方向。

Terraform 和 OpenTofu 让基础设施变更可以像代码一样被管理、评审和回滚。Infracost 可以在变更前估算云成本，帮助团队在 pull request 阶段看到成本影响。Trivy、Gitleaks、TruffleHog 则分别覆盖容器安全、依赖风险、代码扫描和密钥泄露检测等场景。

这些工具的共同价值，是把风险控制前移。

过去，很多安全问题和成本问题会在上线后才暴露；现在，它们可以在提交代码、构建镜像、创建 PR 或部署前被自动发现。对企业工程体系来说，这意味着更稳定的交付质量；对 AI Agent 来说，这意味着它不仅能“完成任务”，还可以在执行过程中主动验证风险。

开发效率与 Shell 增强：命令行体验也在现代化

CLI 生态并不只关心大型系统，也关心开发者每天的细节体验。

just 和 task 提供了比传统 Makefile 更现代的任务运行方式；hyperfine 可以对命令进行基准测试；navi 和 tldr 降低了记忆复杂命令的成本；direnv 让项目级环境变量自动加载；zoxide、atuin、eza、delta 则分别改善目录跳转、历史搜索、文件列表和 git diff 体验。

这些工具看似分散，但共同指向一个趋势：命令行正在从“黑底白字的低级入口”变成高度现代化、可定制、智能化的开发环境。

当这些工具被组合起来，终端就不只是执行命令的地方，而是一个集搜索、导航、调试、分析、部署、协作于一体的工程工作台。

AI Agent 时代，CLI 的价值会进一步上升

如果只从人类开发者的角度看，CLI 的价值是效率；但从 AI Agent 的角度看，CLI 的价值是可执行性。

AI Agent 需要真实地操作工程系统，而不是停留在文本建议层面。它需要读取文件、搜索代码、调用接口、运行测试、管理 issue、检查 CI、扫描安全风险、部署服务、同步协作平台。完成这些任务的最佳接口，往往不是网页，也不是孤立 API，而是已经被工程体系广泛验证过的 CLI。

这意味着，未来判断一个工具是否适合 AI Agent 使用，一个重要标准可能是：它有没有稳定、清晰、可自动化的命令行接口。

对工具厂商来说，CLI 不再只是高级用户的附属功能，而可能成为 AI Agent 接入生态的关键入口。对开发团队来说，整理和标准化内部 CLI，也会成为构建 Agent-native 工程体系的重要基础。

最后

awesome-cli（https://github.com/Eva-Dengyh/awesome-cli） 所整理的并不是一份普通工具清单，而是一张现代开发者 CLI 生态地图。

从企业协作到云服务，从 AI 工具到文件处理，从网络调试到 Kubernetes，从 CI/CD 到安全扫描，再到 Shell 体验增强，CLI 正在覆盖软件工程的几乎每一个环节。它既服务于开发者个人效率，也服务于团队工程自动化，更将在 AI Agent 时代成为连接智能体与真实工程系统的重要桥梁。

未来的软件工程不会只发生在 IDE 里，也不会只发生在网页控制台里。越来越多的工程能力会沉淀到命令行中，被人类、脚本、流水线和 AI Agent 共同调用。

理解 CLI 生态，就是理解现代软件工程的自动化底座。
