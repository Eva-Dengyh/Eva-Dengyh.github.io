为什么 AI 流式输出更偏爱 SSE 而不是 WebSocket？

Eva·2026.05.28·9 分钟阅读

 

观察一下主流 AI 产品的网络层，会发现一个比较一致的现象：处理流式回复的传输层，多数选择了 SSE（Server-Sent Events），而不是看起来更"实时"的 WebSocket。OpenAI 的 /v1/chat/completions 在 stream: true 时返回的是 SSE，Anthropic 的 Messages API 流式接口也是 SSE，Hugging Face 的 Text Generation Inference 同样默认 SSE。

这不是巧合，是在软件工程里非常经典的“奥卡姆剃刀原理”（如无必要，勿增实体）的体现，是协议特性和工程成本权衡之后的结果。在解释原因之前，先把这两个协议本身讲清楚。

什么是 SSE

SSE 全称 Server-Sent Events，是 HTML5 规范的一部分，定义在 WHATWG HTML Living Standard 里。它的本质是一个普通的 HTTP 响应，只是服务端不一次性把响应体写完，而是保持连接打开，按特定格式不断追加数据。

它的传输格式非常简单，基于 text/event-stream 这个 MIME 类型，每条消息的结构大致是：

data: 第一段内容

data: 第二段内容

event: custom
data: 带自定义事件类型的内容

id: 42
data: 带 ID 的内容，用于断线续传

每条消息之间用一个空行分隔。浏览器原生提供 EventSource API 来消费这个格式：

const es = new EventSource('/api/stream');
es.onmessage = (e) => console.log(e.data);

SSE 的几个关键协议特性：

  • 基于 HTTP，没有协议升级，没有自定义帧
  • 单向，只能服务端推给客户端
  • 文本协议，只支持 UTF-8，不支持二进制（要传二进制得自己 base64）
  • 自带重连，连接断开后 EventSource 默认会自动重连
  • 支持事件 ID 和续传，通过 Last-Event-ID 请求头告知服务端从哪里继续

什么是 WebSocket

WebSocket 定义在 RFC 6455 里，是一个独立的应用层协议。它通过一次 HTTP 升级握手（Upgrade: websocket）建立连接，握手成功之后，连接就脱离 HTTP 语义，进入 WebSocket 自己的帧协议。

它的特性更"重"也更通用：

  • 全双工，建立连接后双方都能随时发消息
  • 基于帧，有自己的二进制帧格式，支持文本帧和二进制帧
  • 长连接，连接一旦建立就保持，直到任一端主动关闭
  • 不自带重连，断线后需要应用层自己处理
  • 不自带鉴权，握手阶段虽然是 HTTP 但浏览器 API 不允许设置自定义 header

协议特性对比

把核心差异列出来：

维度SSEWebSocket
通信方向服务端 → 客户端双向
底层协议HTTP（响应未完成的状态）独立协议（HTTP 升级后切换）
数据类型仅 UTF-8 文本文本 + 二进制
浏览器 APIEventSourceWebSocket
自动重连有无
断点续传有（Last-Event-ID）无
自定义请求头支持（普通 HTTP 请求）浏览器 API 不支持
HTTP 中间件兼容完全兼容需要专门支持

为什么 AI 流式输出选 SSE

把上面的特性放到 AI 流式输出这个具体场景里看，几个原因就显出来了。

1. AI 流式输出本质上是单向流

LLM 的推理过程是这样的：客户端发一次请求，服务端开始 token-by-token 生成，每生成一些就推给客户端。这个过程中，客户端不需要再发任何消息——既不需要插话，也不需要确认，也不需要心跳。等本轮回答结束，下一次提问是一个新的 HTTP 请求。

换句话说，这是请求-响应模式，只是响应体被拉长成了一个流。WebSocket 提供的双向能力在这里用不上，付出了协议复杂度的成本，却没有用到收益。

值得说明的一点：少数 AI 场景是真双向的，比如 OpenAI 的 Realtime API 处理语音对话，需要客户端持续推音频帧、服务端持续推音频和转写文本，那个场景 OpenAI 用的就是 WebSocket（以及 WebRTC）。这反过来印证了选型逻辑——真需要双向的时候才上 WebSocket。

2. HTTP 生态可以直接复用

SSE 是 HTTP 响应，意味着 HTTP 这一整套基础设施都能直接用：

  • 反向代理和负载均衡：Nginx、HAProxy、ALB 处理 HTTP 流式响应是标配能力
  • CDN：Cloudflare、Fastly 等支持 SSE 透传，部分还能针对 SSE 优化
  • 鉴权：Authorization header、Cookie、各种 OAuth 流程不用动
  • HTTP/2 多路复用：一个 TCP 连接上可以并发多个 SSE 流
  • 可观测性：现有的 HTTP 监控、日志、链路追踪工具都能继续用

WebSocket 在协议升级之后就不再是 HTTP 流量了，对中间件来说是一团不透明的字节流。这导致一些实际工程上的麻烦，比如某些早期的负载均衡器不支持 WebSocket、某些企业网络环境会拦截或限制非 HTTP 流量、CDN 对 WebSocket 的支持通常需要单独配置。

3. 鉴权模式更顺

这是一个浏览器端经常踩的坑：浏览器原生的 WebSocket 构造函数不允许设置自定义请求头。这是历史遗留问题，写在规范里的。

// 不行，没有第三个参数
new WebSocket(url, protocols, { headers: { Authorization: 'Bearer xxx' } });

结果就是 WebSocket 的鉴权在浏览器里只能走以下几种相对别扭的方式：

  • 把 token 拼到 URL query 里（会被日志、referer 记录）
  • 用 Cookie（需要同域）
  • 用 Sec-WebSocket-Protocol 把 token 塞进去（属于 hack）
  • 连接建立后第一条消息发鉴权信息（连接已经建立才鉴权）

SSE 走的就是普通 HTTP 请求，Authorization header 怎么用就怎么用，没有这些拐弯。

4. 服务端实现更轻

WebSocket 是有状态长连接，服务端要维护连接对象、心跳、状态机、关闭流程。SSE 在服务端的实现可以非常简单：拿到请求，设置响应头，循环写 chunk，写完关掉连接。下面是一个 Node.js 的最小例子：

app.get('/stream', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');

  for await (const token of llm.stream(prompt)) {
    res.write(`data: ${JSON.stringify({ token })}\n\n`);
  }
  res.end();
});

不需要专门的 WebSocket 框架，不需要管理连接池，连接关闭就是 HTTP 响应结束。

5. 断线重连和续传开箱即用

EventSource 默认会在断线后自动重连，重连时会带上最后收到的 id 作为 Last-Event-ID 头，服务端可以据此续传。在网络不稳定的移动端场景里这是个很实用的特性。WebSocket 这块完全要应用层自己实现。

SSE 的局限和工程上要注意的点

平心而论，SSE 不是没有短板，几个常见的：

只能服务端推。一旦需要客户端在流过程中插话（比如打断生成、调整参数），SSE 就不够了。这种场景要么用 WebSocket，要么 SSE 配一个独立的控制接口（用另一个 HTTP 请求发取消信号）。OpenAI、Anthropic 都选的是后一种思路。

EventSource 只支持 GET。但 AI 请求的 body 通常很大（带历史消息、system prompt、各种参数），必须用 POST。这导致几乎所有 AI 厂商的 SDK 都不直接用 EventSource，而是用 fetch + ReadableStream 自己解析 SSE 格式。OpenAI 的 SDK、Anthropic 的 SDK 都是这个做法。这一点是工程上的实际成本。

HTTP/1.1 下的并发连接数限制。浏览器对同一域名的 HTTP/1.1 连接数有上限（一般是 6），多个 SSE 会挤占名额。HTTP/2 以上多路复用解决了这个问题，但如果服务端还在跑 HTTP/1.1，就要留意。

代理缓冲。Nginx 这类反向代理默认会缓冲响应，会破坏流式效果。需要显式关闭，比如设置响应头 X-Accel-Buffering: no，或者在 Nginx 配置里关掉 proxy_buffering。

长连接超时。各级网关、负载均衡器都有自己的空闲超时设置（AWS ALB 默认 60 秒，Cloudflare 免费版 100 秒），AI 长回复可能撞上。需要调整超时，或者通过定期发 SSE 注释行（:\n\n）来保活。

小结

SSE 和 WebSocket 解决的是不同形状的问题。WebSocket 是为真正的双向实时通信设计的，AI 流式输出并不是这种形状——它是一个被拉长的请求-响应。在这个形状下，SSE 因为继承了 HTTP 的所有基础设施、鉴权简单、实现轻量、自带重连，工程成本明显更低。

WebSocket 并没有过时，在多人协作、实时游戏、信令交换、语音对话这类需要双向通信的场景里仍然是合适的选择。但对 AI 文本流这种单向流场景，SSE 是更顺手的工具，主流厂商的一致选择反映的就是这一点。
