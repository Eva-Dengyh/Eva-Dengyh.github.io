开发工具

从聊天上下文到工程真相源：用 OpenSpec 分析 AI 编程时代的规格驱动开发

Eva·2026.05.22·17 分钟阅读

 

导读

在 AI Coding 已经进入日常研发之后，为什么“需求只存在于聊天窗口里”会成为工程交付的隐性风险；以及 OpenSpec 这类规格驱动开发工具，如何把一次次容易漂移的 AI 协作，收束成可审查、可继续、可归档的工程闭环。

OpenSpec 不是一个新的代码生成器，也不是一个更复杂的项目管理系统。

它更像是给 AI 编程助手加了一层轻量的“规格轨道”：写代码前先对齐要做什么，开发中把变化沉淀成文档，完成后把增量规格合并回项目当前真相源。换句话说，它解决的不是“AI 会不会写代码”，而是“AI 写代码之前，人与模型到底有没有对齐目标；写完之后，这次变化有没有被项目长期记住”。

文章内容基于 OpenSpec 官方文档、GitHub 项目说明，以及我在本地项目中使用 OpenSpec 的工程观察整理，旨在分享一种可落地的 AI 协作方法，仅代表个人观点。

一、为什么 AI 编程需要一层规格轨道？

过去一年，AI 编程工具的讨论大多集中在几个问题上：哪个模型更聪明，哪个 IDE 集成更顺手，怎么写 Prompt 才能让 Agent 一次性改对。

这些当然重要。但当你真的把 AI 编程助手放进一个持续演进的项目里，会发现更棘手的问题不是“它会不会写代码”，而是：

  • 它到底理解了这次需求的边界吗？
  • 它改代码时依据的是当前项目事实，还是聊天窗口里的临时印象？
  • 如果这轮对话断了，下一轮还能无损接上吗？
  • 如果多人同时开发，谁知道某个需求为什么这么设计？
  • 如果三周后线上出了问题，还能不能回到当时的设计上下文？

传统人工开发里，这些问题靠需求文档、设计评审、任务拆解、PR Review、测试用例来缓冲。AI 编程助手出现后，很多团队反而把这些缓冲层压缩成了一段聊天：

“帮我加个暗色模式。”

“顺便兼容系统主题。”

“刚才那个设计不对，改成 localStorage。”

“继续。”

这在 Demo 里很顺。在真实项目里，它会慢慢变成上下文债务。

因为聊天窗口不是工程真相源。聊天窗口适合沟通，但不适合承载长期需求；适合探索，但不适合当作团队可审查、可回滚、可交接的记录系统。

OpenSpec 要解决的，正是这条断裂：把 AI 协作从“临时聊天”拉回“仓库内可版本管理的规格工作流”。

二、OpenSpec 到底是什么？

OpenSpec 是一个面向 AI 编程助手的轻量级规格驱动开发（Spec-Driven Development，SDD）框架。它通过 CLI、Slash Commands 和 Skills，把“提案、规格、设计、任务、归档”这些工作产物放进代码仓库，让人和 AI 在写代码之前先对齐要构建的内容。

如果只用一句话概括：

OpenSpec 是把需求上下文从聊天窗口搬进代码仓库的规格工作台。

它不是让 AI 更“自由”的工具，而是让 AI 的自由度有轨道可走。

OpenSpec 初始化后，项目里会出现一个 openspec/ 目录，大体结构如下：

openspec/
├── specs/
│   └── <domain>/
│       └── spec.md
├── changes/
│   └── <change-name>/
│       ├── proposal.md
│       ├── design.md
│       ├── tasks.md
│       └── specs/
│           └── <domain>/
│               └── spec.md
└── config.yaml

这里有两个关键目录：

  • openspec/specs/：项目当前行为的主规格库，是需求层面的 Source of Truth。
  • openspec/changes/：正在进行的变更，每个变更独立成一个文件夹，里面放提案、设计、任务和规格增量。

这就是 OpenSpec 的基本判断：

当前系统怎么工作，放在 specs/；这次准备怎么改，放在 changes/。

这种分离看起来简单，但对 AI 协作非常关键。因为它把“系统当前状态”和“本次变更意图”分开了，让模型不必在一段越来越长的聊天里猜测项目事实。

三、OpenSpec 和普通文档有什么区别？

很多人第一次看到 OpenSpec，会觉得它不就是在项目里多放几份 Markdown 吗？

如果只是这样，没必要专门引入一个工具。OpenSpec 真正有价值的地方，不是“写文档”，而是把文档变成 AI 协作过程里的可执行控制面。

普通文档常见的问题是：

  • 写完就没人看。
  • 设计变了没人改。
  • 和代码脱节后变成历史包袱。
  • AI 不知道该读哪一份。
  • 多人协作时没有统一入口。

OpenSpec 的做法是把文档嵌进工作流：

  • /opsx:propose 先创建变更提案和配套产物。
  • /opsx:apply 按 tasks.md 执行，并随着进度打勾。
  • /opsx:sync 把增量规格同步到主规格。
  • /opsx:archive 在完成后归档变更，保留历史上下文。

这意味着文档不是旁路产物，而是 AI 工作的输入、过程和验收依据。

一句话说：

普通文档记录“我们曾经想过什么”，OpenSpec 约束“这次变更应该怎么被理解、实现和沉淀”。

四、核心概念：OpenSpec 在管什么？

要理解 OpenSpec，先要抓住四个对象：Spec、Change、Artifact、Delta Spec。

1. Spec：系统当前行为的真相源

openspec/specs/ 里的 spec 描述的是系统当前应该具备的行为。它不是实现计划，也不是代码结构说明。

好的 spec 关注的是外部可观察行为：

  • 用户做了什么？
  • 系统应该返回什么？
  • 异常场景怎么处理？
  • 安全、兼容、性能、权限有什么要求？
  • 哪些行为可以被测试验证？

它不应该写成：

在 UserService.ts 里新增 createUserWithProfile 方法。

更适合写成：

### Requirement: 用户注册

系统 SHALL 在用户提交合法邮箱和密码后创建账号，并返回登录态。

#### Scenario: 合法注册
- GIVEN 用户输入未注册邮箱和符合规则的密码
- WHEN 用户提交注册表单
- THEN 系统创建账号
- AND 用户进入已登录状态

Spec 管的是“系统应该表现成什么样”，不是“程序员打算怎么写”。

2. Change：一次变更的独立工作区

openspec/changes/<change-name>/ 是一次变更的工作区。

一个 change 通常包含：

  • proposal.md：为什么做、做什么、范围在哪里。
  • specs/：这次对主规格的增量修改。
  • design.md：技术方案和关键决策。
  • tasks.md：实现任务清单。
  • .openspec.yaml：可选的变更元数据。

这很像 Git 分支，但它管理的不是代码差异，而是需求和设计差异。

代码分支回答的是：

这次代码改了什么？

OpenSpec change 回答的是：

这次为什么要改、准备怎么改、改完后系统行为应该变成什么样？

3. Artifact：把模糊想法拆成可推进产物

Artifact 是 change 里的工作产物。

默认的 spec-driven 流程大致是：

proposal -> specs -> design -> tasks -> implement

它不是为了制造仪式感，而是把一个模糊需求拆成几个不同层次的问题：

  • proposal.md 解决“为什么做、边界是什么”。
  • specs/ 解决“系统行为怎么变”。
  • design.md 解决“技术上怎么落地”。
  • tasks.md 解决“下一步按什么顺序执行”。

这四类问题如果全部塞进一句 Prompt，模型很容易把它们混在一起。OpenSpec 把它们拆开，AI 才能更稳定地接收、更新和执行。

4. Delta Spec：只描述这次变化

Delta Spec 是 OpenSpec 很关键的设计。

它不要求你每次重写完整规格，而是用增量形式说明：

  • ADDED Requirements：新增了什么行为。
  • MODIFIED Requirements：修改了什么既有行为。
  • REMOVED Requirements：移除了什么行为。

这非常适合已有项目。因为真实工程里，大多数工作不是从零写一个新系统，而是在既有系统上改一小段行为。

全量文档的问题是：读者要自己在脑子里做 diff。

Delta Spec 的价值是：它直接告诉你这次 diff 是什么。

五、OPSX 工作流：从 /opsx:propose 到 /opsx:archive

截至 2026-05-22，OpenSpec 官方文档推荐的新工作流是 OPSX。默认 core profile 包含：

  • /opsx:propose
  • /opsx:explore
  • /opsx:apply
  • /opsx:sync
  • /opsx:archive

如果开启 expanded workflow，还可以使用：

  • /opsx:new
  • /opsx:continue
  • /opsx:ff
  • /opsx:verify
  • /opsx:bulk-archive
  • /opsx:onboard

但对大多数团队来说，先掌握默认路径就够了：

/opsx:propose -> /opsx:apply -> /opsx:sync -> /opsx:archive

1. /opsx:explore：想法还不成熟时先探索

当需求还模糊，不要急着创建正式变更。

比如：

/opsx:explore 我想给订单列表加一个批量导出能力，但还不确定要导出哪些字段，也不确定权限怎么卡。

这一阶段适合让 AI：

  • 阅读现有代码和规格。
  • 梳理业务边界。
  • 找出可能影响的模块。
  • 对比几种实现路线。
  • 帮你把模糊想法压成可提案的需求。

探索模式的价值不是“多聊一会儿”，而是防止在没想清楚时直接让模型改代码。

2. /opsx:propose：正式创建变更

当目标比较清楚时，可以创建 change：

/opsx:propose 为订单列表添加批量导出 CSV 能力

AI 会基于项目上下文创建类似目录：

openspec/changes/export-orders-csv/
├── proposal.md
├── design.md
├── tasks.md
└── specs/
    └── orders/
        └── spec.md

这一步要重点审查三件事：

  • 需求意图是否正确。
  • 范围是否过大。
  • 非目标是否写清楚。

如果这一步没卡住边界，后面的实现越快，偏得越远。

3. /opsx:apply：按任务清单实现

提案确认后再进入实现：

/opsx:apply export-orders-csv

AI 会读取 change 里的 artifacts，并按 tasks.md 执行。完成一项后，任务清单会被打勾：

## 1. Export API
- [x] 1.1 增加订单导出接口
- [x] 1.2 校验导出权限
- [ ] 1.3 增加导出字段映射

这一步的关键不是“让 AI 自动做完”，而是让它每次都围绕已经审查过的任务轨道推进。

如果实现过程中发现设计不对，不要硬往下冲。更好的做法是更新 design.md 或 specs/，再继续 /opsx:apply。

4. /opsx:sync：把增量规格同步到主规格

OpenSpec 的主规格在 openspec/specs/，变更期间的规格增量在 openspec/changes/<name>/specs/。

当你希望把 delta spec 合并回主规格时，可以执行：

/opsx:sync export-orders-csv

这一步的意义是：让项目当前行为的真相源随变更更新。

不是所有团队都必须手动执行 sync，因为 archive 往往会提示或处理同步。但理解这一步很重要：OpenSpec 的完整闭环不是“代码写完”，而是“主规格也反映了代码写完后的系统行为”。

5. /opsx:archive：完成后归档

功能完成、验证通过后：

/opsx:archive export-orders-csv

OpenSpec 会把变更移动到归档目录，例如：

openspec/changes/archive/2026-05-22-export-orders-csv/

归档不是清理垃圾，而是保留决策历史。

三个月后你想知道“为什么订单导出没有包含成本价字段”，最应该看的不是某个 PR 里零散的讨论，而是当时的 proposal、design、delta spec 和 tasks。

六、OpenSpec 真正有用的场景

OpenSpec 不是所有改动都要用。它最适合那些“如果只靠聊天，很容易丢边界”的工作。

1. 新功能

新功能往往涉及范围定义、用户行为、接口约定、错误场景和测试验收。直接让 AI 写代码，容易跳过需求澄清。

OpenSpec 可以先把新功能压成：

  • Intent
  • Scope
  • Requirements
  • Scenarios
  • Design
  • Tasks

然后再实现。

2. 修改既有行为

修改既有行为比新增功能更需要 spec。

因为你要回答的不只是“新增什么”，还要回答：

  • 哪个旧行为被改变？
  • 旧行为是否还有兼容要求？
  • 哪些下游依赖会受影响？
  • 测试应该改还是应该新增？

Delta Spec 的 MODIFIED Requirements 正好适合表达这种变化。

3. 大规模重构

重构最怕的是“代码结构变了，外部行为也被不小心改了”。

OpenSpec 可以把外部行为固化在 spec 里，让 AI 在重构时知道哪些行为不能破坏。这里的 spec 不是实现方案，而是行为边界。

4. 跨团队或长周期任务

当任务跨多人、跨天、跨会话时，聊天上下文会迅速腐烂。

OpenSpec 的 change 文件夹能成为交接点：

  • 新人先读 proposal，知道为什么做。
  • 再读 specs，知道行为怎么变。
  • 再读 design，知道技术路线。
  • 最后读 tasks，知道当前做到哪里。

这比让人翻聊天记录可靠得多。

5. AI Agent 协作

OpenSpec 对 AI Agent 特别有价值。因为 Agent 的问题不是不会执行，而是容易在长链路里漂移。

proposal.md、design.md、tasks.md 和 delta specs 相当于给 Agent 提供了外部记忆和阶段目标。

这不是把 Agent 管死，而是让它每一步都有可回看的任务轨道。

七、OpenSpec 和 AI Agent Harness 的关系

如果把 AI 编程助手看成一个非确定性执行者，OpenSpec 做的事情其实很像 Harness 里的“真相源”和“阶段控制”。

它提供的不是运行时沙盒，也不是权限审批系统，而是规格层的控制面：

  • 用 specs/ 固化系统当前行为。
  • 用 changes/ 隔离本次变更意图。
  • 用 proposal.md 卡住目标和边界。
  • 用 delta spec 卡住行为变化。
  • 用 design.md 卡住技术路线。
  • 用 tasks.md 卡住执行节奏。
  • 用 archive 卡住交付闭环和历史追溯。

所以 OpenSpec 不是完整 Harness，但它是 AI 编程 Harness 里非常关键的一层：Spec is Truth。

它解决的是 AI 协作里最常见的上下文问题：

模型可以忘，聊天可以断，但仓库里的规格不能丢。

八、总结

AI 编程时代的工程命题，不只是“让模型替我们多写代码”。

更深一层的问题是：如何让模型在写代码前理解目标，在写代码时不丢边界，在写完后把这次变化沉淀进项目长期记忆。

OpenSpec 的价值正是在这里。

它不是一个更聪明的 Agent，也不是一个更重的需求系统。它是一层轻量规格轨道，把一次 AI 协作拆成可审查、可继续、可同步、可归档的工程闭环。

对个人开发者来说，OpenSpec 能减少“下一轮对话忘了上次为什么这么改”的上下文损耗。

对团队来说，OpenSpec 能把 AI 参与开发后的需求、设计、任务和历史决策重新放回代码仓库，让 Review 不再只盯代码 diff，也能先审查意图和行为变化。

对 AI Agent 来说，OpenSpec 提供了外部真相源。模型可以继续高效执行，但它不再只靠聊天窗口里的临时记忆前进。

说得更直白一点：AI Coding 的问题正在从“能不能生成代码”迁移到“能不能稳定交付变化”。而 OpenSpec 的作用，就是让变化在进入代码之前先被定义，在实现过程中被约束，在完成之后被项目记住。

附：OpenSpec 快速命令清单

安装与初始化

npm install -g @fission-ai/openspec@latest
cd your-project
openspec init

指定工具初始化

openspec init --tools claude,cursor
openspec init --tools all
openspec init --tools none

常用 Slash Commands

/opsx:explore <想法或问题>
/opsx:propose <要构建的能力>
/opsx:apply <change-name>
/opsx:sync <change-name>
/opsx:archive <change-name>

常用 CLI

openspec --version
openspec list
openspec show <change-name>
openspec validate <change-name> --strict
openspec status --change <change-name>
openspec list --specs
openspec view
openspec update

Expanded Workflow

openspec config profile
openspec update

启用后可按需要使用：

/opsx:new
/opsx:continue
/opsx:ff
/opsx:verify
/opsx:bulk-archive
/opsx:onboard
